1.2 第 2 节：遥测规模、成本与覆盖率

按 10,000 个 OSD、每个 80 个指标、每 15 秒一采，估算三副本一年占用和 30 天全量扫描的数据量。

序列数 = 10,000 × 80 = 800,000
每天样本 = 800,000 × 86,400 / 15 = 4,608,000,000（46.08 亿）
2 字节/样本：9.216 GB/天（单副本）
3 副本：27.65 GB/天；一年 ≈ 10.09 TB
8 字节/样本：36.86 GB/天；3 副本 110.6 GB/天；一年 ≈ 40.37 TB
30 天扫描样本 = 4.608B × 30 = 138.24B
2 字节：276.5 GB 逻辑；8 字节：1.106 TB

先用资产清单确定分母，再按覆盖率决定报告能写到什么范围。

coverage = reporting_osds / expected_osds
若 coverage < 0.8：
  - 禁止输出“全局平均/全局 P99”，改为“已观测子集”
  - 在报告顶部标 missing_entities、missing_reason
  - 告警“采集覆盖率低”，优先级不低于业务告警
  - 任何根因结论置信度降级；不得用缺失字段做反证
若 5 分钟内 coverage 下降 > 10%：立即告警

样本量 1 分，三副本年存储 1 分，扫描量 1 分，覆盖率规则 2 分。覆盖率规则须写明“禁止全局均值”。

1.3 第 3 节：时态拓扑 SQL

先在固定快照中检查边的来源及两端实体的权限，得到 authorized_snapshot_edges。查询时用两组时间条件。 进阶篇 §7.2

SELECT src_id, dst_id, relation, valid_from, valid_to, observed_at, source
FROM authorized_snapshot_edges
WHERE src_id = :entity_id
  AND valid_from <= :t
  AND (valid_to IS NULL OR :t < valid_to)
  AND known_from <= :knowledge_cutoff
  AND (known_to IS NULL OR :knowledge_cutoff < known_to);

也可用 tstzrange 查询。

SELECT *
FROM authorized_snapshot_edges
WHERE src_id = :entity_id
  AND tstzrange(valid_from, valid_to, '[)') @> CAST(:t AS TIMESTAMPTZ)
  AND tstzrange(known_from, known_to, '[)') @> CAST(:knowledge_cutoff AS TIMESTAMPTZ);
  • 用事发时点匹配由 valid_from 起算的有效区间，用调查截止匹配知识区间。一条关系从 02:00 起有效、到 02:20 才被采集或写入时，02:16 的报告还查不到它。
  • 区间左闭右开。valid_to 缺失表示有效期无上界，两版关系在切换时不会重复或漏记。
  • 若 02:20 才得知关系在 02:10 已结束，保留旧记录的有效区间，关闭其知识区间并新增修订。查 02:15 的拓扑时，02:16 的快照仍有该边，02:20 之后的快照已知该边失效。

SQL 2 分，半开区间 1 分，两种时间含义 2 分。

1.4 第 4 节：异常、SLO 与误报

M01–M05 P99 = 5, 6, 5, 7, 6 → 中位数 6，MAD = 1。

M06: z = 0.6745 × (33 − 6) / 1 = 18.21
M07: z = 0.6745 × (46 − 6) / 1 = 26.98

分别计算各窗口的好请求比例。

M06: 285,000 / 299,700 = 95.095%
M07: 277,000 / 297,000 = 93.266%
M08: 224,940 / 225,000 = 99.973%

M01–M08 的覆盖率都是 3/3（期望 3、上报 3）。缺数据变体为 1/3。

按 50,000 条序列和 3.5σ 双侧阈值（p≈0.000465）计算误报。

单次采样期望误报 = 50,000 × 0.000465 ≈ 23.3
每天（15s，5,760 次）= 23.3 × 5,760 ≈ 134,000
连续 3 点（独立假设）= 50,000 × 5,760 × (0.000465)^3 ≈ 0.029/天

要把误报控制在 100 条/天以内，可组合以下条件，再用回放验证。

  1. 连续 3 点超限才触发，滤掉单点噪声。
  2. 限定变化幅度。绝对增量 ≥ 5ms 或相对 ≥ 2×。
  3. 先按池、主机或型号分组检测，再查到具体设备。
  4. 设最小样本量，低流量窗口暂停告警。
  5. 将已知无害的模式加到白名单，并设过期时间。
  6. 用回放集检验实际误报量。

在采样点独立的假设下，要求连续超限比单点阈值少报几个数量级。真实采样点有相关性，实际误报量以回放为准。

z 分数、SLO、误报量、规则组合各 2 分。

1.5 第 5 节：容量与硬盘告警预算

算例未另计固定占用。从冗余后容量扣除 5% 的预留，再按可分配容量的 95% 设告警阈值。

raw = 2,400 TB
EC 8+2 冗余后容量 = 2,400 × 0.8 = 1,920 TB
扣 5% 预留后，可分配容量 = 1,824 TB
95% 水位 = 1,732.8 TB
已用 1,500 TB；剩余 232.8 TB
6 TB/天 → 38.8 天
3 TB/天 → 77.6 天
9 TB/天 → 25.9 天

每天的告警量取决于盘数、故障率、召回率和精确率。

10,000 盘 × 2% = 200 次/年 ≈ 0.548 次/天
召回 80% → TP = 0.438/天
精确率 20% → 总告警 = 0.438 / 0.2 = 2.19/天
误报 = 1.75/天

每天只能处理 1 条告警且召回率为 80% 时，精确率至少要 43.8%。达不到时，可降低召回率或增加自动核实。

告警/天 = (N × AFR / 365 × recall) / precision

容量 3 分，硬盘 3 分，公式和决策 2 分。

1.8 第 8 节：变更契约与回放集

以下计划用 mClock 降低 backfill 的影响。回填并发上限按 OSD 生效。共用这些 OSD 的其他池也可能受影响，须一起评估。 Ceph OSD 配置

目标：缓解 ceph-a/hot 池的 backfill 争用
范围：参与 hot 回填的 OSD，核对共用这些 OSD 的其他池
前置：受影响 PG 的可用副本数和故障域数达到获批下限；无新设备故障，PG 退化未继续扩大；当前不在业务高峰；已备份配置；审批人 A/B
变更前：记录 mClock 配置、backfill 速率、P99、degraded PG
幂等键：CHG-<id>-<target>-<version>
执行：先做 dry-run 和预检查，按审批中的 OSD 列表分批调整，核对生效值及共享池负载
回滚：恢复原配置；触发条件 P99 不降或恢复停滞
观察窗：30 分钟
暂时缓解：P99 ≤20ms、错误率不升、degraded PG 下降、恢复速率 >0。继续等保护恢复
结案：业务持续达标，保护恢复并通过验收。受影响 PG 均为 active+clean，无新校验错误
失败：回滚并升级

选 10 个正常窗口、10 个真实事故、5 个缺数据案例、5 个晚到案例。每例记录快照 ID、知识截止、隐藏答案、必引和禁引证据、负对照与评分表。检测 2 分、根因 3 分、证据 3 分、时间 1 分、缺数据 1 分、业务与保护验收 2 分，可按 10 分制换算。

1.9 学习导览九节点练习答案

对应学习导览每个节点的“练习与验收”。

节点 01：订单写请求的 SLO

测量点：应用侧发起 write 之前/完成之后（客户端埋点），不是阵列侧
好请求：成功（无错误/超时）且端到端延迟 ≤20 ms
分母：纳入统计的所有逻辑写请求（含错误/超时）；重试单独标记，不静默去重
排除：健康检查、合成探针、批处理补数（如纳入要单列）

集群告警与应用 SLO 的测量点、阈值和传播延迟不同。PG active+degraded 表示副本不足时仍可服务。维护触发的 backfill 要过一段时间才会与前台争用，应用缓存、重试和队列也能暂时吸收影响。设备侧可能先告警，业务 SLO 随后才恶化。

节点 02：5 万序列的日样本量与治理

50,000 × 86,400 / 15 = 288,000,000 样本/天

指标标签保留实体 ID、集群、池、设备类型等受控字段。request_id、文件名和会话 ID 放到日志或明细。合并直方图时先按 le 汇总相同边界的桶，再算分位数。查 OSD 是否停报时，从资产表取期望数，从 up 或心跳取上报数，按 coverage 阈值告警。再查水位、最后样本时间和断连事件。覆盖不足时只报告已观测范围。

节点 03：维护前后两版 OSD 关系

T01（02:00–02:10:30）：orders → vol01 → hot → PG1 → osd.11/12/13
T02（02:10:30 起）：orders → vol01 → hot → PG1 → osd.12/17/18

比较维护前后时，分别用两个事发时点匹配有效区间，调查截止都用 02:16 匹配知识区间。按 available_at 过滤晚到事件，按 (source_id, event_id) 去重。E04 到 02:18 才可见。实验 CSV 用 observed_utc 表示可见时间。

节点 04：MAD 与首次触发

中位数 6，MAD 1
M06: z=18.21；M07: z=26.98
M07 好请求 93.27%

连续 2 点超限才触发。M06 是首个超限点，M07 首次触发。固定阈值可能漏报缓慢劣化或季节性波动内的异常，也可能在高负载时误报。滚动基线可能把事故起点纳入正常范围，也可能对突发硬故障反应慢。两种规则并行比较。

节点 05：容量三情景与硬盘方案

38.8 天（6 TB/天）、77.6 天（3）、25.9 天（9）

按设备日生成样本，分开标注真实故障、主动更换、迁移和观测结束。按时间和设备切分，用 PR 曲线和每千盘日误报预算选阈值。留出新型号验证模型能否迁移。缺失标签单独建模，避免填成 0。

节点 06：触发、传播、补查

E01 中 osd.11 维护下线。PG 重映射后，E02/T02/M06/M07 支持 backfill 与前台写入争用。补查客户端队列、OSD 级队列和恢复速率，确认资源卡在哪里。交换机端口丢包和错包计数正常会削弱网络假设。结合实际吞吐和路径核对备份是否与本案共享资源（T03）。

节点 08：调度调整的前置/退出/验证

调整前确认受影响 PG 的可用副本数和故障域数达到获批下限，且无新设备故障、PG 退化未继续扩大。避开业务高峰，备份配置并完成审批。若 P99 不降、恢复停滞、错误率上升或新故障域承压，退出调整。观察至少 30 分钟，覆盖一个业务峰值。业务先达标时记为“已缓解、未恢复”，继续查 degraded PG、重建速率和校验错误，等保护通过验收再结案。

节点 09：正常/缺数/晚到

完整数据下，检查正确根因是否进 Top-3、引用是否准确。缺数据时要降低结论强度并列出下一步，晚到记录按调查截止过滤。误判时依次查字段和覆盖率、根因候选、Top-3 排序，以及报告结论、引用和单位。

3. 进阶篇各章练习答案

3.1 第 1 章：介质与控制器

1. 旋转延迟与 IOPS

7200 rpm: 30,000 / 7200 = 4.17 ms
15,000 rpm: 30,000 / 15,000 = 2.00 ms
4 KiB 随机读（寻道 6ms、旋转 4.17ms、传输 0.02ms）：
IOPS = 1 / (6 + 4.17 + 0.02) ms = 1 / 10.19ms ≈ 98 IOPS

单队列且无缓存时，上限约 98 IOPS。企业盘利用缓存和请求队列可到 150–200 IOPS。

2. DWPD 与寿命

DWPD = 14,000 / (3.84 × 365 × 5) = 14,000 / 7,008 ≈ 2.0
每天 3 次全盘：14,000 / (3.84×3) = 1,215 天 ≈ 3.33 年

3. 写放大与 OP

WA = 3 TB / 1 TB = 3
OP 7% → 28%： spare 块更多，GC 更少、WA 通常下降，稳态性能/寿命更好；
但可用容量下降，成本上升。

4. 缓存平均延迟

90%: 0.9×0.1 + 0.1×4 = 0.49 ms
70%: 0.7×0.1 + 0.3×4 = 1.27 ms

命中率降 20 个百分点，平均延迟涨到约 2.6 倍。尾延迟对命中率变化更敏感。

3.2 第 2 章：数据保护

1. 容量与重建

raw = 12×20 = 240 TB
RAID 6 = 10×20 = 200 TB（83.3%）
EC 8+2 = 240×8/10 = 192 TB（80%）
3 副本 = 240/3 = 80 TB（33.3%）
重建：15 TB / 150 MB/s = 100,000 s ≈ 27.8 h

按 150 MB/s 重建整盘，20 TB 约需 37.0 小时，20 TiB 约需 40.7 小时。排期用实际需重建的数据量。

2. 快照空间与一致性

10 TB × 25% × 5 = 12.5 TB（上限，未计共享折扣）

先让数据库或文件系统暂停写入（quiesce），刷写缓存，再用 VSS、agent 或脚本触发快照。多个卷用一致性组。确认快照完成后恢复写入。从快照恢复时，查日志并验证应用一致性。

3. 同步复制

带宽 = 10,000 × 8 KiB × 40% = 32.768 MB/s（31.25 MiB/s，单向，未计开销）
RTT 3 ms → 写延迟至少 +3 ms（加远端处理）
SLO 1 ms：不可行；改异步/同城更短 RTT/放宽 SLO。

4. 为什么快照+同阵列复制不是防勒索备份

  • 攻击者或误操作可用同一管理员权限或凭据删除快照和副本。
  • 快照和副本共用阵列、固件和漏洞，勒索软件可能同时加密两份数据。
  • 缺少离线、不可变或隔离副本时，删除可能无法恢复。
  • 备份成功率反映任务完成情况。数据能恢复多少，要靠恢复演练验证。

可用对象锁或 WORM、离线副本、AirGap、独立凭据和 MFA、不可变保留保护备份，并定期演练恢复。

3.3 第 3 章：协议与网络

1. Zoning vs LUN Masking

Zoning 决定交换机上哪些端口能互相发现，LUN Masking 决定阵列向每个主机 WWN 暴露哪些 LUN。主机能登录 target 却看不到 LUN 时，查 Masking。阵列已授权而主机仍无法连到 target 时，查 fabric 路径和 Zoning。两项都要配置。

2. PFC 暂停帧扩散

PFC 按优先级暂停上游发送。配置或优先级映射不当时，暂停帧可能扩散到整个端口，引起队头阻塞，其他流量也会停顿、延迟变高或丢包。查交换机 PFC/ECN 计数、队列水位和丢弃计数，再查主机 RDMA 重传、CNP，并核对 DSCP→TC 映射和 PFC 配置。

3. S3 multipart

十进制最小固定 part = 1 TB / 10,000 = 100 MB（约 95.37 MiB）
128 MB part：向上取整(1,000,000 MB / 128 MB) = 7,813 个 part
若题目改为 1 TiB 与 128 MiB，则为 8,192 个 part

4. NFS 大目录

1,000,000 / 8,000 = 125 s
数据量 = 1,000,000 × 4 KiB ≈ 3.815 GiB

数据量约 4 GiB，125 秒主要花在元数据操作上。先查元数据操作延迟（metadata op latency）、MDS CPU、目录锁和分片，再查元数据池。

1. PG 数

pg_num ≈ 100 × 100 / 3 = 3,333 → 取 2 的幂 4,096
每 OSD 平均 PG = 4,096 × 3 / 100 = 122.9
若取 2,048：61.4/OSD；两者都可，按容量/负载/autoscaler 调。

2. 故障域

3 个副本同机柜时，机柜断电或交换机故障可能令它们同时不可用。EC 8+2 放在 5 台主机、每台 2 块时，坏 2 台会丢 4 块，超过 m=2，无法重建。放在 10 台主机、每台 1 块时，坏 2 台只丢 2 块，仍可重建。评估故障域时，数清这些故障域同时失效会丢几块，合计须 ≤ m。

3.6 第 6 章：算法

1. 日周期 + 周末低峰

按星期几和时段用 STL 或 Holt-Winters 建基线，对残差算稳健 z 分数。也可取相同负载和时段的历史分位数。固定阈值受峰谷差影响，全局 MAD 容易把正常波动报成异常，也可能漏报。再限定最小样本量、连续窗口数和最小变化幅度。

2. 硬盘标签

真实故障：H 天内故障 → 正例
主动更换：单独标签/竞争风险，不能当正例或负例
迁移/退役：删失或排除，记录原因
观测结束：删失（不能当负例）
随机切分：同盘/同时间段泄漏；按时间 + 按设备分组切分

3. DAG 与控制变量

先画 维护 → backfill → 队列 → 延迟、业务峰值 → IOPS 和 业务峰值 → 延迟。backfill 也可能影响 IOPS。若业务峰值通过 IOPS 影响延迟，控制 IOPS 会挡住这部分效应。若 backfill 和业务峰值都影响 IOPS，按 IOPS 分组或控制 IOPS 会引入对撞偏差。结合 backfill 速率、队列和事故时间窗，按因果图决定控制哪些变量。

4. PG 扩缩

100 OSD：100×100/3 = 3,333 → 4,096
200 OSD：200×100/3 = 6,667 → 8,192

每个 OSD 的 PG 数足够、autoscaler 正常时可以维持现状。PG 过多会增加 peering、内存和恢复开销。结合 pg_autoscaler 的结果和实际负载决定是否调整。

B. 设计题

B11. 稳定身份

  • entity_id = tenant/cluster/type/uuid。可变名称放别名表。
  • 在别名表保存 hostname、WWN、serial、IP、K8s UID 和有效期。
  • 把 OSD 数字编号当别名，并记录 UUID 和生命周期区间。重建后登记为新实体。
  • 主机改名时新增别名，换 HBA 时登记新实体，保留旧关系的有效期。
  • K8s Pod 重建时，以 workload/controller 为稳定实体，单个 Pod 用 UID 和生命周期标识。

B12. 时态拓扑

  • valid_from/valid_to 记录关系实际何时有效，用它还原维护前或维护后的拓扑。
  • observed_at 记采集端首次看见的时间，available_at 记事件和证据首次可查的时间。拓扑修订的可查区间用 known_from/known_to。回放在冻结快照中只取调查截止时已可查的记录。
  • 使用半开区间 [valid_from, valid_to)。valid_to NULL 表示仍有效。
  • 查询 valid_range @> t AND knowledge_range @> cutoff。晚到修订保留旧有效区间，仅关闭旧知识区间并新增修订。
  • 用 source/confidence 标注来源和置信度，以便处理多源冲突。

B13. query_metric 契约

用 entity_id, metric enum, start, end, step, aggregation 查指标。成功时返回 unit, samples, missing_intervals, coverage, query_id, source_id。网关为只读查询绑定身份、租户、授权、快照和知识截止，并限制时间窗、样本量和超时。模型传入的窗口只能缩小范围。错误分 unauthorized/not_found/no_data/timeout/backend_error。

→ 关键词+向量混合召回 → 重排 → 冲突检测 → 返回 doc_id/section/version/effective_at/引用

文档冲突时返回多个候选，并写出差异和适用范围。故障码用精确匹配，工单用语义检索。

B16. 硬盘标签

H 天内发生故障才标为真实故障。主动更换单列为竞争风险或干预，迁移和退役记为删失或排除，观测结束记为删失。按时间和设备切分，避免同一盘的同次故障同时进入训练集和测试集。检查校准与 PR-AUC，按告警预算选阈值。

B17. 缺数据变体

隐藏元数据 IOPS、控制器 CPU 和 backfill 日志，保留业务 P99、磁盘与网络正常的信号，以及正常对照。报告应确认业务影响，注明已查到的介质和网络信号未见异常。控制器或元数据仍待查，补看 metadata op latency、控制器队列和备份扫描。降低结论强度、写明缺口、只用实际取得的数据作反证，均可得分。

B18. 多集群分层

  • 边缘采集原始数据、缓冲、脱敏和粗聚合，断链后续传。
  • 区域保存跨站资产目录、拓扑快照和证据索引，负责路由查询。
  • 全局管理策略、模型、评测和审计，明细留在站点或区域。
  • 把查询下推到数据所在层，按需回查明细。在采集层落实数据驻留和租户隔离。

B19. 告警聚合

先查告警是否落在同一故障域或有共享依赖，再对照时间窗、传播延迟和上下游关系。合并后保留原始告警 ID、规则版本和合并原因。根因各自独立时分别处理，按 SLO 影响定级。

B20. DME MCP 适配

提供 10 个只读工具，分别为 sites、assets、topology_at、query_metric、query_alarms、health、collection_status、changes、smart_analysis 和 search_runbooks。smart_analysis 只查已有报告，设查询预算并标明只读。用 OAuth2/RBAC 限定租户和实体范围，按类别返回错误，每次附 query_id。写工具默认不暴露。

C. 案例题

C21. Ceph 维护后 P99 升高

IOPS 不变、backfill 上升、重传持平，H1 backfill 争用排首位。获批限速后观察 P99 和队列。H2 网络或交换机问题需补查端口丢包和重传。H3 业务负载增加的证据较弱，再查业务 IOPS 和队列。

C22. NFS P99 高、磁盘 15%、控制器 CPU 90%、元数据 IOPS 5×

优先查元数据热点和控制器 CPU 饱和。分别看小文件 create、stat、readdir 的 metadata op latency，排查目录扫描或锁。再查控制器内部队列、MDS 或文件系统 CPU、备份扫描并发和客户端重试。

C23. 对象 PUT 慢、GET 正常、网关 CPU 高

GET 正常说明已观测的读路径未见异常。先查网关 CPU、队列、限流，以及桶索引、热前缀和分片。再查 multipart 的分片大小、并发和未完成分片，以及后端纠删码池的写入。最后核对客户端重试和签名。

C24. 缓存电池失效切写穿

切到写穿是掉电保护，代价是写延迟升高。查电池和缓存状态、写策略、控制器日志、延迟、IOPS 和数据一致性。电池恢复后确认策略恢复为写回，再观察延迟。保持自动保护，避免强制开启写回。

C25. SSD 随机写 P99 周期尖峰

可能原因有垃圾回收（GC）、写放大（WA）、读干扰、热节流、预留空间（OP）不足和 FTL 映射波动。查 GC 次数和耗时、WA、OP、温度、P99/P999、介质错误和队列。对照稳态与尖峰，也比较不同 OP 和温度条件。

C26. 双活 RTT 0.5→4ms

RTT 到 4 ms 时，同步写单等远端确认就至少要 4 ms，无法满足 1 ms SLO。可改用异步复制（RPO>0）、缩短同城 RTT 或放宽 SLO。产品支持时，也可在双活站点本地提交后再异步同步。

C27. 备份扫描导致元数据延迟

给备份限速并错峰，限制并发，把备份流量和业务分开。可用快照、索引或增量备份避开全目录递归。在下一个备份窗口核对 metadata op p99、控制器 CPU 和业务 SLO。

C28. 硬盘告警翻倍但故障率不变

先查模型或阈值版本、盘型与固件分布、重复告警与聚合规则、标签与反馈以及采集频率是否有变化。分版本、盘型和站点比较 PR、校准和提前量，再对照历史同期并查告警去重。

C29. Agent 说根因是交换机但只引用应用日志+一条拓扑边

应用日志和一条拓扑边只够把交换机列为待查。先核对引用指向哪台交换机、拓扑边在事发时是否有效，再按调查截止查端口丢包、错包和拥塞。确认数据覆盖率，和正常路径对照后再下结论。

C30. 验证“故障处理周期缩短 90%”

先问“周期”指 MTTD、MTTA、MTTR，还是从告警到关闭的时间。按事故类型和严重级别确定分母。用同一事故集与人工或旧系统对照，按时间切分并盲评，控制人员、流程和设备变化。记录统计显著性、成本、误报和负对照。向厂商索要测试条件、样本量和失败案例。材料不足时，把 90% 标为厂商宣传值。
