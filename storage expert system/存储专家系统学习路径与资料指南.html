为什么很多“存储 AIOps”最后变成大屏和聊天机器人？因为它们只做了“看见”和“说话”，没有把状态、知识、推理、行动、评测连成一个可验证的闭环。

0.1 专家系统的五个面

一个能用的存储专家系统，至少有五个面。少任何一面，系统都会退化成“会说话的看板”。

面回答的问题典型组件失败表现
状态面现在和当时发生了什么？指标、日志、事件、变更、拓扑快照数据缺失被当成“变好了”
知识面这类现象通常意味着什么？本体、故障模式、Runbook、版本约束检索到过期或不适用的手册
推理面哪条因果链最可信？还缺什么？规则、统计、因果图、故障树、LLM 规划把相关当因果，或只给一个答案
行动面能不能动、谁批、怎么回滚？工单、审批、编排、幂等接口业务恢复了，冗余却没恢复
评测面它到底比人强在哪？回放集、盲评、负对照、成本账只展示成功案例

确定性内核

规则、阈值、SLO、权限、动作契约、验证器。它们必须可审计、可回归，不能由模型“自由发挥”。

概率性外壳

异常检测、预测、LLM 假设生成、RAG 检索、报告组织。它们负责“提问和解释”，不负责“知道设备当前状态”。

级别能力必要证据授权

01 请求路径与 SLO：先知道你在测什么

“存储慢”不是一个可诊断的问题。慢在哪一段、对谁慢、分母是什么、尾部的形状是什么——这四个问题不回答，后面的告警和根因都会错。

1.1 四条路径，不是一条线

块、文件、对象、分布式存储的请求路径不同，瓶颈位置也不同。把它们画在同一张图上，先建立“路径感”。

1.2 一条 I/O 的延迟由什么组成

把端到端延迟拆成可测量的段：

T = T_client_queue + T_fabric + T_frontend + T_cache
  + T_backend_queue + T_media + T_retry + T_software

每一段都要有独立测量点。缺少某一段时，结论只能写成“在已观测段内，瓶颈位于 X 之前/之后”，不能写成“根因是 X”。

段典型证据常见误判
客户端队列应用埋点、HBA/MPIO 队列、iostat await只看阵列延迟，漏掉客户端排队/重试
网络端口利用率、CRC/丢包、重传、PFC/ECN重传正常就断定网络无关（交换机端口丢包未必可见）
前端/控制器端口 IOPS、控制器 CPU、缓存命中/脏页CPU 高就是“负载大”，忽略压缩/快照/EC 开销
后端/介质池/OSD 队列、介质利用率、GC/重建磁盘利用率低就排除后端（队列/后台任务可能仍高）

1.3 队列论：为什么利用率只涨一点，延迟翻倍

对 M/M/1 队列，服务时间 S、利用率 ρ：

排队时间 W = ρS / (1 − ρ)
响应时间 R = S / (1 − ρ)
ρ50%70%80%90%95%
R / S2×3.3×5×10×20×

真实系统不是 M/M/1，SSD 有内部并行、控制器有多队列，不能用它算绝对值；但它解释了“利用率从 70% 到 85%，延迟翻几倍”的非线性，也解释了为什么 85% 以上做容量规划很危险。

1.4 尾延迟放大：平均值会骗人

一个请求扇出到 k 个下游。如果各下游延迟相互独立，且每个下游超过所选延迟阈值的概率均为 p：

P(至少一个慢) = 1 − (1 − p)^k
算例

每个下游 P99 超标概率 1%：k=10 → 9.6%；k=100 → 63.4%；k=1000 → 99.996%。如果每个下游是 P99.9，k=1000 仍有 63.2% 的请求会碰到至少一个慢调用。存储的多副本、EC 条带、多路径、元数据/数据分离都在制造这种扇出。

1.5 SLO 的数学：好请求、错误预算、燃烧率

SLO 的三要素是测量点、好事件、分母。例子：

好请求 = 成功 且 端到端延迟 ≤20ms 的写请求
SLO = 好请求数 / 纳入统计的写请求数 ≥99.9% / 30 天
错误预算 = (1 − SLO) × 总请求数
请求量近似均匀时，99.9%/30 天 ≈ 43 分 12 秒的完全不可用等价时间
燃烧率 = 观测窗口错误率 / (1 − SLO)

燃烧率为 1 且持续整个 SLO 周期时，刚好耗尽该周期预算。请求量近似均匀时，14.4 倍燃烧率持续 1 小时会用掉 30 天预算的 2%。流量不均时，用观测窗内坏请求数除以全周期预算请求数。多窗口规则可要求 1 小时和 5 分钟燃烧率都超过 14.4。

1.6 分位数不能平均：一个必须会算的例子

三个客户端共 100 万请求。合并累计桶后，≤10 ms 有 890,000，≤20 ms 有 984,000，≤50 ms 有 996,900，≤100 ms 有 1,000,000。P99 的秩是 990,000，落在 (20,50] ms 桶。

P99 ≈ 20 + (990,000 − 984,000) / (996,900 − 984,000) × 30
    = 20 + 6,000/12,900 × 30 ≈ 33.95 ms

自测：IOPS 基本不变，但 P99 从 6ms 升到 46ms，最可能是什么？为什么先扩容可能无效？

最可能是同样负载下服务时间变长：后端争用（如维护触发 backfill）、SSD GC、缓存降级、锁/元数据热点、网络重传。IOPS 不变说明不是流量洪峰；扩容增加的是并行能力/容量，不一定缩短已有请求的排队时间，甚至会因为重建/再平衡加剧争用。应先查队列、backfill/GC、缓存、错误与重传，再决定是否扩容。

02 遥测、时间与海量成本：数据多不等于证据多

海量存储的“海量”先体现在遥测上：实体多、标签多、采样密。没有基数控制和覆盖率，系统会把“采集失败”误判成“系统变好”。

2.1 从设备到证据的流水线

遥测不是“把指标存起来”。它是一条有缓冲、有丢包、有水位、有对齐的流水线。

2.2 基数与成本：先算清楚再存

一条时间序列由指标名和标签集唯一确定。标签是维度，不是身份流水号；把 request_id、文件名、快照 ID 放进标签，会制造无限基数。

序列数 ≈ 实体数 × 每实体指标数 × 维度组合数
10,000 OSD × 80 指标 = 800,000 序列
每天样本 = 800,000 × 86,400/15 = 4.608B
2 字节/样本 ≈ 9.2 GB/天（单副本）
3 副本 ≈ 27.7 GB/天；一年 ≈ 10.1 TB

这只是一个集群的原始指标。再乘设备数、租户、日志、追踪、拓扑快照和查询副本，成本会迅速上升。分层是必须的：

层粒度保留用途
原始15s–1min7–30 天事故取证、短窗口
聚合5–30min6–12 个月趋势、容量、周同比
日级1 天2–5 年容量规划、审计
事件/变更事件粒度多年根因、合规
日志/证据原始7–30 天，冷存更久深度取证

2.3 三个时间：事件时间、观测时间、知识时间

这是存储取证最容易错的地方。至少有三个时间：

时间含义防什么错
event_time事情实际发生的时间（设备时钟/日志时间）防止把传播延迟当成因果
observed_time采集/上报系统看到它的时间防止用事故后才到达的数据
knowledge_time进入证据库、可被查询的时间防止回放时“未卜先知”

回放 02:16 的事故时，只能使用 knowledge_time ≤ 02:16 的数据。否则模型会用 02:18 才上报的日志解释 02:16 的告警。拓扑同理：按事件时间选当时有效的版本，而不是当前拓扑。

因为延迟上升至少会触发告警；延迟下降会让看板看起来更健康。停报的 OSD 可能正是负载最高/最不健康的那些，剩余样本是选择性偏差。必须用 expected/reporting 计算覆盖率，并把缺失实体列入证据；否则会把“采集失败”误判为“性能改善”。

03 身份与时态拓扑：别用今天的图解释昨天

存储实体一直在变：主机改名、HBA 换卡、OSD 编号重用、Pod 重建、卷迁移。如果实体身份或拓扑版本错了，根因会精确地指向错误的设备。

3.1 身份比名称重要

实体的“名字”极不稳定：主机名会改，LUN ID 会重用，OSD 数字编号会在重建后复用，WWN 可能因为换卡改变，容器 Pod 名每次部署都不同。专家系统必须建立稳定身份 + 别名 + 生命周期：

entity_id = tenant / cluster_fsid / entity_type / native_uuid
alias     = 显示名、旧主机名、序列号、WWN、IP、K8s UID
lifecycle = 上线、维护、下线、退役

如果只能拿到数字编号（例如 osd.11），必须同时保存 UUID 和“该编号在这一代生命周期内有效”的区间。否则历史事故会被错误地归到新设备上。

3.2 双时态：有效时间与知识时间

拓扑边的每次修订都保留以下信息。

edge: (src, dst, relation)
valid_from, valid_to      # 这条关系在现实中何时有效
observed_at               # 观测系统何时看到它
known_from, known_to      # 该修订何时对调查者可见
source, confidence        # 谁说的、有多确定

查询“02:16 时刻的拓扑”要用半开区间：

SELECT * FROM edge
WHERE src_id = :workload
  AND valid_from <= :t AND (valid_to IS NULL OR :t < valid_to)
  AND known_from <= :knowledge_cutoff
  AND (known_to IS NULL OR :knowledge_cutoff < known_to);

有效区间匹配事发时点，知识区间匹配调查截止。例如 02:20 才发现某条边已于 02:10 结束，应保留旧修订的有效区间，关闭旧知识区间并新增修订。这样仍能复现 02:16 的调查。

3.3 图模型：节点和边的语义要明确

Workload → Volume/LUN/FileSystem/Bucket
Volume   → Pool → PG → OSD → Disk
Host     → HBA/Port → Switch Port → Array Port → Controller
Array    → Site/Rack/Power/FailureDomain

边的语义要明确方向：runs_on、maps_to、replicates_to、depends_on、hosted_by、protects。不要把“网络可达”和“数据依赖”混成一种边；前者影响连通性，后者影响数据完整性。

3.4 事发拓扑重建：一个完整的例子

02:10:30 计划下线并显式标记 osd.11 为 out，PG 的新放置目标包含 osd.17/18。02:14 结束的窗口观测到订单写 P99 升高。02:16 的调查可以用下面两版映射解释放置变化，实际 I/O 路径还需核对 acting 与 OSD 遥测。

时间拓扑版本用途
02:00–02:10:30orders → vol01 → hot → PG1 → osd.11/12/13解释维护前路径

自测：02:16 的报告应该用 T01 还是 T02？为什么不能只用一个？

解释“当前谁在承载、backfill 目标是谁”用 T02；解释“维护前路径、为什么 osd.11 不再是承载者”用 T01。只用 T02 会丢失维护前后的对比，可能把 osd.11 误判为当前故障源；只用 T01 会把 backfill 目标指错。两版都要保留，并按 valid_from/valid_to 与 observed_at 选择。

04 异常检测与告警工程：把噪声变成可处理的信号

5 万条序列、3.5σ 阈值、15 秒采样——如果单点报警，每天会有十几万条误报。检测的目标不是“发现更多”，而是“用可接受的误报量换可接受的首响时间”。

4.1 先选信号，再选算法

信号适合的检测不适合
低基数、平稳指标阈值、滚动基线、CUSUM深度模型（样本不够）
强季节、日/周周期STL 分解、季节基线固定阈值
多指标组合异常隔离森林、矩阵画像、AutoEncoder单指标阈值
计数器/速率先做重置处理，再检测直接对原始计数器建模
事件/日志模板、频次、序列模式只看单条日志
高基数实体分组基线 + 分层模型全局一个阈值

规则不是“低级”，而是可解释、可审计、可回归的基线。任何 ML 检测都应该先和规则并跑，证明它在同一事故集上更好，否则只会增加运维负担。

4.2 稳健基线：中位数与 MAD

median = 中位数(x)
MAD    = 中位数(|xi − median|)
z      = 0.6745 × (x − median) / max(MAD, ε)

用实验室数据验算：M01–M05 的 P99 为 5, 6, 5, 7, 6，中位数 6，绝对偏差 1, 0, 1, 1, 0，MAD = 1。M06 = 33ms：z = 0.6745 × 27 / 1 = 18.21；M07 = 46ms：z = 26.98。

但 z 大不等于影响大。如果基线是 0.1ms、MAD 0.01ms，涨到 0.2ms 也会有巨大 z，但业务可能无感。要加效应量（绝对增量 ≥5ms 或相对倍数 ≥2）和持续窗口（连续 2 个采样点）。实验室里 M06 超限、M07 再次超限，才构成持续异常。

4.3 多重检验：5 万条序列的假阳性

如果 50,000 条序列相互独立、服从正态，使用双侧 3.5σ 阈值，单条序列单次误报概率约 0.000465：

50,000 × 0.000465 ≈ 23.3 条/次
15 秒采样 → 每天约 134,000 条误报

在同样的边际误报概率下，相关性会改变单点超限的聚集程度。实际通知量还取决于连续窗口、效应量门槛、分组检测与聚合规则，可用正常窗口回放估计。

4.4 告警聚合与 SLO 分级

聚合的目标不是“少报”，而是“一页纸说清一个事故”。按三个维度合并：拓扑（同故障域/共享依赖）、时间（窗口重叠/传播延迟）、因果（父告警/子告警）。但聚合有风险：把两个独立根因合成一个，会掩盖第二个故障。因此要保留原始告警 ID、聚合规则版本和“为什么合并”的理由。

告警级别应该由业务影响决定，而不是设备型号。最简单的做法是看 SLO 燃烧率：

P1：1h burn ≥14.4 且 5m burn ≥14.4
P2：6h burn ≥6
P3：3d burn ≥1

再叠加冗余状态：业务 SLO 还在但冗余 degraded，是“高优先级修复、非事故”；业务 SLO 破了且冗余不足，才是“事故”。

忽略低流量1 个请求触发 P1最小样本量

05 容量与硬盘风险预测：把“提前”变成可验收的数字

“提前 14 天/30 天/1 年”不是模型能力，而是口径、标签、误报和运维预算的组合。不看这些，预测数字只是营销。

5.1 容量账本：raw、usable、effective

raw       = 裸容量
usable    = 副本：raw / 副本数
          = EC k+m：raw × k / (k + m)
effective = usable − 快照 − 克隆 − 元数据 − 回收站 − 安全水位

例子：10 个节点 × 12 块 20 TB = 2,400 TB raw。EC 8+2 的效率是 80%，可用 1,920 TB；再留 5% 安全水位，有效 1,824 TB。若已用 1,500 TB、净增 6 TB/天：

到 95% 水位 = (1,824 × 0.95 − 1,500) / 6 ≈ 38.8 天
3 TB/天 → 77.6 天；9 TB/天 → 25.9 天

报区间，不报单点；把“扩容/清理/生命周期变更”作为切换点，切换后重新拟合。

5.2 容量模型与回测

容量预测的难点不是模型，而是口径和切换点。常用方法：稳健线性回归、分位数回归、ARIMA/SARIMA、季节分解、结构模型/集成。回测要用滚动原点：在历史每个时点只用当时可见的数据训练，预测未来 H 天，再向前滚动。指标包括 MAE/MAPE、pinball loss、区间覆盖率、跨阈值时间误差。随机切分会让未来信息泄漏到训练集，指标虚高。

5.3 硬盘故障预测：标签比模型重要

硬盘预测的第一个问题是标签，不是算法：

样本 = (disk_id, day t, 当时可见的特征)
正例 = 该盘在 (t, t+H] 内发生“真实故障”
负例 = 该盘在 (t, t+H] 内没有故障，且观测未截尾
排除 = 主动退役、迁移、数据销毁、观测结束

如果“主动换盘”被当成故障，模型会学到运维策略；如果观测结束的盘被当成负例，会低估风险；如果同一块盘的相邻日期同时进入训练和测试，会泄漏。正确切分是按设备 + 按时间：训练集和测试集不能共享同一块盘的同一次故障。

特征用当时可见的 SMART/NVMe 指标及其变化率：重分配扇区、待定扇区、不可纠正错误、命令超时、CRC 错误、磨损、通电小时、温度、型号、固件、批次。树模型通常比 Logistic 回归强，但可解释性和校准要单独做。

5.4 告警预算：先定运维能处理多少

10,000 块盘，年故障率 2% → 每年 200 次故障，约 0.55 次/天。若召回 80%、精确率 20%：

TP/天 = 0.55 × 0.8 = 0.44
总告警/天 = 0.44 / 0.2 = 2.2
误报/天 = 1.76

如果精确率只有 5%，总告警 8.8 条/天，运维就会开始忽略。先定运维能处理的告警量，再反推阈值，比追求高召回更现实。评测要看 PR-AUC、召回@告警预算、每千盘日误报、提前量分布、概率校准（Brier/校准曲线）。

失败模式后果纠正
容量口径混用提前/延后扩容raw/usable/effective 分开
随机切分指标虚高按时间/设备切分
主动换盘当故障学到运维策略单独标签/竞争风险
只看 AUC高误报PR-AUC + 告警预算
预测无区间决策过度自信分位预测 + 回测
不监控漂移慢慢失效漂移 + 校准监控

06 根因、证据与反证：从“最可能”到“可证伪”

根因报告最危险的一句话是“最可能是 X”。如果没有说明“什么证据会推翻 X”，它就不是诊断，而是猜测。

6.1 相关、干预与反事实

证据强度含义存储例子
相关A 和 B 同时异常backfill 高时延迟高；但可能都是共同原因
干预改变 A 后 B 按预期变化限速 backfill 后 P99 下降
反事实如果没做 A，B 会怎样需要模型/对照，不能直接观测

存储运维没有随机对照试验，但有自然实验：维护窗口、限速/调度调整、分批升级、同集群不同池/租户的对照、变更前后的中断时间序列。因果图（DAG）要先画清楚共同原因、对撞和中介，再决定控制哪些变量。

6.2 候选从哪里来

候选 = 时间上先于症状的变更
     ∪ 事发拓扑上可达的实体
     ∪ 同故障域内共现异常的实体
     ∪ 已知故障树/历史工单匹配的模式
     ∪ 影响范围与对照不吻合的共享依赖

要给传播留出合理的时间窗口。维护于 02:10:30 生效，02:11 开始 backfill，02:14 结束的窗口观测到尾延迟上升。02:18 收到晚到日志后，复盘才可补上 02:12:30 的积压时间。

6.3 证据评分：六个维度

维度问题例子
时间领先候选是否先于症状？02:16 可看到 02:14 窗口异常；02:18 后可补上积压日志

剂量响应强度/范围是否与症状吻合？backfill 615 MiB/s 时 P99 46ms
特异性能否解释“为什么是这些而不是那些”？只有 hot 池受影响，cold 正常
对照未受影响对照是否符合预期？audit 走另一组 OSD，SLO 正常
干预响应改变后是否按预期恢复？调度调整后 P99 下降、恢复继续

评分可以是加权和，也可以是贝叶斯似然；但不要把加权和直接叫“概率”，除非做过校准。权重应该从回放集里学，而不是拍脑袋。

07 Agent、RAG 与工具契约：让模型“查得到”，而不是“猜得对”

会聊天不等于会调查。调查需要边界、工具、证据、验证和停止条件；没有这些，模型越流畅，越危险。

7.1 有界状态机，而不是自由聊天

初始化（症状、窗口、资产、权限）
  → 查采集健康/覆盖率
  → 查业务影响（SLO、错误、范围）
  → 查拓扑（事发时刻）
  → 查变更/事件
  → 生成候选假设
  → 对每个假设选择最有区分度的查询
  → 证据足够/预算耗尽/需要人工 → 输出

每一步都要有预算：最大工具调用数、最大时间窗、最大返回行数、最大 token、最大并行度。没有预算的 Agent 会在大规模环境里把查询打爆。

7.2 工具契约：比 prompt 重要

一个好工具不是“能查指标”，而是“查询语义明确、结果可引用、失败可解释”。最少包含：

{
  "name": "query_metric",
  "description": "按实体、指标、时间窗查询聚合指标；返回样本、单位、缺失区间和查询 ID",
  "input": { "entity_id": "...", "metric": "enum", "start": "...", "end": "...", "step": "..." },
  "output": { "unit": "ms", "samples": [], "missing_intervals": [], "coverage": 0.98, "query_id": "..." },
  "constraints": { "max_range": "7d", "max_samples": 10000, "read_only": true }
}

关键点：时间参数用绝对时间 + 时区；返回必须带单位、缺失区间、覆盖率和查询 ID；枚举值要稳定；错误要分类型（无权限/无数据/超时/参数错/后端错）；写工具单独授权，默认不暴露。

7.3 MCP：把工具变成可组合的协议

MCP 用 JSON-RPC 连接模型客户端和工具服务端，通常暴露 tools、resources、prompts。它的价值不是“又一个 API”，而是工具的描述、调用和权限可以标准化，不同 Agent 可以复用同一套存储工具。

系统公开状态范围
Pure1 Manage MCP已正式可用只读管理面查询
Fusion MCP开源，文档公开阵列/卷/文件系统/工作负载/拓扑；部分性能查询依赖直连令牌
NetApp DII MCPPreview（2026-09 文档）租户内只读：性能/容量/日志/告警/采集健康
华为 DME公开材料未见 MCP 服务北向 RESTful/SNMP/Ansible/CSI；故障智能体可通过北向 API 接入跨域智能体

7.4 RAG：检索的是“适用知识”，不是“相似文本”

RAG 的失败大多不是向量模型，而是过滤条件。一个存储 Runbook 的检索至少要过滤：

租户/ACL → 产品 → 型号 → 版本区间 → 故障码/症状
→ 审批状态 → 生效时间 → 关键词+向量混合召回 → 重排

分块要保留章节标题、表格、图注和原文链接；故障码用精确匹配，工单/复盘用语义召回。冲突的文档要返回多个候选和冲突点，不要强行合并。GraphRAG 适合“实体关系 + 多跳”的问题，但不适合替代精确的配置查询。

7.5 证据对象与防幻觉

把证据作为结构化对象传给模型，而不是一段散文：

evidence_id, query_id, source, entity_id, window,
observed_at, quality, payload_ref, summary

报告必须：每个事实引用 evidence_id；区分“观测到的事实”和“推断”；明确知识截止时间；数据不足时输出“未决 + 下一步查询”；数值做单位/量纲校验（ms vs s、MiB vs MB、IOPS vs 带宽）。验证层要做引用存在性、引用与结论一致性、时间边界、数值范围、权限范围、输出 schema。模型自评不能替代外部校验。

7.6 安全：日志和文档也是不可信输入

1. 为什么 IOPS 不变、P99 升高时，先扩容可能无效？

因为瓶颈可能是服务时间/排队，而不是并发能力：backfill、GC、缓存降级、锁/元数据热点、网络重传都会让同样负载变慢。扩容不缩短已有请求的排队，甚至可能因重建/再平衡加剧争用。先查队列、后台任务、缓存、错误与重传。

2. 三个客户端 P99 分别是 10/20/30ms，全局 P99 是多少？

不能从这三个数算出来。全局 P99 取决于各客户端的请求量分布和尾部形状；必须合并相同桶边界的直方图后插值。直接平均会失真。

3. 一半 OSD 停报，平均延迟下降，为什么危险？

停报的可能是高负载/不健康 OSD，剩余样本是选择性偏差；平均值下降会掩盖采集失败。必须用 expected/reporting 计算覆盖率，并把缺失实体列入证据；覆盖率低时不得输出全局均值。

4. 为什么调查要保留历史拓扑？

维护和迁移会改变 PG 到 OSD 的映射。按 valid_from/valid_to 选事发时点有效的关系，再按 known_from/known_to 选调查时点可见的修订。晚到纠正需要保留旧修订，才能复现原来的调查。

5. 5 万条序列、3.5σ 单点阈值，为什么每天会有十几万误报？

双侧 3.5σ 单次误报概率约 0.000465；50,000 × 0.000465 ≈ 23.3 条/次；15 秒采样每天 5,760 次 → 约 13.4 万。必须加连续窗口、效应量、分组检测、最小样本和告警预算。

6. 为什么硬盘预测不能随机切分？

同一块盘的多天样本高度相关，随机切分会让同一次故障前后样本同时进入训练/测试，模型记住“指纹”而非可迁移特征。按时间 + 按设备切分，并隔离同盘同次故障；留出新型号/新固件做迁移测试。

7. 什么证据会推翻“backfill 争用”假设？

限速/暂停 backfill 后 P99 不降、受影响 OSD 队列不降；业务不经过这些 OSD；对照业务同等恶化；或发现更早的可解释触发（端口丢包/控制器饱和）且 backfill 只是伴随。反证要写进报告。

8. 为什么 Agent 必须先查采集健康，再查业务指标？

数据不齐时，指标可能只代表已观测子集，缺失还可能非随机（故障设备更容易停报）。先查 coverage/watermark/missing，再决定能不能下全局结论；覆盖率低时输出“未决 + 下一步”，而不是高置信根因。

9. P99 恢复到 SLO 内，为什么还不能结案？

业务恢复 ≠ 冗余恢复。还要看 degraded/undersized PG、副本/EC 同步、重建速率、scrub 错误、复制/双活 lag、快照/备份、容量水位、配置是否保持。状态应是“已缓解”，不是“已恢复/已结案”。

10. 如何验证“故障处理周期缩短 90%”这句话？

定义指标（MTTD/MTTA/MTTR 或告警到关闭）、分母（事故类型/级别）、对照（同一事故集/人工/旧系统）、盲评、时间切分、混杂控制（人员/流程/设备）、统计显著性和成本/误报。要求厂商给出测试条件、样本量、失败案例；否则只能当营销口径。
