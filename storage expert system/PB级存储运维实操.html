建设手册 · 基础 Ceph 回放

第一站在已有的实验 Ceph 集群核对资产和数据覆盖。第二站用合成数据，从相同的业务症状找出三种原因。第三站用模拟器检验设备受理后丢响应、执行进程重启和拓扑变化时，作业能否继续或停下来重审。第四站用一起合成容量事故练习诊断、审批、提交和验收。第二至第四站从仓库根目录开始。第三、四站需要 Python 3.10 或以上，第三站另需 SQLite 3.35 或以上。运行 python -c "import sqlite3; print(sqlite3.sqlite_version)" 查看 SQLite 版本。

1. 接入一个实验 Ceph 集群

收集并对照三类事实

使用已部署且版本明确的实验 Ceph 集群。到可访问管理面的实验节点或 cephadm shell，用已授权的只读身份运行命令。记录站点、责任人、Ceph 版本和集群 FSID。已有业务测试客户端时，登记 workload ID、稳定卷或共享 ID 以及所用池。把下方配置和 keyring 路径换成实验环境中的实际位置。 Ceph 监控 · Ceph 设备管理

ceph_read() {
  ceph -c /etc/ceph/ceph.conf -n client.ops-observer \
    -k /etc/ceph/ceph.client.ops-observer.keyring "$@"
}
ceph_read fsid
ceph_read status --format json
ceph_read osd tree --format json
ceph_read osd dump --format json
ceph_read device ls --format json
ceph_read health detail --format json
ceph_read mgr services --format json
  1. 期望资产。 用完整快照和设备映射建立清单。从 OSD 树取主机和故障域，从 OSD map 取 epoch 与 up/in，从设备信息取盘身份。记录快照的采集时间、发布时间和原文位置。找不到物理盘映射的 OSD 标为待核对。
  2. 已观测事实。 在 Prometheus 查本环境实际提供的 OSD 状态和进程性能计数器。挑一个 OSD，核对资产、状态和采样时间。只聚合单位和测量点都相同的指标。用期望资产数作覆盖率分母。
  3. 事件与变更。 收集健康事件和实验维护记录。比较不同观测时点的快照，把差异记为事件。对同一次变化使用同一个 ID，并记录在哪次快照看到。此后再接真实推送或 ITSM 事件。已有业务测试客户端时，另接应用成功率和尾延迟。

先建三张表。inventory_snapshot(snapshot_id, collected_at, complete, source_ref) 记录快照是否完整。entity_revision(entity_id, native_id, source_id, valid_from/to, known_from/to) 保存资产的各个版本。需要还原历史拓扑时，另建关系表，记录两端的实体 ID、关系类型，以及何时生效和何时可查。调查前查 source_health(source_id, expected_count, reporting_count, watermark, missing_ids)，确认上报范围和数据到达时间。

验收与故障变体

先保存一份健康快照作为基线，再在本地采集副本或回放文件里模拟下列情况。模拟漏读分页时，只截短副本，保留对实验集群的观测。

变体 预期
资产快照缺最后一页 保留上次完整结果，显示本轮不完整。原有资产保持期望成员资格
同一事件重复回放 按 source + event_id 去重，游标在持久化后推进
一个 OSD 指标源停报 期望数不变。报告上报数下降，并列出缺失的实体
晚到的拓扑纠正 仍能复现旧调查时点的快照。在新的调查时点查到修订后的关系
相同 OSD 编号被新生命周期复用 历史事故仍关联原 OSD UUID 或代次，当前资产使用新身份

提交接入验收表，列出数据源、权限、期望数、覆盖率、采样频率、重复测试、断连时间、补传后的数据水位，以及一条可查到原始样本的证据。手头没有实验集群时，先用第二站的 CSV 练习如何统计和对照数据，有集群后再补做接入验收。

2. 从同一个症状识别三种原因

打开跨层回放 CSV。A、B、C 是三个独立的合成事故。每例的应用写 P99 都升到 46 ms，调查均截止于 2026-11-21T02:16:00Z。observed_at 是条目首次可见的时间。网络值是同一业务路径当前值与自身基线的比值，该路径已完成映射。独立对照业务走另一条路径和另一个池。一次只给模型一个案例中已经查到的证据。A 的晚到数据留到复盘。

$replay = Import-Csv -LiteralPath '.\storage expert system\lab\cross-layer-replay.csv'
$cutoff = [DateTimeOffset]'2026-11-21T02:16:00Z'
$replay | Where-Object { $_.case_id -eq 'A' -and [DateTimeOffset]$_.observed_at -le $cutoff }

任务与比较方法

  1. 用“写 P99 超过 20 ms”这条共同规则发出告警，记下单凭规则可以判断什么。
  2. 分轮给模型证据。开头只给业务告警、时间和可查的来源名称。把 application、network、ceph、device、changes、control 当作受限工具，每次调用只给该来源当时可见的数据。逐轮记录查询、返回的证据 ID 和待查问题。可以让模型并行查彼此独立的来源，也可以自己按相同规则选下一项查询。
  3. 输出 impact、hypotheses、evidence_for、evidence_against、next_check。给根因候选标明证据强弱。写一项可能推翻当前判断的检查，并列出缺的信息。
  4. 从 B 的快照移除 B04、B05、B08、B10，注明缺少网络和相关变更数据，再答一次。仍可保留网络路径这个待查候选，但要降低结论置信度。
参考证据与评分
案例 支持最强的候选 排除其他路径还需要什么
A A06–A08 支持 PG 映射变化后 backfill 与前台争用。A02–A05 削弱了提交量突增或已观测网络拥塞的解释 查实际 acting 路径和 OSD 服务时延。A10 到 02:16 时尚未可见
B B04、B05、B08、B10 支持有效链路减少后该路径拥塞。B06、B07 削弱了后端恢复争用的解释 核对主机和交换机两端的时间与流量，确认该链路确实承载受影响业务
C C03、C08、C10 支持单次写入量增加、池吞吐上升。C07 的队列上升，C06 未观察到 backfill 查块大小分布、并发和同池其他负载，核对批量导出与设备压力出现的先后

每例 5 分。根因排序 2 分，引用与反证 2 分，可执行的下一步 1 分。分别记录引用未来数据和编造证据的错误。缺数据时，检查报告能否保留有证据的业务影响，并承认有更多原因待排查。两种方法用相同的来源快照。比较找到第一条能区分候选原因的证据所用时间、调用数和人工复核耗时。

3. 验证一次跨进程的卷扩容任务

工作流模拟器用 SQLite 保存状态。设备作业和执行器状态分开提交，每条命令启动一个新进程。模拟器使用已有审批，可模拟设备已受理但响应丢失、按请求键找回作业、业务先恢复和审批后拓扑变化。请按顺序运行，每条命令推进一步。

路线 A：设备已受理，执行器丢了响应

在 PowerShell 中从仓库根目录运行。每次演练创建独立的临时数据库，便于保留此前结果。

$script = '.\storage expert system\lab\workflow_replay.py'
$db = Join-Path ([IO.Path]::GetTempPath()) ('storage-replay-' + [Guid]::NewGuid() + '.sqlite')
python $script $db init
python $script $db step
python $script $db step
python $script $db step
python $script $db step
python $script $db step
python $script $db verify-protection
python $script $db step
调用 预期状态 验收点
init approved 审批与设备拓扑修订均为 7
第 1 次 step submission_unknown 设备任务数为 1，执行器没有拿到 job ID
第 2 次 step tracking 新进程用原请求键找回 job ID，设备任务数仍为 1
第 3 次 step tracking 设备作业仍在运行
第 4 次 step verifying 作业完成，业务验证通过，保护验证待完成
第 5 次 step verifying 保护信号缺失，工作流仍开放
verify-protection verifying 保护验证通过，等待状态机读取验证结果
最后一次 step succeeded 业务与保护验证均通过，设备受理作业数为 1

路线 B：审批后的拓扑发生变化

$driftDb = Join-Path ([IO.Path]::GetTempPath()) ('storage-drift-' + [Guid]::NewGuid() + '.sqlite')
python $script $driftDb init
python $script $driftDb drift-topology
python $script $driftDb step
python $script $driftDb status

预期状态为 needs_reapproval，设备任务数为 0。查 status，确认审批绑定的是修订 7，现场拓扑已变为修订 8。写出重新规划时要复验的容量、影响路径和保护依赖。

复盘与迁移到真实接口

模拟器只运行一个执行者，审批和验证结果均为预设。接入真实设备时，从厂商 API 或集群管理器获取作业。以 ONTAP 为例，从异步响应取得 job ID，再追踪作业。能否按客户端请求键核对受理状态取决于接口，无法确认时转人工。扩容前确认数据面和文件系统是否支持，并查池水位和保护关系。扩容后验应用可用空间和业务读写。扩容无法原样回退时，提前确定补偿和交接办法。 ONTAP 异步作业

在对照记录里写下 request_id、设备 job_id、审批版本、每次推进前后的状态、业务与保护的验收证据，以及设备受理的作业数。换盘、固件升级、迁移和恢复演练可以沿用这份记录格式。

4. 处理一次写入空间不足的容量事故

这个案例使用合成数据和本地模拟器。全部状态写在临时 SQLite 文件里。脚本只用 Python 标准库，单个执行者分次启动，不访问网络或真实设备。

查清写入失败的原因并批准计划

INC-ENOSPC-01 的应用写入报 ENOSPC（E01）。卷 ceph-lab/pool-7/image-9f 上的文件系统容量为 20 GiB，可用空间为 0，仍有可用 inode（E02）。租户配额余量 10 GiB（E03），池余量 16 GiB（E04）。四条证据都在调查截止 2026-11-22T02:16:00Z 前可查。报告应先确认文件系统已满，再决定能否扩容。

计划把卷和文件系统从 20 GiB 扩到 24 GiB。本题按新增 4 GiB 扣减池与配额余量，扩容后至少保留 8 GiB 池余量。计划哈希涵盖事故、目标、动作、扩容参数、拓扑版本、保护性余量和证据 ID。先检查计划，再把确切目标和哈希交给教学角色 lab-approver。批准从教学时钟当前时刻生效，满 10 分钟失效。首次提交前重新核对审批、卷当前大小、拓扑版本、配额和池余量。

在仓库根目录用 PowerShell 运行。每次演练创建独立数据库。保留 $caseDb 供后续命令使用，脚本会拒绝用错的数据库。

$chain = '.\storage expert system\lab\incident_chain.py'
$caseDb = Join-Path ([IO.Path]::GetTempPath()) ('incident-chain-' + [Guid]::NewGuid() + '.sqlite')
$scenario = 'success'
python $chain $caseDb init --scenario $scenario
python $chain $caseDb diagnose
$plan = python $chain $caseDb plan | ConvertFrom-Json
$plan.plan | ConvertTo-Json
python $chain $caseDb approve --approver lab-approver --target $plan.target --plan-hash $plan.plan_hash --valid-minutes 10

找回作业并分别验收

第一次 step 记录提交意图，模拟设备受理并保存作业，再模拟响应丢失。第二次 step 启动新进程，通过原请求键查回作业 ID。第三次 step 模拟设备报扩容完成，此时还要验业务和保护。查不到原作业或作业参数不符时，转入 needs_review 对账。

模拟时钟从 02:16 开始，设备完成时推进 1 分钟，两个正常探针都在完成后 1 分钟观察。再推进 1 分钟后，分别检查文件系统可用空间、写入与回读，以及 PG 状态和 scrub 校验错误。在设备完成时或更早观测到的记录、来自其他目标的记录和距当前检查超过 5 分钟的记录均不能作为通过依据。

python $chain $caseDb step
python $chain $caseDb step
python $chain $caseDb step
python $chain $caseDb advance-clock --minutes 1
python $chain $caseDb verify-business
python $chain $caseDb verify-protection
python $chain $caseDb status | ConvertFrom-Json |
    Select-Object incident_id, target, phase, device_jobs, job_id, volume_gib |
    ConvertTo-Json -Compress
命令 状态 核对内容
第 1 次 step submission_unknown 设备受理 1 个作业，执行器尚无 job_id
第 2 次 step tracking 用原 request_id 找回 mock-job-001，仍为 1 个作业
第 3 次 step verifying 设备已完成，业务与保护尚未验收
verify-business verifying V-B01 核对 24 GiB 文件系统、可用空间、100/100 次写入及回读
verify-protection succeeded V-P01 核对受影响范围的 PG 均为 active+clean，无退化 PG 和 scrub 错误。两项均通过

成功路线的最后一行实际输出如下。

{"incident_id":"INC-ENOSPC-01","target":"ceph-lab/pool-7/image-9f","phase":"succeeded","device_jobs":1,"job_id":"mock-job-001","volume_gib":24}

重跑失败路线

每次回到本节第一段命令，生成新的 $caseDb。按表改场景或在相应位置插入命令。核对阶段和 device_jobs。

变体 改哪一步 应看到的结果
缺保护样本 令 $scenario = 'missing-protection'，其余照常 业务已通过，保护为 missing。仍是 verifying，作业数 1
等保护样本期间业务证据过期 在缺保护样本的路线中，业务验收后再执行 python $chain $caseDb advance-clock --minutes 6，然后检查保护 业务为 stale，保护仍为 missing。继续 verifying，作业数 1
保护样本过期 令 $scenario = 'stale-protection'，其余照常 V-P00 来自作业完成前，保护为 stale。仍是 verifying，作业数 1
拓扑在批准后改变 批准后执行 python $chain $caseDb drift-topology，再执行一次 step needs_reapproval，作业数 0
审批过期 批准后执行 python $chain $caseDb advance-clock --minutes 10，再执行一次 step needs_reapproval，原因为 approval_expired，作业数 0
角色、目标或哈希不符 分别把审批命令的 --approver、--target 或 --plan-hash 换成错误值，再执行一次 step 审批被拒，仍是 planned，作业数 0
池余量突然降到 10 GiB 批准后执行 python $chain $caseDb tighten-pool，再执行一次 step 扩 4 GiB 会跌破 8 GiB 余量。进入 blocked，作业数 0
