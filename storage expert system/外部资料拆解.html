0. 为什么不能只贴链接

从资料提取设计要求时，记录以下三项。

  1. 记下文档日期和产品版本。产品页改版、文档下线或版本更新后，原结论可能失效。
  2. 核对发布状态。“支持 MCP”可能指博客里的规划，也可能指已正式发布的工具。
  3. 写清机制的输入、输出和验收方法。例如，要用故障树做诊断，就要知道怎么建树、怎么输入症状和怎么评测结果。

1. Ceph 的数据放置与健康

Ceph 先用哈希把对象映射到 PG，再用 CRUSH 把 PG 映射到一组 OSD。PG 的 active/clean/degraded 和 OSD 的 up/in 各有含义。

客户端对象
   │ hash(object)
   ▼
PG（placement group）
   │ CRUSH(pgid, osdmap, crushmap)
   ▼
OSD 集合（主 + 副本/EC 块）
   │
   ▼
BlueStore → 块设备 → HDD/SSD

状态：
  PG: active / clean / degraded / undersized / peering / stale / inactive
  OSD: up/down（进程可用） × in/out（参与放置）
  • active 表示 PG 能提供服务，clean 表示所有副本一致。两项都满足才算完全健康。
  • degraded 表示副本不足，PG 处于 active 时仍可服务。undersized 表示 acting 集合大小低于预期。peering 时 PG 的主 OSD 与其他 OSD 协商数据版本，期间可能暂停服务。
  • up/down 记录 OSD 进程状态，in/out 记录是否参与 CRUSH 放置。down+in 表示进程已停但仍参与放置，up+out 表示进程仍在运行但已移出放置。
  • OSD 下线维护可能触发 PG 重映射和 backfill。backfill 与前台 I/O 争用时，IOPS 可能接近原水平，延迟却上升。

维护时 osd.11 下线，PG 从 osd.11/12/13 重映射到 osd.12/17/18。即使 PG 有 active 状态，也可能同时标了 undersized 或 degraded。用 ceph health detail 查看具体 PG 和原因。

保存 PG 和 OSD 的原始状态。若业务延迟也升高，沿维护、重映射、backfill 的时间线查哪些前台请求共用了这些资源。

原文见 Ceph OSD/PG 监控 · Ceph 健康检查 · Ceph 文档总入口

2. Ceph Prometheus 模块

ceph-mgr 内置 Prometheus exporter，通过 /metrics 暴露集群、OSD、PG 和池指标。Prometheus 抓取后，由 Grafana 展示，Alertmanager 发送告警。

ceph-mgr (prometheus module)
   │ HTTP /metrics
   ▼
Prometheus（scrape、存储、规则）
   ├─ Grafana（看板）
   ├─ Alertmanager（告警）
   └─ 远程写/长期存储（可选）
  • exporter 随 mgr 进程运行。常见指标包括 ceph_osd_*、ceph_pg_* 和 ceph_pool_*。
  • 抓取间隔决定时间分辨率，常见为 15s 或 30s。大集群要核对抓取是否超时，以及产生了多少条序列。
  • 按 OSD 和 PG 打标签会增加序列数。PG 多时，可限制导出的指标或标签，也可用 recording rule 预聚合。
  • mgr 故障可能中断指标上报。监控 mgr 状态和抓取结果。

用资产表里预期上报的 OSD 数作为覆盖率分母，才能发现 OSD 停报。

coverage = 有目标指标新样本的预期 OSD 数 / 预期上报的 OSD 总数

若一半 OSD 停报，仅剩余 OSD 的平均延迟可能反而下降。记录资产台账中的预期数，再与目标指标的新样本数计算覆盖率。ceph_osd_up 为 0 表示已上报下线，Prometheus 的 up 表示抓取是否成功。PG 级指标可按需查或聚合后留存。

原文见 Ceph Prometheus 模块 · Ceph 监控（Squid）

3. Ceph mClock

Ceph Tentacle 的 OSD mClock 用 reservation、limit、weight 给客户端 I/O、后台 recovery 和后台 best-effort 分配资源。backfill、scrub、快照裁剪和 PG 删除归入后台 best-effort。

请求 → 分类（client / background recovery / background best-effort）
        │
        ▼
   mClock 调度器
   ├─ reservation：保底份额
   ├─ limit：上限
   └─ weight：剩余能力按权重分
        │
        ▼
   OSD 后端（BlueStore/介质）
  • reservation 保证最低份额，limit 限制最高份额，weight 决定怎么分剩余份额。
  • 选 profile 时同时看客户端延迟、recovery 和 backfill 完成时间。后台份额太小，副本不足的时间就会延长。
  • 调参前查 Ceph 版本、OSD 实际使用的 profile 和调度模式。内置 profile 会设置底层参数。手动改值前，查支持的修改方式和参数会被覆盖的条件。
  • 介质已饱和时，调度只能调整各类请求的份额。

前台 P99 高、backfill 压力大、磁盘利用率 90%。在演练中切换到优先前台的 profile，比较切换前后的 backfill 速率、PG 状态和业务 SLO。backfill 属于 best-effort。只改 recovery 的 limit 时，仍需查 backfill 的份额。若 P99 未下降，先核对变更和 backfill 速率，再查网络、设备和客户端。

写清业务 P99 和恢复进度各自的验收条件，并约定什么时候回滚。

4. Prometheus 直方图与原生直方图

直方图按累计桶记录延迟分布。先合并各实例的桶，再算全局分位数。原生直方图使用稀疏桶和指数桶，减少配置和存储开销。

请求延迟
  │ 观察值落入桶
  ▼
桶计数（le=10ms, 20ms, 50ms, ...）
  │ 累计
  ▼
histogram_quantile(0.99, sum by (le) (rate(bucket[5m])))
  │ 桶内线性插值
  ▼
P99
  • 经典直方图的桶边界固定。各客户端或实例的边界一致时才能合并。
  • 按 le 汇总桶计数，再算全局 P99。
  • 线性插值假设桶内均匀分布。桶太粗，估计误差可能较大。桶越细，经典直方图的序列越多。
  • 启用原生直方图前，确认客户端和服务端都支持。

三个客户端共发出 100 万次请求。合并桶后，984,000 次 ≤20 ms，996,900 次 ≤50 ms。第 990,000 次请求落在 (20,50] ms 桶，桶内线性插值得出 P99 约为 33.95 ms。各客户端 P99 的算术平均约为 41.48 ms。 原始桶计数与计算

用合并后的桶按 SLO 的延迟阈值统计请求。低流量窗口要报告样本量，因为 P99 可能只由一条请求决定。

5. OpenTelemetry 日志与时间语义

OTel 用 resource 记录日志来自哪个资源，用 scope 记录哪个库或模块生成，用 record 记录事件本身。事件发生时间和采集端看到的时间分开记录。

Resource（service.name, host, k8s.pod）
   └─ Scope（instrumentation library）
        └─ LogRecord
             ├─ time_unix_nano（事件时间）
             ├─ observed_time_unix_nano（观测时间）
             ├─ severity / body / attributes
             └─ trace_id / span_id（可选关联）
  • time_unix_nano 记录事件发生时间，observed_time_unix_nano 记录采集端看到事件的时间。设备时钟偏差、缓冲和批处理都可能拉大两者的差距。
  • 用 trace_id/span_id 关联日志和追踪。缺少这些字段时，按实体和时间窗对齐。
  • 统一日志属性键，如服务名、集群、租户和实体 ID，便于聚合。
  • 采集端要处理积压，并记录丢弃情况。

一条告警发生于 02:10:30，02:18 才被采集。以 02:16 为截止做回放时，只选 observed_time <= 02:16 的记录，这条告警留到复盘。归档时保存事件时间、观测时间和来源。

6. Everpure Pure1 + Fusion：设备群遥测与工具化调查

Pure1 收集阵列遥测，提供健康、容量和性能视图。外部 Agent 可分别接入只读的 Pure1 Manage MCP，以及查询阵列内部关系和工作负载的 Fusion MCP。Fusion 2.0 的写工具默认关闭。

阵列（Pure Storage FlashArray/FlashBlade）
   │ 遥测/健康/容量/性能
   ▼
Pure1 管理面（设备群视图、AI Copilot、MCP Server）
   │ 只读查询
   ├─ 健康/容量/性能/告警
   └─ 设备群/租户/站点

Fusion（阵列、卷、文件系统、工作负载、预设、拓扑）
   │ MCP / 直连令牌
   ├─ 拓扑与关系查询
   ├─ 部分性能查询（依赖直连令牌）
   └─ 可选写工具（默认关闭，启用后核对确认设置）
  • 用 Pure1 找出异常站点、租户或设备。
  • 用 Fusion 查卷在哪台阵列、属于哪个工作负载，以及与谁共享资源。
  • MCP 为查询工具定义输入格式，Copilot 或 Agent 从工具输出读取事实。
  • Fusion 2.0 的精选写工具和通用写工具各自启用，均受阵列令牌约束。保留默认服务端确认时，不支持交互确认的客户端会被拒绝。管理员可关闭这项确认。它只覆盖通过 Fusion 发出的请求。要查普通批准和拒绝，查看 INFO 日志，默认 WARN 不记录这两类事件。

值班收到“订单库延迟升高”的报告。

1) Pure1 MCP: 查设备群健康/性能 → 发现 site-a 的 array-3 前端延迟升高
2) Fusion MCP: 查 array-3 上的卷/工作负载 → 定位 orders-vol
3) Fusion MCP: 查卷的拓扑/共享依赖 → 发现同阵列的 backup-vol 在同一池
4) 查变更：备份作业在 02:12 启动
5) 结论：备份与订单卷共享池/后端，可能是争用；列出反证（网络/磁盘/负载）

保存每次调用的工具、实体、时间窗和结果。共享存储池与备份开始时间只支持争用候选，仍需查网络、磁盘和业务负载。读写工具分别授权。

7. NetApp AutoSupport + Digital Advisor：遥测、资产与风险建议

ONTAP 的 AutoSupport 把设备遥测、日志和配置发给 NetApp。Active IQ/Digital Advisor 将这些记录与资产、软件版本和支持合同关联，给出风险、容量、升级和生命周期建议。

ONTAP 集群
   │ AutoSupport（遥测/日志/配置，周期或事件触发）
   ▼
NetApp 支持云（Active IQ）
   ├─ 资产/合同/版本
   ├─ 风险规则/健康评分
   ├─ 容量趋势
   └─ 升级/生命周期建议
        │
        ▼
Digital Advisor（看板/报告/建议）
  • AutoSupport 还上报事件。风险规则和知识库可用来查已知 bug、终止支持（EOL）和配置最佳实践。
  • 用历史容量估算趋势。确定升级方案前，核对版本兼容矩阵和支持合同。
  • 数据保存在厂商云。客户可查看建议和报告，原始数据能否导出需另行确认。

某卷使用率 80%，支持合同还有 8 个月到期。每周增加 5 个百分点，两周到 90%。每周按 5% 复利增长，约 2.41 周到 90%，按周采样要到第 3 周才看到越线。值班员用容量趋势评估扩容或分层，再按合同和当前版本的 EOL 时间核对是否应升级到 X。

8. NetApp DII + MCP：先验证采集，再查容量/性能

Data Infrastructure Insights（DII）采集资产、性能、容量和日志。先用它核对采集健康和资产身份，再查 Monitor 告警或用 MCP 读取数据。

数据源（ONTAP、E-Series、StorageGRID、交换机、VMware、云）
   │ 采集器
   ▼
DII 数据层（资产、性能、容量、日志、告警、采集健康）
   ├─ Monitor（阈值/异常/容量/性能）
   ├─ 看板/报告
   └─ MCP（Preview，租户内只读：性能/容量/日志/告警/采集健康）
  • 查询指标前，先查采集器是否在线、应采的数据是否到齐。
  • Monitor 能按阈值、异常或容量规则生成事件和告警。根因需要另行调查。
  • 截至文中核验日期，MCP 仍是 Preview，工具只读且限于当前租户。

应用 P99 升高，DII 显示某阵列性能异常。3 个采集器中有 1 个断连，采集器在线率为 67%。资产覆盖率还要按授权台账查哪些设备有样本。暂时只用已收到的数据作判断。

原厂配方用 AcquisitionUnitsService_getAcquisitionUnits 查采集单元和最后上报时间，用 CollectorService_getDataSources 查数据源和最后成功采集时间。有缺口时查看单个单元或数据源详情。接入方可自建 collection_status 汇总这些结果和资产样本覆盖率。没有可靠的台账分母时，覆盖率记为未知。

9. Dell AIOps / PowerStore：健康评分、预测与来源保留

PowerStoreOS 4.2 的本地异常视图标记设备性能偏离。另行连接 Dell AIOps 后可查云端健康、趋势和容量等分析。设备 Health Checks 可按条件处理指定的已知问题。

PowerStore
   ├─ 本地 Manager（4.2）：设备性能偏离点，无直接告警
   ├─ Support Connectivity + 云端接入 → Dell AIOps：健康、趋势和建议
   └─ Health Checks：4.2 起检查包纳入 RxDefinitions，并可对指定问题开启 Auto-Repair
  • 本地异常视图按设备显示时延、IOPS、带宽和 I/O 大小，只标偏离点。单卷要查对应性能视图。
  • 云端健康分和助手取决于是否接通、上传了哪些数据以及账号支持范围。核对建议能否追到指标或告警。
  • 只有命中可修复的已知问题，并满足检查包、版本和模式要求时，才验 Auto-Repair。

云端报某卷 24 小时内用量增加 20%，本地设备 IOPS 变化不大。值班员再查卷用量、快照、克隆、备份和应用变更。找到增长原因后，附对应指标、事件或变更记录。

10. AWS DevOps Agent：跨栈调查与沙箱

AWS DevOps Agent 在 Agent Space 内关联拓扑、告警、日志和变更。调查工具在只读沙箱内运行，网络访问受白名单限制。

Agent Space
   ├─ 应用拓扑（服务/资源/依赖）
   ├─ 告警/日志/指标/变更
   ├─ 调查工具（只读 AWS API）
   └─ 沙箱（临时环境、网络白名单）
        │
        ▼
   调查结论/证据/建议

按服务卡核对评估口径、用户角色、功能范围和限制，再配置 Agent 可查看的应用、账号和数据。

部署后 5 分钟，错误率上升。Agent 根据服务拓扑查下游，把部署、配置变更和下游超时放到同一时间线上。Agent 可提出建议，在沙箱验证。生产变更走审批流程。

11. 华为 DME：设备侧管理面的完整数据通路

iMaster DME 部署在数据中心，通过 REST、SNMP、SSH 和 CSI 纳管华为与第三方存储，以及交换机、服务器、虚拟化和容器。它提供资源管理、监控、诊断、自动化和数据目录。DME IQ 部署在云端。

设备/主机/交换机/虚拟化/容器
   │ 南向：REST / SNMP / SSH / CSI / 平台 API
   ▼
┌─────────────────────────────────────────────┐
│ iMaster DME（ServiceMesh 微服务）            │
│  配置库 / 历史库 / 搜索索引 / 告警引擎        │
│  拓扑 / 智能分析 / 健康评分 / 故障智能体       │
│  资源发放 / 编排 / 工作台 / 数据目录           │
└─────────────────────────────────────────────┘
   │ 北向：RESTful / SNMP Trap / Ansible / CSI / 云管 / ITSM
   ▼
客户云管 / ITSM / 自建平台

独立云服务：iMasterCloud DME IQ（移动 APP、Call Home、工单、在线客服）
  • 华为存储通过 RESTful 接口同步资源和性能数据，用 SNMP Trap 上报事件。端口光功率等少量指标走 SSH。第三方设备用各自接口。资源每 6 小时同步，性能粒度为 1 或 5 分钟。
  • 从配置库查当前属性，从历史库查性能，用 OpenSearch 做全局搜索。要查事故当时的拓扑，需另存关系来源和版本。分钟级数据保留 7 天，30 分钟聚合保留 6 个月，天级保留 2 年。受支持的 Dorado V6 及后续设备要预先启用 5 秒留存，DME 才能从设备按需回查，最长一周。DME 自身不保存 5 秒历史。

16. FAST ’20 硬盘故障预测：标签、特征与评测

论文用了 64 个站点约 38 万块盘的两个月数据，从 SMART 时序特征预测未来 10 天的故障，报告平均 F-measure/MCC 约为 0.95。

每块盘每天的特征（SMART/型号/年龄/变化率）
   │
   ├─ 标签：未来 H 天内是否故障
   ├─ 切分：按时间/按设备，避免同盘泄漏
   ▼
模型（特征工程 + 分类器）
   │
   ├─ PR 曲线/阈值
   ├─ 提前量分布
   └─ 校准/误报
  • 每块盘每天是一条样本。同一块盘的样本高度相关，随机切分可能让同一块盘同时进入训练集和测试集。
  • 标签定义里写清故障窗口 H。窗口越长，可以更早预警，预测也更难做准。
  • 特征包括 SMART 原始值和变化率，以及型号、固件和年龄。不同厂商的 SMART 属性可能不同。
  • 故障样本占比很低。评估 PR-AUC、告警预算下的召回率、提前量和概率校准。

某块盘今天出现 SMART 待定扇区，模型给出未来 10 天故障概率 0.3。若在告警预算内，可安排提前换盘。校准差时，报 0.3 的这一批盘实际故障率可能只有 0.05，会多报很多告警。

验收时先检查故障标签和训练、测试切分，再对照告警预算和实测故障率。

18. MCP：把工具变成可发现、可调用的协议

Model Context Protocol 用 JSON-RPC 连接客户端和服务端。服务端提供 tools、resources 和 prompts。客户端把工具描述传给模型，由模型选择调用。

Host（Claude/IDE/Agent）
   │ MCP Client
   ▼ JSON-RPC
MCP Server（存储/监控/知识库）
   ├─ tools/list → 工具 schema
   ├─ tools/call → 执行并返回
   ├─ resources/list/read → 资源
   └─ prompts/list/get → 提示模板
  • 工具声明名称和输入格式，可补描述和输出格式。模型根据工具说明选择调用。
  • resources 提供只读上下文，prompts 提供预置模板。
  • 在连接和工具两层控制访问。连接层按 stdio 或带认证的 HTTP 配置。工具层限制租户和实体范围，写工具单独授权。
  • 存储团队要定义工具的实体、时间窗、单位和证据 ID。

下面是 tools/call 请求的 params 示例。

{"name":"query_metric","arguments":{"entity_id":"ceph-a/hot","metric":"p99_ms","start":"2026-11-10T02:00:00Z","end":"2026-11-10T02:16:00Z","step":"1m"}}

服务端返回样本、缺失区间、覆盖率和 query_id。模型在报告中引用 query_id，审核人据此查原始结果。

19. NVMe 规范：队列、命令与命名空间

NVMe 通过多对提交和完成队列、doorbell 和命名空间组织命令。多队列可提高并发并降低共享队列带来的延迟。

主机
 ├─ Admin 队列（创建/管理）
 └─ I/O 队列（常见为每核一组）
      │ 提交命令 → SQ tail doorbell
      ▼
   NVMe 控制器
      │ 执行 → 完成队列
      ▼
   命名空间（Namespace）→ NAND/介质
  • 较深的队列可容纳更多并发请求。每核独立队列可减少锁竞争。轮询和中断模式也会影响延迟。
  • 命名空间是逻辑块设备。NVMe-oF 使用多路径或多个控制器时，要处理路径故障。
  • NVMe-oF 可通过 TCP、RoCE 或 FC 传命令。排查尾延迟时先看网络拥塞。使用 RoCE 时，再按组网方案检查 PFC 或 ECN 配置。

4 KiB 随机读、队列深度 64 时，单盘可达 500k IOPS。改为队列深度 1 后，IOPS 会低很多。观测到的延迟包括排队和服务两部分。

IOPS 和延迟同时升高时，对照各队列深度和拥塞位置，再判断慢在排队还是介质服务。

21. Google SRE Workbook：SLI、SLO、错误预算与燃烧率

用 SLI 衡量可靠性，用 SLO 定义目标。错误预算率为 1−SLO，燃烧率为错误率除以错误预算率。

SLI（好请求/总请求）
   │
   ▼
SLO（如 99.9%/30 天）
   │
   ├─ 错误预算 = 0.1%
   ├─ 燃烧率 = 实际错误率 / 0.1%
   └─ 多窗口告警（1h/5m）
  • SLI 要写清在哪测、哪些事件算好、哪些计入分母。SLO 是内部目标，SLA 通常约定商务后果。
  • 团队按剩余错误预算决定是否继续发布。预算用完后冻结变更。
  • 用长、短窗口共同判断燃烧率，兼顾快速发现和控制误报。只有一个阈值时，容易频繁通知值班人员或漏报。
  • 除请求成功率外，还要为存储定义冗余和耐久性指标。

30 天请求型 SLO 要求 99.9% 的请求为好请求，错误预算为全周期请求数的 0.1%。流量近似均匀时，相当于完全不可用 43 分 12 秒。1 小时坏请求率为 1.44% 时，燃烧率为 14.4，消耗周期预算的 2%。可要求 1 小时和 5 分钟窗口都超过阈值再告警，由团队定义通知级别。

处置后分别复查业务 SLO 和存储冗余。
