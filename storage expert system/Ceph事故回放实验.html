要查什么，用哪些数据

02:16 UTC，值班员接到投诉，orders 写入变慢。先确定哪些业务受影响，再按现有证据给原因排序，最后记下还要查什么。

每行时间是 5 分钟窗口结束时刻，间隔不足 5 分钟的窗口有重叠。

  • 业务。 请求总数包含错误。healthy_writes_under_20ms 统计成功且延迟 ≤20 ms 的写请求。write_iops 是窗口内平均提交速率，write_p99_ms 是应用端的窗口 P99。
  • 存储。 osd_device_queue 取目标路径上观测到的最高设备队列深度，backfill_mib_s 是池相关活动的窗口平均速率。
  • 网络。 retransmits_per_s 是已采集 TCP 路径的平均重传率。
  • 覆盖率。 用实际有上报的目标 OSD 数除以预期上报数。已退出服务的旧 OSD 单独处理。

本题每个窗口的 SLO 是至少 99% 的写请求成功且延迟 ≤20 ms。窗口未达标时保留错误数和总请求数。查询日志和遥测只取 observed_utc ≤ 调查时点 的记录，查询拓扑按事发时间。以下事件、拓扑和结果均为合成数据。

操作顺序

  1. 什么时候报警？ 用 M01–M05 的 P99 算中位数和 MAD（各点到中位数距离的中位数）。用 z = 0.6745 × (值 − 中位数) / max(MAD, 1 ms) 算 M06 和 M07。连续两条采样的 z ≥ 3.5 才触发，注意窗口有重叠。再算 M07 和 M08 的好请求比例，划定影响范围。
  2. 延迟卡在哪里？ 只看 02:16 已可见的证据。用 E02 和 T02 对照回填记录和放置目标。要确认实际服务路径，还需查 up/acting 和各 OSD 的指标。分别说明后端争用、备份流量和网络问题各有哪些证据、还缺什么。
  3. 模型会接着查什么？ 在同一份 02:16 快照上跑阈值规则，再用模型写报告。按下方模板分次给证据，记录查询和返回的证据 ID。证据不足时，让模型限定下一次查询的时间和范围，或把原因标为未决。沿用同一组输出字段。
  4. 少了数据还能确认什么？ 隐藏 E02、T02 和 M06–M07 的 backfill、队列字段。把这两行的 reporting_osds 改为 1，保留应用 SLO。看报告能否确认业务影响，并把后台恢复争用列为待查原因。
  5. 业务何时好转？退化 PG 何时降到 0？ 把调查截止改为 02:35:15，加入 E04、E05 和 M09–M12。逐行算好请求比例，核对请求强度和退化 PG 数。记下应用何时好转、退化 PG 首次在哪个窗口降到 0。结案前再查受影响的 PG 是否均为 active+clean，确认业务和数据保护持续达标。

完整快照测试只给 M01–M08、E01–E03 和 T01–T03。缺数据测试另开会话，只给变体快照。到处置验证再加入晚到证据和干预数据。参考答案留给人工评分。
