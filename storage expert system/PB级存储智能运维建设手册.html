学习导览 · 原理与实现 · 三站实操 · 厂商能力对照

本篇以三个站点约 10 PB 原始容量、块/文件/对象混合部署为教学假设，沿着同一条路线建设系统：设备纳管 → 现场证据 → Agent 调查与计划 → 审批和执行 → 业务与数据保护验收。初版选择一个 Ceph 集群、一条应用写入路径和一个可观察的设备异步作业。第二个厂商接入后，用同一任务协议验证设备适配层。容量、采样和验收数字均为算例，上线时由业务 SLO、采购周期和设备实测决定。

1. 定容与部署

先列四本账。业务账决定可承载多少数据与负载，观测账决定采集规模，资产账决定拓扑和清单规模，任务账决定调查与处置并发。每本账都有独立分母。

2. 多厂商接入与数据管道

新设备从登记到上线

  1. 登记。 录入站点、设备所有者、管理端点、厂家型号、固件、设备标识范围和权限。适配器获得独立只读凭据，执行通用的身份和时间探测。
  2. 能力探测。 记录能否列出盘/卷/端口、哪些指标可读、历史查询范围、事件订阅、分页和限流语义。明确每项能力所需版本。异步作业查询和写入能力另行登记。
  3. 首轮全量。 按页遍历资产，记录快照标识与采集状态。在完整快照成功后发布新一代资产。分页失败时保留上一次完整结果，标记过期。只有确认扫描完整后才将消失的资产转为待核对或退役。
  4. 增量与对账。 有事件游标时从游标续订，用事件通知驱动重点对象刷新，同时周期获取全量或摘要核对。全量期间收到的事件按快照边界及源版本重放。接口缺少稳定快照或游标时，记录盲区并缩小重查范围。
  5. 上线验收。 对照设备界面抽查身份、单位、数量和路径。模拟凭据失效、分页错误、事件丢失和限流。固件升级后重新探测，设备退役时保留历史身份和证据引用。

按实际设备能力选择厂商 REST、Redfish/Swordfish、Ceph、SNMP 或受限的只读采集器。Swordfish 给出通用的存储资源模型，各型号仍需对照其实际支持。Ceph Manager 的 Prometheus 模块提供集群级监控，ceph_exporter 暴露进程性能计数器，应用端 SLO 另从业务测量。 SNIA Swordfish · Ceph Tentacle 监控

每种数据独立设水位。推荐同时展示期望设备数、上报设备数、关键指标新鲜率、延迟分位和丢弃量。断链恢复后按优先级上传关键事件、恢复查询水位，再补普通明细。只对有明确语义的重复项去重。缓冲满时记录丢失的信号类型、数量和时间段，排查工具返回 PARTIAL_COVERAGE。以上游至少一次交付为工作假设，接收端用源 ID 或稳定键防重。

3. 业务到物理设备的映射

一个可用的实体目录要把三条关系区分开。

关系 典型路径 用于回答
I/O 路径 应用 → 主机/容器 → 卷或共享 → 前端端口 → 控制器/网关 → 池 → 介质 这个慢请求经过哪里？哪些观测点缺失？
放置与保护 卷 → 池 → PG → up/acting OSD，或 卷 → 快照 → 复制对 → 远端恢复点 下线一块盘会失去哪些副本？本次变更会否影响 RPO？
共享故障域 盘 → 盘柜 → 控制器 → 机架/电源/交换机 → 站点 多个告警是否共享背板、链路或供电？能否同批处置？

容器场景先从业务、Pod、PVC、PV 找到 CSI volumeHandle，再用驱动或后端接口映射到卷的稳定 UUID。FC 可按主机 WWPN、交换网络和阵列卷映射对齐。Ceph 路径同时留 OSD map epoch、up 和 acting，避免把正在迁移的放置目标当成实际服务路径。资产表记录“同一物理盘的新旧名称”“同一槽位换了盘”“一个 OSD 重新部署”等区别。低置信匹配允许查看并标注，设备变更前需要确认目标。 Kubernetes 持久卷 · Ceph OSD 与 PG 状态

证据服务按 实体 + 事件窗口 + 调查截止 查询，并返回数据新鲜度、来源、单位、原始查询与证据 ID。调用时先查应用和影响范围，再看事发拓扑。缩小到候选路径后才读取设备明细。更新后仍要能回放事故当时看到的关系，具体表和索引见进阶篇时态查询。

4. 按设备与故障域诊断

故障面 支持证据与对照 处置与验证
介质、背板与盘柜 盘的介质错误和延迟上升；横向比较同盘柜、同型号的盘。多盘同时异常时，重查共享链路、电源与控制器 风险评估按物理标识和所在故障域。验证新盘身份、数据迁移、冗余与业务影响
主机、多路径与 SAN 应用慢且主机队列升高。区分写量与块大小变化、路径切换、交换机拥塞及阵列端口异常 用实际有效路径对照，观察重试、队列、错误和端到端好请求比例
控制器与共享池 比较控制器 CPU、缓存、端口与池延迟。同池和异池负载形成不同对照 评估 QoS、工作负载安置或迁移，追踪受影响租户和控制器余量
Ceph 恢复与重平衡 查 OSD/PG、up/acting、backfill 与恢复速率。与前台请求强度、网络及设备队列对齐 受监督评估后台调度和维护窗口。校验前台恢复及 PG 冗余完成
文件与对象元数据 文件关注客户端、MDS/元数据池与数据路径。对象关注网关、单租户/桶热点、索引与后端 文件操作按 create/stat/readdir 与读写分开验收，对象按 GET/PUT/LIST、状态码和对象大小分开
复制、快照与备份 跟踪复制 lag、恢复点年龄、完整性校验、任务失败、保护目标和远端水位 实际恢复到隔离目标，检查数据一致性和应用能否读取，再计算实测 RPO/RTO

一个风险盘口径应证明 预测 → 资产认定 → 变更可行性 → 验收。输入盘寿命预测时保留模型、阈值和预测窗口。Agent 对照同机框信号与历史故障，检查是否存在同时发生的链路或固件问题。准备维护时按故障域排序，验证副本与 min_size、设备余量、正在恢复的任务、备件与当班工单。作业进行中监控恢复速度与业务 SLO，结束后核对硬件序列号及业务读写。升级同理，额外核对兼容矩阵、分批窗口、回退限制和混合版本约束。 Ceph 设备管理 · Ceph OSD 服务 · CephFS 排障 · AWS Backup 恢复验证

算例。 两块风险盘都告警。盘 A 的介质错误持续增加，同机框其他盘无相同变化。盘 B 的介质错误平稳，但同机框多盘的链路重试同步上升。Agent 对 A 生成换盘候选，对 B 追加背板、控制器端口与电源检查。若 A 所在池仍在恢复，即使预测风险高，也要先复验冗余。假设需迁移 12 TB，有效恢复速率估为 200 MB/s，理想耗时约 16.7 小时。若维护窗口仅 4 小时，要评估窗口外持续恢复的业务和保护影响，再决定改期或调整分批。

5. Agent 怎样承接不同运维任务

用户在对话、告警与工单入口提出目标。系统把意图转换为任务类型、设备范围、限制条件和期望交付。一个入口可以服务多类任务，技能负责各自的证据顺序和完成条件。

需求 技能输入 Agent 工作 完成交付
“早班巡检哪些站点要关注？” 站点、时间窗、责任队列 先核对数据覆盖，再合并故障域告警、容量风险与保护异常 带优先级、负责人、缺测站点和原始证据的巡检单
“订单写入为什么突然变慢？” 业务、症状、开始窗口 查 SLO 和对照，沿拓扑并行读取主机/网络/阵列，再根据结果挑选反证 影响范围、竞争假设、待验证项和下一步动作
“这批高风险盘能安排本周换吗？” 设备范围、维护窗口、备件 校验身份、风险、冗余、容量和共享故障域，选择可安排批次 能换、应推迟、需人工确认三类对象及各自原因
“池还能撑过采购周期吗？” 池、用量口径、采购/上架时间 查高增长情景、最紧张故障域、快照牵连与回收影响 到阈值区间、提前量、扩容与回收选项
“验证这份备份能在半小时内恢复” 恢复点、目标、RTO/RPO、应用检查 查所有依赖与恢复资格，生成受监督的隔离恢复任务，读取状态与结果 实测时间、恢复点、校验结果、未达项

每个技能至少定义 skill_id/version、输入与授权范围、允许的工具、目标证据与候选假设、降级条件、最大时长/工具开销、响应结构、退出与交接。模型负责解释目标、选择下一条信息量大的查询、组织解释与计划。规则与统计模型负责阈值、趋势、硬盘风险和候选打分。工具网关负责用户身份、租户范围、强类型参数、查询预算与审计。执行器只接受策略认可并经过审批的动作版本。

第一段查询通常取得业务影响、采集健康和拓扑。第二段可并行查网络、设备、近期变更，结果回来后只追踪仍有区分度的候选。例如 MDS 元数据延迟恶化而数据路径稳定，就查 create/stat、缓存回收和目录扫描。累积证据中断时，回传已经确认的事实、未决假设与下一步。记录技能、规则、模型、证据快照和调用轨迹，便于对照升级。 AWS DevOps Agent 技能与调查模式 · 已有工具契约

计划记录目标稳定 ID、事实快照、预期配置差异、策略版本、风险限制、验证与补偿。审批绑定计划哈希、目标和有效期。执行开始时重读配置、拓扑、容量和冗余，检查工作流是否与别的维护冲突。动作在限定范围用单独服务身份执行，持续追踪厂商作业或集群状态。长时任务保存作业 ID、游标、已完成步骤与复查截止时间，工作进程重启后继续。

重点是处理结果未知。 客户端超时可能发生在设备接受动作之后。先保存提交意图和幂等键，重启或超时后按幂等键、作业 ID、设备状态对账。如果接口支持原生幂等，重试应沿用同一个键。只有能确认先前动作未受理时，才考虑重新提交。接口无法确认时，交给人工核对。幂等键应与不可变请求内容关联。并发执行以集群、池或故障域限制影响量，并用租约与版本防止过期执行者推进任务。ONTAP 的异步 202 和设备 job 示例可用来理解受理与完成的区别。 ONTAP 异步作业 · Temporal 活动与重试

验证读取设备实际状态和业务指标。恢复操作还要验校验结果、应用可读与复制进度。可逆配置按预案撤回。卷扩容等操作应按产品能力提前定义补偿、隔离、人工接管或恢复路径。分批部署时用同类设备作对照，并检查样本量和查询质量。 Google SRE 金丝雀发布

7. PB 级数据资产运营

需要做归档、迁移、空间回收时，新增资产清单与生命周期任务。原始数据留在存储侧，区域目录记录对象或文件版本、大小、时间、租户、保护状态、可用的访问特征与数据位置。业务访问热度应来自独立的访问记录或对应产品提供的统计。清单用作基线，增量事件用于追踪变化，定期对账发现删除、改名、版本变更和遗漏。文件系统的 inode 身份需要带文件系统与生命周期，不能把一次路径扫描当成永久身份。

例如归档 200 TB 文件或对象，持续可用带宽 400 MB/s，理论数据搬运约 139 小时，实际还要考虑小文件的元数据开销、校验、重试、回读成本与业务高峰。技能先查访问热度与归属，再排除保留期限、法务保全、快照引用、合规与恢复时限不满足的对象。执行按批次保存清单、迁移状态与校验结果，只有策略允许且核验通过才进入源数据处置。快照或版本保留可能让逻辑删除与实际释放容量不同。 Amazon S3 Inventory · S3 Lifecycle 行为
