1. 介质与控制器：延迟和可靠性的物理来源

1.1 HDD：寻道、旋转与顺序性

HDD 的一次随机读包含寻道、旋转等待、传输和排队。

T = T_queue + T_seek + T_rotational + T_transfer
  • 寻道。磁头移动到目标磁道。企业级 7200 rpm 盘平均需 4–8 ms，最坏可达十几毫秒。
  • 旋转。磁头等目标扇区转到下方。平均旋转半圈，可按转速 rpm 换算。
平均旋转延迟(ms) = 30,000 / rpm
7200 rpm → 4.17 ms
15,000 rpm → 2.00 ms
  • 传输。用块大小除以持续带宽得到传输时间。
  • 排队。等待控制器或设备处理。高并发时，排队时间可能最长。

以一块 7200 rpm 的 HDD 为例，估算 4 KiB 随机读 IOPS。

IOPS ≈ 1 / (平均寻道 + 平均旋转 + 传输 + 排队)
     ≈ 1 / (6 ms + 4.17 ms + 0.02 ms) ≈ 98 IOPS（单队列、无缓存）

企业盘可借助缓存、命令队列、重排请求和短行程（short-stroke）达到 150–200 IOPS。用 HDD 承载小块随机 I/O 时，按每盘每秒百余次的量级估算，再用实测核对。

顺序读很少来回寻道，带宽取决于面密度和转速。企业级 7200 rpm 盘通常为 200–280 MB/s。随机读用 IOPS 比较，顺序读用带宽比较。

SMR（叠瓦式）盘随机写时可能要重写磁道，造成延迟和写放大骤增，也叫“写入悬崖”。这类盘适合顺序追加和归档。为数据库随机写选盘时，先区分 CMR 和 SMR。

HDD 可能因磁头或介质缺陷、振动、温度、掉电或固件故障而失效。SMART 可记录重分配扇区、待定扇区、不可纠正错误、命令超时和 CRC 错误。信号往往少、出现得晚，还会随型号变化。

1.2 SSD：FTL、GC 与写放大

SSD 按页读写，按块擦除。

  • 读写单位是 page，常见大小为 4–16 KiB。
  • 擦除单位是 block，常见大小为 128–512 个 page。
  • 写过的物理页要等所在块擦除后才能再次写入。

FTL（Flash Translation Layer）把逻辑块映射到物理页（page）。更新时把数据写到新页，把旧页标为无效。垃圾回收（GC）先搬走仍有效的页，再擦除整个块（block），腾出空间供后续写入。垃圾回收和前台 I/O 争用带宽时，尾延迟会升高。

按实际介质写入量和主机写入量计算写放大。

WA = 写入 NAND 的数据量 / 主机写入的数据量

例如主机写 1 TB，NAND 实际写 2.5 TB，WA = 2.5。WA 越高，寿命消耗越快、有效带宽越低。

用 TBW 和 DWPD 描述写入寿命。

TBW（Total Bytes Written）= 保修期内可写入的总量
DWPD（Drive Writes Per Day）= TBW / (容量 × 365 × 保修年数)

例如，一块 3.84 TB 的盘保修 5 年，TBW 为 7,000 TB。

DWPD = 7,000 / (3.84 × 365 × 5) = 7,000 / 7,008 ≈ 1.0

若每天写入 5 倍全盘容量，约 1 年就会达到保修写入量，估算忽略写放大和预留差异。规划时同时计算 IOPS、带宽和写入寿命。

尾延迟还受 GC、读干扰（read disturb）、磨损均衡、掉电保护、预留空间（OP）和温度影响。用消费级盘承载企业随机写时，实测尾延迟和稳态 IOPS。

1.3 NVMe 与 NVMe-oF：队列和网络

NVMe 用多对提交和完成队列、doorbell 与轮询减少协议开销。可为每个 CPU 核分配一对队列。4 KiB 随机读可达几十万到百万 IOPS，延迟为几十到几百微秒。

NVMe-oF 通过网络传输存储命令。

传输 特点 主要风险
NVMe/TCP 通用、易部署 CPU 开销、TCP 重传、拥塞
RoCEv2 低延迟、RDMA PFC/ECN 配置、丢包、拥塞
FC-NVMe 复用 FC 织物 成本、 zoning/LUN 兼容
NVMe over Fabrics 统一语义 多路径、命名空间、拥塞

RoCE 用 PFC（优先级流控）以及 ECN 控制拥塞。配置不当可能导致暂停帧扩散、队头阻塞或丢包重传。常态网络延迟可能只有几十微秒，拥塞时尾延迟可达毫秒级。

1.4 控制器与缓存

一次请求经过以下控制器部件。

前端端口 → 协议处理 → 缓存（读/写）→ 后端总线 → 磁盘/SSD
                │
             NVRAM / BBU / 超级电容（掉电保护）
  • 写缓存。写回模式在缓存镜像完成后应答主机，再异步下刷（destage）到介质。它依赖掉电保护。缓存降级或电池失效时，系统可能切到写穿，延迟会升高。
  • 读缓存。命中时可降低延迟。预取有利于顺序读，随机读预取过多会挤掉常用缓存。
  • 缓存命中率。按 hit / (hit + miss) 计算。还要检查未命中的代价，以及预取或冷数据是否挤占缓存。
  • CPU/ASIC。压缩、去重、EC、快照、克隆和复制都消耗控制器资源。CPU 饱和时，多个 LUN 可能同时变慢。
  • QoS。按租户、卷或卷组限制 IOPS、带宽和时延，减少相互影响。限流本身也会引入排队。

控制器 CPU 和前端端口利用率都高、磁盘利用率却低时，先查控制器软件、压缩或快照等工作。磁盘利用率高而控制器 CPU 低时，先查后端队列和介质。

1.5 介质故障与预测的物理边界

  • AFR（年化故障率）。企业盘约 0.5%–2%，随型号、批次和工况变化。
  • UBER（不可恢复读错误率）。可用来估算重建时遇到读错误的概率。大盘需要读更多数据，重建通常更久，遇错的风险也更高。
  • 浴盆曲线。故障可分为早期失效、随机失效和磨损失效。预测模型很难同时覆盖三个阶段。
  • SMART 的局限。有些故障缺乏明显前兆。厂商的属性 ID 可能不同，采样频率可能较低，运维策略也会影响故障标签。

DME 白皮书披露了 14 天硬盘健康度预测和 30 天 SAS HDD 故障预测。评估实际效果仍需 PR 曲线、概率校准和各型号的表现，这些材料未公开。

2. 数据保护数学：RAID、EC、快照、复制与备份

2.1 RAID 与纠删码：可用容量、写惩罚与重建

假设各盘容量相同，比较可用容量、容错和写入开销。

方案 可用容量（N 块盘，每块 C） 容错 部分条带写惩罚 重建读
RAID 0 N×C 0 1 不适用
RAID 1 / 10 N×C/2 1（每镜像对） 2 1 份
RAID 5 (N−1)×C 1 4 N−1 份
RAID 6 (N−2)×C 2 6 N−2 份
EC k+m N×C×k/(k+m) m 约 2(m+1)（单块部分写，全条带写可避免） k 份
3 副本 N×C/3 2 3 1 份

部分条带写会增加 I/O。RAID 5 要读旧数据、读旧校验、写新数据、写新校验，共 4 个 I/O。RAID 6 有两份校验，约 6 个 I/O。执行 RAID 或 EC 全条带写时，直接写新数据和校验即可。小随机写多时，估算 RAID 6 或 EC 增加的 I/O 成本，再比较节省的容量。

例如，12 块 20 TB 盘的原始容量为 240 TB。

RAID 6：可用 10 × 20 = 200 TB（83.3%）
EC 8+2：可用 240 × 8/10 = 192 TB（80%）
3 副本：可用 240 / 3 = 80 TB（33.3%）

用已用容量 U 和重建速率 R 估算重建时间。

T_rebuild = U / R
20 TB / 200 MB/s = 100,000 s ≈ 27.8 h
20 TB / 100 MB/s = 200,000 s ≈ 55.6 h
20 TB / 50 MB/s  = 400,000 s ≈ 111.1 h

可用“年化故障率 × 重建窗口”粗估重建期间另一块盘故障的概率。以下假设 AFR = 2%，重建需 27.8 h。

单盘在窗口内故障概率 = 0.02 × 27.8 / (365×24) ≈ 6.4×10⁻⁵
RAID 6 剩余 11 块盘中再坏一块 ≈ 11 × 6.4×10⁻⁵ ≈ 7.0×10⁻⁴（0.07%）

单次重建期间再坏一块盘的概率较低。管理 1,000 个阵列且每年多次重建时，还要估算累计风险。重建压力也可能让实际故障率高于平时的 AFR。盘大、负载高或重建慢时，特别要核对重建需要多久。

2.2 快照与克隆：空间、一致性与删除代价

快照保留旧数据块的引用。常见实现有 COW 和 ROW。

  • COW（Copy-on-Write）。覆盖旧块前先复制到快照区。读旧快照时读这份副本。写路径多一次复制，快照随旧块被覆盖而占用更多空间。
  • ROW（Redirect-on-Write）。更新写到新位置，快照继续指向旧块。写路径省去复制，代价是映射更复杂，删除快照可能需要回收大量块。

按每日变化量和保留期估算快照空间。

快照空间 ≈ 数据量 × 每日变化率 × 保留天数 × 共享折扣

10 TB 卷每天变化 20%，保留 7 天，最坏占用 14 TB。块共享和未变化块会降低实际占用。容量规划为快照和克隆预留 20%–30%，并按业务变化率复核。

安排快照或克隆时，按恢复要求选择一致性方式，并确认克隆依赖。

  • 崩溃一致。快照对应突然断电时可见的持久状态。恢复后可能要跑 fsck 或重放日志。
  • 应用一致。先让数据库或文件系统暂停写入并落盘（quiesce），再打快照。可用 VSS、agent 或脚本配合。
  • 克隆。完整克隆复制数据，链接克隆共享块。删除或分裂链接克隆前，检查依赖链。

2.3 复制与双活：RPO/RTO 与带宽

模式 数据能恢复到何时 写延迟 距离 风险
同步复制 已确认的写入都在远端持久化时，可做到零数据丢失 受两端写入及往返延迟影响 受 RTT 限制，常见于同城 远端慢会拖慢本地，链路断开时看复制策略
异步复制 复制滞后可用来估计，最终以目标站通过校验的恢复点为准 通常先确认本地写入 可跨城 链路拥堵或复制积压会拉长数据缺口
双活/Active-Active 同步且两端都已持久化的写入可做到零丢失 取决于写入路径和仲裁 同步双活要求站点间低延迟 脑裂、仲裁、跨站一致性
快照复制 取决于故障前最后一份已传到目标站并通过校验的快照 通常无需等待快照传输 可跨城 快照漏做、传输积压或恢复校验失败都会拉长数据缺口

RPO 是业务允许丢失的最长时间。演练时，用业务中断时点减去目标站最后一个通过校验的恢复点，再与 RPO 比较。如果同步复制失联后允许源站继续写入，失联期间要单独核算可能丢失的数据。 AWS 灾备目标定义 · ONTAP 同步复制策略

按写入速率和块大小估算同步复制带宽。

带宽 ≈ 写吞吐 × (1 + 协议/快照开销)
例：10,000 IOPS × 8 KiB × 30% 写比例 = 24 MB/s

RTT 为 2 ms 时，同步写至少增加 2 ms，无法满足 1 ms 的写入 SLO。双活还要设计仲裁站点、quorum、脑裂（split-brain）策略和跨站锁。

2.4 备份、归档与防勒索

  • 独立备份。同一阵列、同一管理员域内的快照可能和原数据一起被误删，或一起受勒索软件影响。
  • 3-2-1。保留 3 份数据，使用 2 种介质，至少 1 份离线或异地。补充要求是保留 1 份不可变副本，并在恢复验证中达到 0 错误。
  • 不可变或隔离副本。对象锁、WORM、离线副本和 AirGap 用来防止删除或加密。读权限另行控制。
  • 恢复验证。定期恢复样本并记录 RTO 和校验结果。
  • 勒索检测。观察扩展名、异常 I/O、文件熵和快照元数据。发现异常后，先保护快照，再隔离和恢复。

3. 协议与网络：把延迟拆到每一跳

3.1 FC：WWN、Zoning 与 LUN Masking

FC 交换机和阵列分别控制连通性和卷访问权。

  • WWN 是标识。WWPN 标识端口，WWNN 标识节点。
  • Zoning 由交换机决定哪些端口能互相发现和通信。
  • LUN Masking 由阵列决定哪个主机 HBA 能访问哪个 LUN。

只配 Zoning 时，主机仍看不到未映射的 LUN。只配 LUN Masking 时，主机可能无法通过交换机访问目标。

排查 FC 时还要看登录、拓扑通知和缓冲区信用。

  • FLOGI/PLOGI 分别用于登录 fabric 和目标端口。大量端口同时登录可能造成拥塞。
  • RSCN 通知 fabric 拓扑变化。大规模变更可能触发主机重扫。
  • NPIV 让一个物理 HBA 端口使用多个 WWPN，支持虚拟化和多租户。
  • BB Credit 表示端口缓冲区信用。信用耗尽时，发送会暂停，可能表现为间歇性延迟或超时。

FC 的端到端延迟通常很低（几十到几百微秒），但拥塞、信用耗尽、错误重传、zone 变更会让尾延迟突然变长。

3.2 iSCSI：TCP 上的块协议

iSCSI 用 TCP 传输 SCSI 命令。

  • 通常用 CHAP 认证，用 MPIO（DM-Multipath）管理多路径。
  • 依赖 TCP 重传和拥塞控制。丢包后的重传可能增加毫秒到秒级的延迟。
  • TOE 或网卡卸载可减少 CPU 开销。性能不一致时，核对各主机的卸载配置。
  • 与 FC 相比，iSCSI 更易部署、成本低，但延迟抖动和 CPU 开销更高。

诊断 iSCSI 尾延迟时，还要查网卡队列、丢包、TCP 重传、交换机端口错包、MTU、巨帧配置和多路径策略。

3.3 NVMe-oF：队列、拥塞与无损网络

NVMe-oF 常用三种网络传输。

传输 优势 关键配置/风险
NVMe/TCP 通用、无需 RDMA CPU 开销、TCP 重传、拥塞窗口
RoCEv2 低延迟、低 CPU PFC/ECN、无损配置、丢包敏感
FC-NVMe 复用 FC 运维体系 兼容性、zoning、成本

PFC 按优先级暂停上游发送，ECN 标记拥塞，让发送端降速。检查以下配置问题。

  • PFC 暂停帧扩散会导致队头阻塞，整个端口可能停发。
  • ECN 阈值过高可能因降速太晚而丢包，过低会浪费带宽。
  • 多路径哈希不均时，可能一条链路拥塞，其他链路空闲。

3.4 NAS：元数据、锁与租约

NFS

  • NFSv3 无状态，文件锁依赖锁管理器（NLM）。客户端缓存和属性超时会影响观测到的延迟。
  • NFSv4.1 支持会话、租约和 delegation。客户端可以本地缓存或延迟写，并在故障恢复时重放。
  • pNFS 将数据路径分到多个 DS，元数据仍在 MDS。布局（layout）和客户端并行度会影响吞吐。

SMB

  • SMB3 支持 oplock/lease、持久句柄、多通道和加密。租约允许客户端缓存读写，减少往返。
  • 目录热点、锁竞争、签名/加密 CPU 开销会拖慢元数据操作。

分别为元数据延迟、数据延迟、元数据 IOPS 和数据带宽设置目标。遇到慢 readdir 和慢 1 MiB 顺序读，分别检查元数据路径和数据路径。

3.5 S3：一致性、分片与重试

  • Amazon S3 为新建、覆盖和删除提供强一致性。使用兼容实现或网关时，查具体产品文档。
  • Multipart。Amazon S3 对象上限约 48.8 TiB。每次上传最多 10,000 个 part，每个为 5 MiB–5 GiB，最后一个 part 无最小值。十进制 1 TB 对象用固定大小分片时，每个至少 100 MB。兼容 S3 的其他实现要查各自规格。Amazon S3 multipart 限额
  • LIST 按前缀分页，大桶和热前缀可能增加延迟。实时统计应使用专门的指标。
  • 遇到 5xx 或 SlowDown，用指数退避和抖动，并限制重试次数。
  • 网关的认证、限流、桶索引和 EC 编码都可能成为瓶颈。对象 SLO 按 GET/PUT/LIST、状态码和对象大小分别统计。

4. 文件、对象与 Ceph 内部：命名空间和数据放置

4.1 文件系统：MDS、目录与锁

分布式文件系统通常把元数据和文件内容分开存放。

客户端 → MDS（目录、inode、权限、锁、布局）→ 元数据池
客户端 → OSD/DS（实际数据块）→ 数据池

客户端和服务端通过缓存、租约和锁协调访问。

  • inode/dentry 缓存。客户端缓存属性和目录项，减少往返。用租约和回调保证一致性。
  • 锁。读写锁、范围锁和委托控制访问。并发写同一文件或目录可能争锁。
  • delegation/lease。服务端委托部分权限，让客户端本地缓存。故障恢复时要收回。
  • 目录分片和子树分区。把大目录分给多个 MDS，可减轻热点。跨分片的 rename 和 readdir 开销会增加。
  • 热点目录。大量小文件 create/unlink 可能先占满元数据池或 MDS CPU，数据盘仍很空闲。

写入 1 万个 4 KiB 文件，数据量只有约 40 MiB，却可能触发几万次元数据 RPC、加锁和日志写入。为元数据操作延迟（metadata ops latency）单独设置 SLO。

4.2 对象存储：桶索引、分片与 GC

对象存储通过桶索引定位对象。

bucket → 对象键 → 桶索引（分片）→ 对象元数据 → 数据块/EC 条带
  • 桶索引分片。大桶或并发读写相同前缀可能让某个分片过载。使用会按前缀集中分片的实现时，避免全用时间戳等单调前缀。
  • multipart。客户端逐片上传，完成时提交分片编号和 ETag。也可中止上传。未完成的分片会占空间，用生命周期规则清理。
  • EC 池。对象按条带编码到多个 OSD。小对象可能合并或内联，大对象按条带切分。
  • GC。删除对象后异步回收空间。集中删除可能让后台 GC 抢占前台资源。
  • 一致性。许多对象存储提供强一致性。网关缓存和跨区域复制仍可能有延迟。分别衡量本地读和跨区读的 SLO。

4.3 Ceph：CRUSH、PG 与恢复

Ceph 先把对象映射到 PG，再由 CRUSH 选择 OSD。

object → hash(object_name) → PG ID → CRUSH(pgid, cluster map) → OSD 集合
  • CRUSH 使用确定性的伪随机算法。输入和 map 相同，就得到同一组 OSD。可配置 host、rack、row、site 等故障域和权重。
  • PG 是放置和复制的单位。PG 太少时数据可能放得不均，太多会增加 peering 和内存开销。
  • PG 数估算。以下按每 OSD 约 100 个 PG 的经验值计算。
pg_num ≈ (OSD 数 × 每 OSD 目标 PG 数) / 副本数
例：100 OSD × 100 / 3 ≈ 3,333 → 取 2 的幂 4,096

4,096 个 PG、3 副本时，每 OSD 平均承载 4096×3/100 ≈ 123 个 PG，略高于 100。也可选 2,048 个 PG，每 OSD 约 61 个。实际用 pg_autoscaler 调整，再复核容量和负载。

  • Peering。PG 的主 OSD 与其他 OSD 协商数据版本，确认哪份数据有效。期间 PG 可能处于 peering 或 inactive，暂时无法服务。
  • Recovery/Backfill。恢复缺失副本。新 OSD 或重映射时用 backfill，需扫描整个 PG。两者都消耗网络、磁盘和 CPU。
  • Scrub。轻量 scrub 检查元数据，deep-scrub 还检查数据校验和。发现不一致时，可按故障情况执行 repair。
  • BlueStore。直接管理块设备，用 RocksDB 保存元数据，并为数据加校验和。省去本地文件系统层，可减少双写。
  • mClock。按客户端、后台 recovery 和后台 best-effort 分配 reservation、limit 和 weight。scrub 属于后台 best-effort。调参前查版本和 osd_op_queue 模式。
  • Map epoch。保存调查时看到的 osdmap、pgmap 和 CRUSH map 版本，便于复现当时的放置。

根据 PG 状态决定先查什么。

状态 含义 下一步
active+clean 可服务，对象已达到配置副本数 仍需查看其他健康项和 scrub 结果
active+degraded 可服务但副本不足 看 down/out OSD、恢复进度
active+undersized acting 集合小于期望 看 CRUSH、可用 OSD
undersized+degraded+peered 已完成 peering，但可用副本未达到 min_size，当前不能处理客户端 I/O 检查 min_size、可用副本与恢复进度
inactive 不能服务 看 peering 卡住、unfound objects
stale PG 映射变更后，Monitor 尚未收到该 PG 的状态更新 看主 OSD 状态及其到 Monitor 的通信
down 持有必要数据的副本不可用，PG 离线 查所需副本、OSD 与 PG 状态

先查 ceph health detail，再查 ceph osd tree、ceph pg dump_stuck 和 ceph pg <pgid> query。核对 up/acting、peering、unfound 和 scrub 错误，再查主机、网络和磁盘。

4.4 故障域：为什么“副本数”不等于“可靠性”

3 个副本全在同一机柜时，机柜断电会让副本同时不可用。EC 8+2 的 10 个块分布在 5 个 host 时，坏 2 个 host 可能丢数据。计算时要看每个故障域内放了多少块。

副本/校验数 × 故障域隔离 × 重建速度 × 静默错误检测

CRUSH rule 要显式指定 failure domain（host/rack/row/site），EC 还要考虑 crush-failure-domain。跨站点时还要考虑仲裁、延迟和脑裂。

5. 性能与容量建模：从指标到决策

5.1 USE 与 RED：先定位资源，再谈异常

  • USE（Utilization、Saturation、Errors）用于资源排查。对 CPU、内存、网络、磁盘、控制器和队列分别观察利用率、饱和度和错误。
  • RED（Rate、Errors、Duration）用于服务排查。根据请求速率、错误和持续时间判断端到端 SLO。

先按下表检查各类资源。

资源 Utilization Saturation Errors
CPU 使用率 run queue/steal MCE/温度
内存 使用率 swap/回收 OOM
网络 带宽/端口 队列/暂停帧/重传 CRC/丢包
磁盘 利用率/IOPS 队列深度/await 介质错误
控制器 CPU/缓存 队列/脏页 降级/电池

利用率高、队列仍短、延迟稳定时，可能只是负载高。利用率低而延迟高时，检查锁、重传、GC、后台任务或上游限流。

5.2 Little 定律、排队与 USL

用 Little 定律根据吞吐和延迟估算在途请求数。

L = λ × W
并发数 = 吞吐 × 延迟

50,000 IOPS × 0.5 ms 得到 25 个在途请求。20,000 IOPS × 2 ms 反而有 40 个。队列变长时，同时查请求速率和服务时间。

M/M/1 说明利用率接近 100% 时，响应时间会加速上升。

R = S / (1 − ρ)
ρ=80% → 5×S；ρ=90% → 10×S；ρ=95% → 20×S

用 USL（Universal Scalability Law）估算增加 CPU 核或节点时，吞吐如何变化。

X(N) = N / (1 + α(N−1) + βN(N−1))
  • α 表示争用导致的串行等待。
  • β 表示为保持一致性或同步缓存付出的开销，可能让吞吐随规模扩大而下降（retrograde）。

例如，α=0.1，β=0.01。

N=1: 1
N=8: 8 / (1 + 0.7 + 0.56) = 3.54（效率 44%）
N=16: 16 / (1 + 1.5 + 2.4) = 3.27（效率 20%，已回退）

共享锁、元数据服务、一致性协议和网络都可能限制扩展。扩容前，用实测数据估计 USL 参数，检查增加节点能带来多少吞吐。

5.3 IOPS、带宽、缓存与混合负载

带宽 = Σ (IOPS_i × 块大小_i)
平均延迟 = 命中率 × 命中延迟 + (1 − 命中率) × 未命中延迟

例如，总计 100,000 IOPS，其中 70% 为 4 KiB 读、30% 为 8 KiB 写。

读带宽 = 70,000 × 4 KiB = 286.7 MB/s
写带宽 = 30,000 × 8 KiB = 245.8 MB/s
合计 ≈ 532.5 MB/s

RAID 6 的部分条带写、SSD 的 GC 和 EC 的条带更新都会增加介质写入量。规划带宽时，将写惩罚和 WA 计入。

例如，缓存命中率为 90%，命中耗时 0.1 ms，未命中耗时 4 ms。

0.9 × 0.1 + 0.1 × 4 = 0.49 ms
命中率 70%：0.7 × 0.1 + 0.3 × 4 = 1.27 ms

命中率从 90% 降到 70% 时，平均延迟约为原来的 2.6 倍。尾延迟要单独测。调缓存时同时检查命中率、冷数据挤占、预取和写回策略。

5.4 容量、TCO 与扩容窗口

从原始容量算出冗余后容量，再减去单列的固定占用。扣一次预留后得到可分配容量，乘告警比例得出告警线。快照等占用若已计入已用容量，就保留在已用容量中。若已从总容量扣除，就从拿来比较的已用容量中排除，确保同一项只计一次。

冗余后容量 = raw × RAID / EC / 副本方案的容量效率
扣固定占用后容量 = 冗余后容量 − 该口径下单列的固定占用
可分配容量 = 扣固定占用后容量 × (1 − 预留比例)
告警线 = 可分配容量 × 告警比例

例如，100 个节点，每节点 12 块 20 TB 盘，合计 24,000 TB raw。EC 8+3 的效率为 8/11，约 72.7%。算例无另列固定占用，先扣 10% 预留，再用可分配容量的 90% 告警。

冗余后容量 = 24,000 × 8/11 ≈ 17,455 TB
扣 10% 预留后，可分配容量约 15,709 TB
当前已用 12,000 TB；90% 告警线 = 14,138 TB
剩余可增长 = 2,138 TB；50 TB/天 → 42.8 天

从预计触线的日子往前算，给采购、上架、布线、初始化和数据重平衡留出时间。再按失去一个故障域的情景复算 N+1 余量和重建空间，同时考虑快照和克隆的增长及业务峰值。若现有预留已经覆盖这种故障，核对预留是否足够，只扣一次。

算 TCO 时，计入介质、控制器、机柜、电力、制冷、网络、软件许可、维保、人力、迁移和停机。比较每 TB 单价时也要比较这些成本。

5.5 SLO 与容量/性能的联动

  • 用同一时间窗和测量点对照 SLO 和容量数据。先确认允许的延迟和错误率，再估算现有容量还能支撑多久。
  • 错误预算即将用尽时，可扩容或优化以减轻影响。如果代码、配置或热点才是根因，还要修正它们。
  • 容量告警同时报告预计到阈值的时间、置信区间和假设，包括增长率和业务变化。

容量水位等硬边界用规则监控。对同组实体建立稳健基线，用变化点识别持续偏移，再按异常持续时间和业务可感知的幅度判断是否告警。多指标联动或周期复杂时，再用机器学习模型补充检测。

6.2 生存分析：硬盘预测的正确统计语言

生存分析估计一块盘在不同时间点发生故障的风险。

  • 删失（censoring）。观测结束、主动更换或迁移时，若后续故障时间未知，按删失或竞争事件处理。
  • 竞争风险。区分真实故障、主动退役和迁移，分别建模。
  • 时变特征。SMART 每天变化。每条样本只用当时可见的特征。
  • Kaplan-Meier。估计生存曲线，无需指定整体分布。
  • Cox 比例风险。估计特征对风险的影响，并检验比例风险假设。
  • 校准。预测风险为 10% 的盘，实际故障率也应接近 10%。检查 PR-AUC 和校准曲线。

也可按未来 H 天是否故障做二分类。构建样本时，避免同一块盘跨训练集和测试集，避免用到未来数据，记录运维干预。

6.3 因果推断：存储里的“自然实验”

维护、限速和分批升级可提供对照条件。

  • 维护一个 OSD 时，观察同 PG 的前台延迟。
  • 限制 backfill 速率后，观察 P99 是否下降。
  • 分批升级时，比较已升级和未升级集群。
  • 用同一集群里不同的池或租户作对照。
  • 比较变更前后时，可用中断时间序列（ITS）或差异中的差异（DiD）。

先画因果图（DAG）。业务峰值同时推高 IOPS 和延迟，是两者的共同原因。两个原因指向同一个告警时，告警是两条箭头汇合的对撞点。维护经由 backfill 影响延迟，backfill 就是中介。用后门准则或 do-calculus 判断估计因果关系时该控制哪些变量。

例如，估算 backfill 对延迟的影响时，若 backfill 也影响 IOPS，控制 IOPS 可能挡住一部分因果路径。先画 DAG，再决定调整哪些变量。

6.4 贝叶斯网络与故障树

故障树用 AND 或 OR 表示多个原因需要同时发生还是任一即可。贝叶斯网络用条件概率来推断可能的原因。

P(根因 | 证据) ∝ P(证据 | 根因) × P(根因)

多个原因可各自触发告警时，可用 Noisy-OR 建模。

P(告警 | 原因集合) = 1 − Π(1 − p_i)

产品故障树通常由专家维护确定性规则。贝叶斯网络需要历史数据或专家先验，还要校准概率。可以用故障树找候选，再用贝叶斯或统计方法排序。

6.5 图算法：影响范围、路径与中心性

  • BFS/DFS。沿依赖边查可能受影响的实体。用 BFS 找最少跳数。
  • 最短路径。检查两个实体之间是否有路径，可用延迟或带宽作为边的权重。
  • 连通分量。沿故障域关系找相连的实体。
  • 中心性（度/介数/接近）。识别关键交换机、控制器和共享池。
  • 社区发现。按拓扑找联系较紧的实体，再核对业务和故障域边界。
  • 时态图。为边保存有效期，查事故时使用事发时间切片。

6.6 优化：放置、容量与 QoS

优化目标和约束随任务变化。

  • 放置和装箱。把卷或租户分配给池或控制器，同时满足容量、性能、故障域、亲和和反亲和约束。小规模可用 ILP 或 CP-SAT，大规模可用贪心或启发式方法。
  • QoS 分配。在租户间分配 IOPS 和带宽，尽量满足 SLO 并留安全余量。可用排队论或优化方法。
  • 扩容和迁移。尽量减少停机、迁移量和成本。兼顾性能、成本和风险时，可加权或比较 Pareto 前沿。
  • 备份窗口。按 RPO、RTO 和业务低峰安排备份时间。

方案要便于审批、执行、回滚和验收。给出优化结果时，附上所用约束和取舍。

6.7 LLM Agent：规划、工具与验证

Agent 的调查循环由模型规划、工具执行、证据和验证组成。

状态 → 计划 → 工具调用 → 观察 → 证据 → 判断是否足够 → 报告/停止

上线前明确以下约束。

  • 预算。限制步数、运行时间、token 和查询行数，避免后端过载。
  • 工具契约。约定输入输出 schema、时间口径、权限、错误类型和证据 ID。
  • 验证器。在模型外检查引用、单位、数值、时间截止、权限和 schema。
  • 记忆。工作记忆保存当前事故。长期记忆保存 Runbook 和历史工单，并按版本和 ACL 管理。
  • 复核假设。让模型主动列出反证和其他可能原因。
  • 评测。统计任务成功率、证据正确率、工具成本、越权拒绝、缺数据暂缓和轨迹可复现性。

ReAct 和 Plan-and-Execute 都可编排调查。无论用哪种，先验收工具输出和验证器。

第一版可用 PostgreSQL 存资产和拓扑，用时序库存指标，用对象存储保存证据。

-- 实体：稳定身份 + 别名 + 生命周期
CREATE TABLE entity (
  entity_id    TEXT PRIMARY KEY,          -- tenant/cluster/type/uuid
  tenant_id    TEXT NOT NULL,
  cluster_id   TEXT,
  entity_type  TEXT NOT NULL,             -- host/switch/array/pool/lun/fs/osd/disk
  native_uuid  TEXT,
  display_name TEXT,

  alias_value TEXT NOT NULL,
  valid_from TIMESTAMPTZ NOT NULL,
  valid_to   TIMESTAMPTZ,
  PRIMARY KEY (entity_id, alias_type, alias_value, valid_from)

-- 时态边：保留有效时间和每次修订的知识时间
CREATE TABLE edge (
  src_id      TEXT NOT NULL,
  dst_id      TEXT NOT NULL,
  relation    TEXT NOT NULL,              -- runs_on/maps_to/replicates_to/depends_on
  valid_from  TIMESTAMPTZ NOT NULL,
  valid_to    TIMESTAMPTZ,
  observed_at TIMESTAMPTZ NOT NULL,
  known_from  TIMESTAMPTZ NOT NULL,
  known_to    TIMESTAMPTZ,
  source      TEXT NOT NULL,
  confidence  REAL NOT NULL DEFAULT 1.0,
  attrs       JSONB NOT NULL DEFAULT '{}',
  CHECK (valid_to IS NULL OR valid_from < valid_to),
  CHECK (known_to IS NULL OR known_from < known_to),
  PRIMARY KEY (src_id, dst_id, relation, valid_from, source, known_from)
);

CREATE INDEX edge_src_time ON edge (src_id, valid_from, valid_to);
CREATE INDEX edge_dst_time ON edge (dst_id, valid_from, valid_to);

-- 事件：source_id 由接入服务从已登记来源设置
CREATE TABLE event (
  source_id    TEXT NOT NULL,
  event_id     TEXT NOT NULL,
  event_type   TEXT NOT NULL,             -- change/alert/deploy/maintenance
  entity_id    TEXT NOT NULL REFERENCES entity(entity_id),
  event_time   TIMESTAMPTZ NOT NULL,
  observed_at  TIMESTAMPTZ NOT NULL,
  available_at TIMESTAMPTZ NOT NULL,
  source_ref   TEXT,
  payload      JSONB NOT NULL,
  PRIMARY KEY (source_id, event_id)
);

-- 证据对象：不可变引用
CREATE TABLE evidence (
  evidence_id TEXT PRIMARY KEY,
  incident_id TEXT,
  query_id    TEXT NOT NULL,
  source_id    TEXT NOT NULL,
  entity_id    TEXT NOT NULL REFERENCES entity(entity_id),
  window_start TIMESTAMPTZ,
  window_end   TIMESTAMPTZ,

建表和写入时遵守以下约束。

  • entity_id 使用稳定 ID，名称和别名另存表。
  • observed_at 记录来源何时看到关系。known_from/known_to 记录调查者何时能查到这一版。补录或纠正时，在同一事务中设置旧版的 known_to，再插入新版。旧版的 valid_from/valid_to 原样保留。例如 02:20 才得知某条边在 02:10 结束，旧版保留原先没有终点的有效区间，新版的 valid_to 为 02:10，known_from 为 02:20。撤销关系时结束旧版的知识区间，按需记录撤销事件。同一来源对同一条关系的写入要逐次处理。查询时同时匹配两个半开区间（含起点，排除终点）。
  • event_time 记录事件发生的时间。observed_at 记录采集端看到它的时间。正文和索引都可用后，接入服务正式发布，并用 available_at 记录首次可查时间。补录保留原发生时间和观测时间，available_at 填补录记录实际发布的时间。
  • 每个来源使用接入时登记的稳定 source_id。同一来源重传同一事件时用 ON CONFLICT (source_id, event_id) DO NOTHING 避免新增记录，保留首次可查时间。若来源会复用事件编号，先用能够区分来源重置前后的代次，或用稳定的原生版本区分记录。相同键对应不同内容时，记录冲突并查证。证据只追加。需要删除时添加墓碑标记（tombstone）并记审计。
  • 时间统一存 UTC，展示时转换为本地时区。

7.2 as-of 查询

回放时，网关固定调查截止时间和快照，重查当前权限，再传入获准的来源与实体组合、时间窗和预算。生产快照只包含当时已经提交并发布的批次或不可变记录清单。

available_at 用于筛选快照里已经可查的记录。一个事务可能在 02:15 开始，到 02:17 才提交。可查时间要以正式发布为准。这条记录在 02:16 尚不可查，后来提交也不能加入旧快照。

下列 PostgreSQL 示例从已经限定在快照内的底表读取，演示如何按可查时间和权限筛选。接入实际列表时，还要按事件时间或证据窗口限制范围，并按固定顺序分页。$1 和 $2 是来源与实体数组，同一位置组成一个获准的来源与实体组合。$3 是服务端设置的 knowledge_cutoff。

WITH allowed AS (
  SELECT source_id, entity_id
  FROM unnest($1::text[], $2::text[]) AS scope(source_id, entity_id)
),
candidates AS (
  SELECT 'event' AS kind, event_id AS record_id, source_id, entity_id, observed_at, available_at
  FROM event
  UNION ALL
  SELECT 'evidence', evidence_id, source_id, entity_id, observed_at, available_at
  FROM evidence
)
SELECT c.kind, c.record_id, c.source_id, c.observed_at, c.available_at
FROM candidates c
WHERE c.available_at <= $3::timestamptz
  AND EXISTS (
    SELECT 1 FROM allowed a
    WHERE a.source_id = c.source_id AND a.entity_id = c.entity_id
  )
ORDER BY c.available_at, c.kind, c.source_id, c.record_id;

先测去重。两个来源各报一条 E01，应保留两条。重放其中一个来源的 E01，行数仍为两条。

再测晚到记录。一条记录在 02:12 被观测到，02:18 才能查，从 02:16 冻结的快照查不到。另开调查，选择 02:18 已发布的快照和新的截止时间，权限相同时应能查到。取消该来源的访问权限后，新快照也不应返回这条记录。恢复原授权再重跑 02:16 的查询，验证旧快照本身就没有收录这条记录。

查拓扑时，用事发时点匹配有效区间，用同一个调查截止时间匹配知识区间。边的 source 是登记的可信来源 ID。下面用 PostgreSQL 的 tstzrange 表示这两个区间。网关只让查询使用两端实体都获准从该来源访问的边。示例用固定教学数据，生产查询须读取选定的发布版本，或在查询里按发布版本过滤。

CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE edge ADD COLUMN valid_range TSTZRANGE
  GENERATED ALWAYS AS (tstzrange(valid_from, valid_to, '[)')) STORED;
ALTER TABLE edge ADD COLUMN knowledge_range TSTZRANGE
  GENERATED ALWAYS AS (tstzrange(known_from, known_to, '[)')) STORED;
CREATE INDEX edge_range_gist ON edge USING GIST (src_id, relation, valid_range, knowledge_range);

CREATE FUNCTION scoped_topology_edges(
  allowed_sources TEXT[], allowed_entities TEXT[],
  valid_at TIMESTAMPTZ, knowledge_cutoff TIMESTAMPTZ
)
RETURNS SETOF edge
LANGUAGE sql STABLE
AS $$
  WITH allowed AS (
    SELECT source_id, entity_id
    FROM unnest(allowed_sources, allowed_entities) AS scope(source_id, entity_id)
  )
  SELECT e.*
  FROM edge e
  WHERE e.valid_range @> valid_at
    AND e.knowledge_range @> knowledge_cutoff
    AND EXISTS (
      SELECT 1 FROM allowed a
      WHERE a.source_id = e.source AND a.entity_id = e.src_id
    )
    AND EXISTS (
      SELECT 1 FROM allowed a
      WHERE a.source_id = e.source AND a.entity_id = e.dst_id
    );
$$;

下面两个查询沿边查下游。单跳查询依次传入配对的来源和实体数组、拓扑有效时点、知识截止时间和起点 ID。网关先校验设备和时间范围，再传入参数。生产工具还须检查关系类型和方向是否获准。

SELECT src_id, dst_id, relation, source, confidence
FROM scoped_topology_edges($1, $2, $3, $4)
WHERE src_id = $5
ORDER BY relation, dst_id;

多跳复用同一套授权后的边，并在第六个参数指定最大深度。起点须在授权实体中。

WITH RECURSIVE reach(entity_id, depth, path) AS (
  SELECT $5::text, 0, ARRAY[$5::text]
  WHERE $5::text = ANY($2::text[])
  UNION ALL
  SELECT e.dst_id, r.depth + 1, r.path || e.dst_id
  FROM reach r
  JOIN scoped_topology_edges($1, $2, $3, $4) e ON e.src_id = r.entity_id
  WHERE r.depth < $6::integer
    AND NOT e.dst_id = ANY(r.path)
)
SELECT entity_id, min(depth) AS depth
FROM reach
GROUP BY entity_id
ORDER BY depth, entity_id;

用一条跨租户路径验收。起点属于当前租户，下一跳是有权访问的卷，再下一跳只属于另一租户。单跳应只返回该卷。将深度设为 3，多跳也应在该卷停止，不能经过另一租户的实体继续查。再把一条边改为来自未授权的来源。即使有权查看两端实体，查询也应跳过这条边。

大图上的递归 CTE 可能很慢。生产查询要限制深度、边类型和租户范围。多跳开销过高时，可用图数据库或预计算结果。

7.3 PromQL：SLO、覆盖率和异常

先算成功且耗时 ≤20 ms 的好请求比例。

sum(rate(http_request_duration_seconds_bucket{le="0.02",code=~"2.."}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))

再算 99.9% SLO 的燃烧率。

(1 - (
  sum(rate(http_request_duration_seconds_bucket{le="0.02",code=~"2.."}[1h]))
  /
  sum(rate(http_request_duration_seconds_count[1h]))
)) / (1 - 0.999)

计算采集覆盖率时，从 CMDB 导出预期上报的 OSD，每个 OSD 的 expected_osd 为 1。osd_telemetry_fresh 表示指定窗口里目标指标是否有新数据。两者均以 (cluster, osd) 唯一标识。按集群统计。预期数为零时，无覆盖率。预期 OSD 全部停报时，覆盖率为 0。

(
  sum by (cluster) ((osd_telemetry_fresh == 1) and on (cluster, osd) (expected_osd == 1))
  or on (cluster) (0 * sum by (cluster) (expected_osd == 1))
)
/
(sum by (cluster) (expected_osd == 1) > 0)

up 表示已发现的目标是否抓取成功。用统一 exporter 时，仍要逐 OSD 检查数据是否新鲜。覆盖率的分母来自独立资产清单。Prometheus 抓取目标

以下用毫秒为单位计算异常分数。启用 --enable-feature=promql-experimental-functions 后，取截至 5 分钟前的一小时数据做基线。

0.6745 * (latency_ms - quantile_over_time(0.5, latency_ms[1h] offset 5m))
/
clamp_min(mad_over_time(latency_ms[1h] offset 5m), 1)

quantile_over_time(0.5, …) 计算中位数。未开启实验函数时，可离线或用流处理计算 MAD，再导出成指标。此例分母下限为 1 ms。换指标时，按单位和噪声重新设下限。PromQL 函数

  3. 每次查询生成 query_id，返回可引用的证据。各证据保留自己的 observed_at 和 available_at。历史回放读取已冻结的证据及其引用。

适配层统一字段和单位，再把响应交给模型。工具说明写清怎样获取下一页，以及各类错误该怎样处理。

7.5 Agent 循环与验证器

context = load_authorized_investigation(session, investigation_id)
state = init(symptom, context.window, context.budget)
for step in range(max_steps):
    if state.budget_exhausted():
        return undecided(state, reason="budget")
    plan = llm.plan(state, tools=available_tools(context))
    call = validate_schema(plan.tool_call)
    if not authorize(call, context):
        state.add_refusal(call)
        continue
    obs = execute_read(call, context=context, timeout=state.timeout)
    state.add_evidence(obs.evidence)
    if state.sufficient() or state.no_discriminating_query():
        break

report = llm.compose(state, schema=REPORT_SCHEMA)
errors = verify(report, state, context)
if errors:
    report = llm.repair(report, safe_feedback(errors), state)  # 有界重试
    errors = verify(report, state, context)
if errors:
    return undecided(state, reason="report_validation_failed")
return report

没有越权实体/租户
结论强度与覆盖率匹配（coverage 低 → 不得给高置信）
