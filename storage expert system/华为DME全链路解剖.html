三条读法建议：

  1. 不要把“博客愿景”当成“产品功能”。 博客讲因果推理、知识图谱、数字孪生、跨域 Agent；25.1.0 白皮书讲的是故障树、智能分析、故障智能体、运维助手。前者是方向，后者是可交付能力。
  2. 不要把“产品指标”当成“可复现指标”。 80% 日常运维一句话完成、5 倍效率、90% 故障周期缩短、1 分钟识别/3 分钟定界/5 分钟定位，都是厂商口径，缺少测试集、分母和误报率。
  3. 不要把“北向 REST”当成“Agent 工具生态”。 DME 有开放的 REST/SNMP/Ansible/CSI，但没有公开的 MCP 服务、工具 Schema 和 Agent 发现机制；接入通用 Agent 需要自建适配层。

1. 一句话结论与产品地图

iMaster DME 是部署在数据中心的基础设施与数据管理平台。 它统一管理适配的存储、网络、服务器及虚拟化等资源，提供监控、诊断、自动化、数据目录和防勒索。iMasterCloud DME IQ 是华为另行说明的云端智能运维平台，功能和部署范围以各自资料为准。DataMaster 是 DME 产品页披露的存储运维智能体。

它强在设备覆盖、故障树/专家规则、自动化编排、云地协同和真实设备数据；弱在开放工具契约、可核验评测、时态证据、业务 SLO、处置治理和跨域覆盖。后文逐项展开。

1.1 它不是什么

  • 不是开源项目。 没有公开源码、公开 Roadmap、公开 Issue 跟踪。
  • 不是通用 AIOps 平台。 它的对象是存储/交换机/主机/虚拟化/容器，不是任意业务应用；根因分析主要围绕存储 I/O 路径和华为设备故障树。
  • 不是 MCP 工具服务器。 公开材料没有 MCP；北向是 RESTful/SNMP/Ansible/CSI。
  • 不是数据湖计算引擎。 Catalog 做元数据目录、联邦检索、冷热分析，不做 Spark/Trino 那种计算。
  • 不是“无人值守”产品。 博客自己列了幻觉、权限围栏、爆炸半径、数字孪生、跨域协同五个挑战；白皮书的动作工作台也明确区分客户管理员与华为服务人员。

[白皮书] 披露的采集细节很关键：

  • 华为闪存性能采集 1 分钟，分布式 5 分钟（OceanStor 9000/以太网交换机 5 分钟，其他分布式 1 分钟），FC 交换机 1 分钟。

  • 配置库/历史库/Elasticsearch/OpenSearch 是内部组件，没有公开的客户侧原始数据导出接口。

2.3 这个架构意味着什么

[推断] 三点：

  1. DME 是“管理面聚合器”，不是“数据面探针”。 它擅长从设备管理接口取聚合指标，不擅长应用侧 eBPF/OTel 级别的请求追踪。业务 SLO 和客户端尾延迟需要另建。
  2. DME 的数据是“产品内闭环”的。 采集、存储、分析、展示都在 DME 内；客户很难把原始遥测拉到自己的数据湖做二次建模。这在多云/多厂商环境是限制。
  3. 开放的是“控制面 API”，不是“证据面 API”。 北向 REST 可以查资源、性能、告警，但公开材料没有给出查询 ID、数据快照 ID、时态拓扑、证据出处这类取证所需的契约。

3. 逐环节对照

下面九个环节与深入篇一一对应。每一节固定五段：DME 公开能力 → 机制 → 业界先进 → 缺口 → 练习。缺口分三档：

  • 高：直接影响专家系统的正确性/安全性/可验证性，建议自建。
  • 中：影响效率和覆盖，可先用适配层补。
  • 低：产品已覆盖，主要靠用对。

3.1 环节 0：领域本体与资源模型

DME 公开能力。 DME 的资源模型相当完整，覆盖设备全生命周期：

类别 对象
基础设施 数据中心、可用分区、机柜、存储设备、光纤交换机、以太网交换机、安全设备、服务器、备份介质/软件/一体机
虚拟化/容器 FusionCompute、VMware、OpenStack、容器平台/集群、全局命名空间、并行客户端（DPC）
存储资源 存储池、LUN、文件系统、Dtree、共享、服务等级、QoS、快照/克隆/复制/双活

[白皮书] 还说明：存储资源纳管每 6 小时同步；支持华为全系列和主流第三方存储；配置存储池仅支持华为闪存；免密跳转仅支持华为闪存/分布式。

机制。 资源模型是“配置库 + 历史库 + 搜索索引”的组合：配置库存当前属性，历史库存变更/性能，OpenSearch 存可搜索的资源和关系。白皮书明确全局搜索依赖 OpenSearch，返回对象的基本信息、资源关系、性能、健康、告警、异常检查结果。这是一个以设备为中心的 CMDB 模型，不是通用本体（ontology）。

业界先进。 [原理] OpenTelemetry 的 resource/service semantic conventions 提供跨厂商的实体和属性命名；ITIL/CMDB 提供配置项与关系；属性图/知识图谱（Neo4j、RDF/OWL）提供多跳和规则推理；Palantir 这类平台把“本体 + 动作 + 权限”做成可编排层。存储领域还缺一个被广泛采用的公开本体——这是行业空白，不是华为一家的问题。

缺口。

缺口 等级 说明
没有公开的存储本体/关系 Schema 中 资源模型在产品内，客户拿不到 OWL/RDF/属性图定义；跨厂商实体对齐困难
知识图谱有产品页/博客表述，但 25.1.0 白皮书未展开 中 产品页把“知识图谱”列为四大关键技术，[博客] 说“知识图谱 + 实时数据流”；但 [白皮书] 的智能分析仍是故障树/规则，公开材料没有给出图谱的 schema、规模、查询接口
没有“故障模式/症状/处置”的公开本体 高 Runbook、故障码、症状、动作没有公开的实体关系，难以做跨产品推理

练习（答案见答案册第 2 部分）。 把 DME 的资源对象翻译成一张属性图：节点、边、基数、时态字段；标出哪些字段有公开依据、哪些需要现场 API 探测。再写一条“从业务卷到物理盘”的多跳查询。

3.2 环节 1：请求路径与 SLO

DME 公开能力。 DME 的强项是设备侧 I/O 路径，不是应用侧端到端：

  • 端到端性能关联分析：按 I/O 路径自上而下对比对象指标；同一指标多对象同图；支持 1 小时/4 小时/12 小时/1 天/1 周/1 年/自定义粒度。
  • SAN 拓扑：从 FC 交换机取端口对端 WWN，匹配主机/存储 WWN；从华为存储取 HostLink 映射；物理连接 + 逻辑映射结合。
  • NAS 拓扑：从华为存储取 IO trace，展示客户端到文件系统的访问关系；A 系列还支持 DataTurbo 客户端、Scaleout 网络拓扑。
  • 容器拓扑：依赖华为 CSI Driver，展示 Node/App/Workload/Pod/PVC/PV/存储单元。
  • 智能分析：I/O 全路径时延分析、资源瓶颈、故障/亚健康/配置分析；A 系列可按并行客户端 → zone → 业务网络/Scaleout/存储 zone 的故障树逐层展开，识别“首错模块”；输出覆盖计算/网络/存储侧的报告。
  • 彩页口径：1 分钟识别、3 分钟定界、5 分钟辅助定位；秒级性能视图。

机制。 [推断] DME 的“端到端”边界是它纳管的网元：主机（通过 OS/虚拟化接口）、FC/IP 交换机、存储前端端口/控制器/池/LUN/文件系统。它能看到“主机到存储”的路径，但看不到应用进程内部的调用链；也没有公开的 OpenTelemetry/eBPF 接入。因此它回答的是“存储路径上哪一段慢”，不是“应用为什么慢”。

业界先进。 [原理] OpenTelemetry traces + eBPF（如 Pixie/Cilium）可以做到应用请求级跨组件追踪；SLO 平台（Sloth、Nobl9 等）用多窗口燃烧率管理错误预算；Pure1/Fusion 把工作负载、卷、阵列、设备群放进同一查询模型；AWS DevOps Agent 强调应用拓扑 + 变更时间线 + 跨源调查。

缺口。

缺口 等级 说明
没有公开的“业务 SLO/错误预算”对象 高 DME 的 SLA 是数据保护策略（OceanProtect），不是应用 SLO；没有好请求/分母/燃烧率模型
公开材料未见应用侧 OTel/分布式追踪接入 高 无法把应用 P99 与存储 I/O 路径自动关联；需自建埋点/追踪并对齐时间
客户端侧尾延迟/重试不可见 中 主机侧覆盖依赖 OS/虚拟化接口；第三方主机、容器 sidecar、数据库内部队列不在视野
非华为阵列的路径分解深度有限 中 智能分析的 I/O 路径/故障树主要面向华为闪存/A 系列；第三方设备以通用指标为主

练习（答案见答案册第 2 部分）。 用一次应用 P99 升高的事故，画两条时间线：应用侧（请求、重试、错误码）和 DME 侧（前端端口、控制器、池、LUN、磁盘）；标出哪一段能直接关联、哪一段只能靠时间对齐推断。

3.3 环节 2：采集、时序与海量成本

DME 公开能力。

  • 采集：REST（华为存储资源/性能）、SNMP Trap（告警）、SSH（端口光功率等少量指标）、CSI（容器）、虚拟化/容器平台 API；第三方存储按厂商接口。
  • 粒度：闪存 1 分钟、分布式 1/5 分钟、FC 1 分钟；实时 5 秒；5 秒历史按需从 Dorado V6+ 设备读，最长一周。

  • 规模：彩页写最大 175 套存储；多节点横向扩展；跨数据中心 < 50 ms/0.1% 丢包/100 Mbit/s。

机制。 [推断] DME 走的是“产品内时序库 + 预聚合 + 搜索索引”的路线，优先保证管理面查询和报表，不是“原始遥测湖”。这对运维够用，对二次分析不够：客户拿不到原始样本、桶边界、采集水位和查询 ID。

业界先进。 [原理] Prometheus/OTel + 对象存储的分层时序；Kafka 做采集缓冲；ClickHouse/专用 TSDB 做高基数聚合；原生直方图保留桶；OpenLineage 做数据血缘；DII 把“采集健康”作为一等查询对象；Pure1 做设备群遥测。

缺口。

缺口 等级 说明
没有公开的原始遥测导出/流式接口 高 无法自建数据湖、无法做客户侧长期回放和二次建模

3.4 环节 3：资产身份与时态拓扑

DME 公开能力。

  • 多厂商资源台账：华为/第三方存储、FC/IP 交换机、服务器、虚拟化、容器、备份、安全设备；支持模板批量接入、堡垒机接入、手工资产。
  • 拓扑：SAN（WWN + HostLink）、NAS（IO trace）、容器（CSI）；6 小时同步；全局搜索展示资源关系和健康。
  • 标签、服务年限、维保、机柜、可用分区；可用分区用于存储网络连通域和资源池划分。
  • 数据中心视图：资源统计、容量利用率、告警统计、设备列表。

机制。 [推断] 拓扑是当前状态 + 定期同步：每 6 小时从设备/交换机/平台拉一次，构建当前关系。白皮书没有提“历史拓扑快照”“as-of 查询”“拓扑版本号”“PG mapping epoch”之类的时态能力。它回答“现在是什么”，不一定能回答“02:16 时是什么”。

业界先进。 [原理] 双时态建模（valid time + transaction time）、事件溯源、图数据库的时态边、CMDB 的 CI 历史。Fusion MCP 提供阵列/卷/文件系统/工作负载/设备群拓扑查询；DII 把资产身份和采集覆盖放在调查入口；AWS DevOps Agent 用应用拓扑 + 变更时间线做跨源调查。存储领域还需要 PG/CRUSH epoch 级别的映射快照。

缺口。

缺口 等级 说明
没有公开的“事发时刻拓扑”查询 高 回放/审计时无法证明当时的数据放置；只能用当前拓扑或外部快照
没有公开的拓扑版本/epoch 高 Ceph 的 PG mapping、CRUSH map epoch 无对应公开字段；存储侧映射变更难以精确对齐
没有公开的图查询/路径 API 中 北向 REST 可以查资源，但没有公开的多跳路径、影响范围查询契约
拓扑来源以华为设备为主 中 第三方阵列/主机/交换机的深度关系有限；跨厂商实体对齐靠人工/别名
6 小时同步 中 变更窗口内的拓扑变化可能滞后；不能用于分钟级取证

练习（答案见答案册第 2 部分）。 向 DME 提三个问题：能否按时间点查询拓扑？能否导出拓扑快照？能否给出 LUN 到物理盘的完整路径及版本？把答案写成接口需求；如果是否，设计一个“DME 定时快照 + 变更事件 + 外部图库”的补偿方案。

3.5 环节 4：异常检测、告警与健康评分

DME 公开能力。 这是 DME 最成熟的产品化部分之一。

告警规则：

  • 屏蔽、闪断/振荡、汇聚、相关性（根因/衍生父子）、自动确认、标识（维护态/无效）、重定义（名称/级别/类别）、远程通知、告警同步、维护经验、事件转告警、名称组、HCS 全栈协同。
  • 北向上报可按告警 ID、源类型、级别、分类、根因父/子告警过滤，通过 SNMP Trap 送第三方。

检查策略：

  • 性能阈值（连续 N 个采样点超限）、容量阈值、可用性（硬盘健康、设备/端口/交换机/主机状态）、配置合规、可回收/低利用率资源。
  • 检查周期可配；支持“所有/任意”条件；可设置恢复动作（如变更服务等级）并自动执行。
  • 巡检：预置每日关键风险项 + 自定义计划。

AI 健康：

  • 百分制扣分：告警、性能异常（基线对比、预测对比）、性能预警（过去 1 个月预测未来 2 周）、容量预警（过去 180 天预测未来 1 年）。
  • 80+ 专家经验检查项（产品页/彩页口径）；性能预测用 Lasso/岭回归/随机森林融合；容量预测用 SVM/ARIMA/对数回归/线性回归融合。

机制。 [推断] DME 的检测是“规则/策略 + 统计基线 + 预测 + 健康评分”的混合，不是单一 ML 异常检测。优点是每个告警都有规则/检查项可解释；缺点是阈值和权重由产品/用户设定，缺少公开的误报率、召回率和校准。

业界先进。 [原理] SLO 多窗口燃烧率、FDR/多重检验、分层基线、Alertmanager 抑制、异常检测的可解释性与告警预算；DII 的 Monitor 把阈值/异常/容量/性能分开；Dell 的健康评分/预测分析/生成式助手；Pure1 的设备群健康。告警工程的核心不是“检测更多”，而是“用可接受的误报量换可接受的首响时间”。

缺口。

缺口 等级 说明
没有公开的 SLO/错误预算/燃烧率 高 告警级别仍以设备/规则为主，难以直接对齐业务影响
没有公开的告警质量指标 高 误报/集群日、事故级召回、MTTD/MTTA/MTTR、重复翻页率未公开
相关性规则是用户定义的父子关系 中 不是自动学的因果图；复杂共同原因仍靠人
健康评分是启发式，不是校准概率 中 60 分/扣分比例不等于故障概率；跨型号可比性未公开
动态阈值/预测的统计口径未公开 中 基线窗口、季节处理、异常判定、模型版本不可见
第三方设备检测深度有限 中 阈值/性能可用，故障树/亚健康/智能分析主要面向华为设备

练习（答案见答案册第 2 部分）。 选一个 DME 告警，倒推它的“检查项/阈值/连续点数/恢复动作”；再写一个对应的 SLO 燃烧率规则，比较两者在同一事故上的触发时间和误报。

3.7 环节 6：根因、证据与反证

DME 公开能力。

  • 智能分析：I/O 全路径时延、资源瓶颈、故障/亚健康/配置分析；输出根因、故障传播、修复建议；入口在告警、全局搜索、拓扑、性能分析、健康。
  • 场景：资源时延高、业务中断（首错模块）、存储 CPU 高、流量突变的“变化点”分析。
  • A 系列流程：并行客户端诊断 → zone 内诊断 → 业务网络/Scaleout/存储 zone 故障树 → 汇总报告。
  • 故障智能体：匹配故障场景，按“故障排查思维链”调用工具：资源健康、关联告警根因、性能瓶颈/异常、劣化风险、故障树智能分析；输出诊断结论。
  • 覆盖：闪存系列故障场景 64%；明确未覆盖对象服务、迁移服务、容灾服务、备份服务、AI 存储全局资源、主机侧和交换机侧关联资源。
  • 工作台：待诊断 → 诊断中 → 已诊断 → 恢复中 → 已恢复 → 待关闭 → 已关闭；自动聚合同一时间窗、有关联的告警为一个“问题”。
  • 口径：1 分钟识别、3 分钟定界、5 分钟辅助定位（彩页）。

机制。 [推断] 这是“专家故障树 + 产品知识 + 有限工具调用”的路线：先把现象匹配到场景，再沿故障树/ I/O 路径做排除，最后给结论。它不等同于统计因果推断；[博客] 提到的“因果推理模型 + 知识图谱”在 25.1.0 白皮书里没有对应的公开实现细节。

业界先进。 [原理] 因果图/do-calculus、反事实、差异中的差异、故障树 + 贝叶斯网络、证据溯源；AIOpsLab 把检测/定位/诊断/缓解做成任务；RCAEval 做候选召回/重排分解和盲测；ORCA-bench 考模糊报障下的多源调查。

缺口。

缺口 等级 说明
没有公开的证据对象/出处/查询 ID 高 报告结论难以逐条回查到样本、窗口、来源；审计和复现困难
没有公开的反证/竞争假设表达 高 产品偏向“给结论”，缺少“哪些假设被排除、排除到什么程度”
覆盖 64%，且排除主机/交换机/对象/迁移/容灾/备份 高 真实事故常跨主机/网络/对象/备份；覆盖外只能靠人工

数字孪生/因果图谱是博客方向 中 [博客] 自己说“必须依赖实时数字孪生环境仿真”“从相关走向因果”，说明尚未产品化

3.8 环节 7：LLM、Agent、RAG 与工具契约

  • 基于生成式 AI 的对话式数字助理；自然语言交互（LUI）、多轮上下文、意图理解、任务拆解、API 调用、结果汇总。
  • 流程：意图库语义匹配/排序 → 多轮追问确认 → 调用系统 API → 结构化整理/摘要。
  • 功能：查性能（含阈值线/趋势总结）、查资源列表、查关联对象、查健康评分、执行智能分析（输出结构化报告与处置建议）。
  • 口径：80% 日常运维一句话完成、5 倍效率提升（产品页/彩页）。

故障智能体：

  • 基于故障场景知识构建排查思维链，自动监控告警/故障消息，匹配场景、解析对象、查关联资源、执行排查、给结论。
  • 工具：资源健康、关联告警根因、性能瓶颈/异常、劣化风险、故障树智能分析。
  • 可通过北向 API 接入用户侧跨域智能体，从应用做到基础设施的跨域诊断。

DataMaster：

  • 产品页确认对话式运维、故障 Agent，以及内置模型或客户提供的第三方模型对接。
  • AgenticOps 博客描述优化 Agent 按 SLO 分析并在管理员确认后执行，也描述云端 MaaS 周级迭代和本地工具协同。25.1.0 白皮书未展开这两项的具体交付边界，需核对部署版本、许可和数据流。

机制。 [推断] 运维助手是“意图库 + 工作流 + API”的受控 Agent：先匹配预置意图，再调预置 API，最后用 LLM 组织答案。它不是开放式工具规划（模型自由发现/组合任意工具），也不是通用 MCP 客户端。故障智能体是“场景匹配 + 故障树 + 工具调用”的值班数字人，边界由场景库决定。

业界先进。 [原理] MCP 把工具描述/调用/权限标准化；RAG 用 ACL/版本/生效时间过滤后再召回；Agent 观测记录工具轨迹、证据引用、成本和越权尝试；AWS DevOps Agent 提供 Agent Space、应用拓扑、跨源调查和沙箱；Pure1/Fusion/DII 已把存储查询暴露为 MCP 工具。

3.9 环节 8：处置、验证与安全

DME 公开能力。

自动化：

  • 资源发放：块（LUN/映射/Zone）、文件（命名空间/文件系统/Dtree/共享）；自动创建 Zone、映射 LUN。
  • 待办任务：提前规划、变更窗口执行、原子任务组、定期执行、邮件通知、参数预检查、低权限规划/高权限审核。
  • 业务编排：任务流（预检/主流程/异常流程）、参数表单、执行日志、导入导出、API Explorer；步骤支持预置操作和 Ansible Playbook。
  • 检查策略的恢复动作：如 LUN 性能阈值触发“变更服务等级”，可自动执行。

工作台：

  • 故障智能体诊断、人工诊断、巡检、信息收集、自定义动作（隔离硬盘/端口、批量命令、重启节点/进程）。
  • 自定义动作由华为专业服务定义、驻场服务执行；客户管理员跟踪/关闭。
  • 问题状态机：待诊断 → 诊断中 → 已诊断 → 恢复中 → 已恢复 → 待关闭 → 已关闭。

数据保护/安全：

  • 副本管理（快照/克隆/复制/双活/云备份）、容灾报表、SLA。
  • 防勒索：HyperDetect、文件扩展名拦截、实时检测、智能检测、安全快照、网存联动（HiSec Insight）、AirGap、备份集群响应、虚拟机隔离恢复。
  • 安全配置核查、远程证明（超融合场景，需 TPM）。

机制。 [推断] DME 的自动化是“预置工作流 + 审批 + 服务人员执行”，强在设备厂商的领域动作和预检查，不是“Agent 自由生成动作”。这对安全是好事，但也意味着开放 Agent 很难直接复用这些动作。

业界先进。 [原理] 政策即代码（OPA）、变更审批、幂等/回滚、dry-run、金丝雀、爆炸半径、审计；Fusion 的受监督写工具默认隐藏、需显式配置；AWS Agent 沙箱只读 + 网络白名单；Terraform/Ansible 的幂等和 plan/apply。

缺口。

缺口 等级 说明
没有公开的 Agent 动作授权模型 高 读/写工具是否分离、Agent 能调到哪一级、如何审批，未公开
没有公开的幂等/回滚/dry-run 契约 高 工作流有预检查，但接口级幂等键、回滚动作、失败补偿未公开

没有公开的处置后双验收 高 业务 SLO + 冗余/复制/备份的自动验证未公开；工作台状态机不等于数据验证

3.10 环节 9：评测、多集群与规模化

DME 公开能力。

5. DME 的真实优势

不要因为缺口多就低估它。以下五点很难自建：

  1. 设备覆盖和数据深度。 华为全系列 + 主流第三方存储/交换机/服务器/虚拟化/容器；HostLink、IO trace、CSI、端口光功率、控制器/池/LUN 级指标，这些不是通用工具能拿到的。
  2. 故障树和领域知识。 智能分析把 I/O 路径、首错模块、亚健康、配置、故障传播串起来；80+ 检查项、64% 闪存场景，是多年现场知识的产品化。
  3. 自动化与预检查。 资源发放、Zone 自动划分、待办窗口、低权限规划/高权限审核、Ansible 编排、工作流 API，这些是“能落地”的运维动作。
  4. 云端支持与协同。 DME IQ 产品页列出 Call Home、工单、7×24 支持、移动运维、远程巡检和升级。DataMaster 的云端 MaaS 与本地工具协同来自博客描述，部署形态、数据流和驻留边界需确认。
  5. 真实设备数据。 海量局点的硬盘日志、故障样本、版本矩阵，是公开数据很难替代的训练资产；但这也是“黑箱”的来源。

9.3 与业界系统的对照

逐款机制、优劣和版本来源见业界 AI 运维产品与华为 DME 对标。用 OceanStor 做设备级排障时，先验证 DME 的路径、故障树和工作台。再选择要对标的环节。Fusion 可用来核对外部工具和写入确认，DII 可用来核对异构采集健康，PowerStore 可用来核对异常区间和信号，AWS 可用来核对跨域调查、记忆和回放，Datadog 可用来核对按目标授权及执行后复查。

交通银行联合项目公开了知识图谱、RAG、流程编排和多 Agent。采购或实施时，应核验这些能力在目标版本与部署里的交付方式，并测试能否贯通调查证据、ITSM 审批、原厂作业和独立验收。

10. 结论

  • DME 是很好的“设备侧事实源 + 动作执行器”，不是完整的开放式存储专家系统。
  • 它的 AI 能力是“规则/故障树 + 预测 + 受控 Agent”的组合，优势是领域深度和可落地，边界是覆盖范围、开放性和可验证性。
  • 在 OceanStor 为主的环境，优先复用 DME 已交付的设备能力。跨厂商平台需要逐项验证业务 SLO、时态证据、外部工具契约、处置治理和回放评测。可用现有北向 API 对接，或按外部 Agent 的要求封装工具。
  • 最危险的误读是把博客愿景当产品现状，或把厂商指标当验收标准。正确做法是：用 DME 拿设备事实，用自己的评测集证明增益，用自己的权限模型守住动作。
