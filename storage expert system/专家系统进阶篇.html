1. 介质与控制器：延迟和可靠性的物理来源

1.1 HDD：寻道、旋转与顺序性

HDD 的一次随机读大致由四段组成：

T = T_queue + T_seek + T_rotational + T_transfer
  • 寻道：磁头移动到目标磁道，平均 4–8 ms（企业级 7200 rpm），最坏可达十几毫秒。
  • 旋转：等待目标扇区转到磁头下。转速 rpm 的平均旋转延迟是半圈：
平均旋转延迟(ms) = 30,000 / rpm
7200 rpm → 4.17 ms
15,000 rpm → 2.00 ms
  • 传输：块大小 / 持续带宽。
  • 排队：控制器/设备队列等待，高并发时占主导。

所以一块 7200 rpm HDD 的 4 KiB 随机 IOPS 上限大致是：

IOPS ≈ 1 / (平均寻道 + 平均旋转 + 传输 + 排队)
     ≈ 1 / (6 ms + 4.17 ms + 0.02 ms) ≈ 98 IOPS（单队列、无缓存）

实际企业盘靠缓存、命令队列、顺序化和短行程（short-stroke）可以到 150–200 IOPS，但量级不会变。这也是为什么“用 HDD 跑随机小 IO”在容量之外几乎没有优势。

顺序读则完全不同：磁头不用来回寻道，带宽由面密度和转速决定，企业级 7200 rpm 通常 200–280 MB/s。随机看 IOPS，顺序看带宽，两者不能用一个“性能”指标概括。

SMR（叠瓦式）盘还有“写入悬崖”：随机写会触发磁道重写，延迟和写放大骤增；它适合顺序追加/归档，不适合数据库随机写。采购时必须区分 CMR/SMR，不能只看容量单价。

HDD 的可靠性也有物理来源：磁头/介质缺陷、振动、温度、掉电、固件。SMART 能看到重分配扇区、待定扇区、不可纠正错误、命令超时、CRC 错误等，但这些信号稀疏、滞后、型号相关，这是硬盘故障预测难的根本原因。

1.2 SSD：FTL、GC 与写放大

SSD 的读写单位不对称：

  • 读/写以 page（常见 4–16 KiB）为单位；
  • 擦除以 block（常见 128–512 个 page）为单位；
  • 不能原地覆盖，必须先擦后写。

FTL（Flash Translation Layer）维护逻辑块到物理 page 的映射。更新一个 page 时，新数据写到新 page，旧 page 标记无效；无效 page 积累到阈值后触发 GC：把有效 page 搬走，擦除整个 block，再复用。GC 消耗后台带宽，和前台 IO 争用，形成尾延迟。

写放大：

WA = 写入 NAND 的数据量 / 主机写入的数据量

例如主机写 1 TB，NAND 实际写 2.5 TB，WA = 2.5。WA 越高，寿命消耗越快、有效带宽越低。

寿命常用两个口径：

TBW（Total Bytes Written）= 保修期内可写入的总量
DWPD（Drive Writes Per Day）= TBW / (容量 × 365 × 保修年数)

例：3.84 TB 盘，5 年保修，TBW 7,000 TB：

DWPD = 7,000 / (3.84 × 365 × 5) = 7,000 / 7,008 ≈ 1.0

如果业务每天全盘写 5 次，这块盘大约 1 年就耗尽保修写入量（忽略 WA 和预留差异）。容量规划必须同时算 IOPS、带宽和写入寿命。

SSD 的尾延迟还来自：GC、读干扰（read disturb）、磨损均衡、掉电保护、预留空间不足、OP 设置、温度。消费级盘在企业随机写下尾延迟会明显恶化，不能只看稳态 IOPS。

1.3 NVMe 与 NVMe-oF：队列和网络

NVMe 用多队列（每核一对提交/完成队列）、doorbell、轮询，减少了 SAS/SATA 的协议开销。随机 4K 读可以到几十万到百万 IOPS，延迟几十到几百微秒。

NVMe-oF 把命令放到网络上：

传输 特点 主要风险
NVMe/TCP 通用、易部署 CPU 开销、TCP 重传、拥塞
RoCEv2 低延迟、RDMA PFC/ECN 配置、丢包、拥塞
FC-NVMe 复用 FC 织物 成本、 zoning/LUN 兼容
NVMe over Fabrics 统一语义 多路径、命名空间、拥塞

RoCE 的“无损”依赖 PFC（优先级流控）和 ECN；配置不当会出现暂停帧风暴、队头阻塞、丢包重传。端到端延迟预算里，网络可能只占几十微秒，但一次拥塞就能造成毫秒级尾延迟。

1.4 控制器与缓存

存储控制器的关键部件：

前端端口 → 协议处理 → 缓存（读/写）→ 后端总线 → 磁盘/SSD
                │
             NVRAM / BBU / 超级电容（掉电保护）
  • 写缓存：写回模式先在缓存镜像完成就向主机确认，再异步 destage 到介质。低延迟，但依赖掉电保护；缓存降级/电池失效时可能切换写穿，延迟骤升。
  • 读缓存：命中率高时延迟低；预取对顺序读有效，对随机读可能污染缓存。
  • 缓存命中率：hit / (hit + miss)；但命中率不是越高越好，关键是未命中的代价和缓存污染。
  • CPU/ASIC：压缩、去重、EC、快照、克隆、复制都消耗控制器 CPU；CPU 饱和会表现为“所有 LUN 都慢”。
  • QoS：按租户/卷/卷组限制 IOPS/带宽/时延，防止 noisy neighbor；但 QoS 本身也会引入排队。

一个常见的误判：控制器 CPU 高 + 前端端口利用率高 + 磁盘利用率低 → 瓶颈在控制器（软件/压缩/快照），不是介质。反过来，磁盘利用率高 + 控制器 CPU 低 → 瓶颈在后端/介质。

1.5 介质故障与预测的物理边界

  • AFR（年化故障率）：企业盘约 0.5%–2%，不同型号/批次/工况差异大。
  • UBER（不可恢复读错误率）：决定大容量盘重建时遇到读错误的概率；盘越大，重建越久，风险越高。
  • 浴盆曲线：早期失效、随机失效、磨损失效；预测模型很难同时覆盖三段。
  • SMART 的局限：很多故障没有明显 SMART 前兆；不同厂商属性 ID 不一致；采样频率低；标签受运维策略影响。

DME 白皮书披露的 14 天健康度、30 天 SAS HDD 故障预测，是产品化模型；但公开材料没有给出 PR 曲线、校准和跨型号表现。学习时要把“模型存在”和“模型可信”分开。

2. 数据保护数学：RAID、EC、快照、复制与备份

2.1 RAID 与纠删码：可用容量、写惩罚与重建

常见方案的可用容量与写惩罚：

方案 可用容量（N 块盘，每块 C） 容错 部分条带写惩罚 重建读
RAID 0 N×C 0 1 不适用
RAID 1 / 10 N×C/2 1（每镜像对） 2 1 份
RAID 5 (N−1)×C 1 4 N−1 份
RAID 6 (N−2)×C 2 6 N−2 份
EC k+m N×C×k/(k+m) m 约 2(m+1)（单块部分写；全条带写可避免） k 份
3 副本 N×C/3 2 3 1 份

“写惩罚”来自部分条带更新：RAID 5 要读旧数据、读旧校验、写新数据、写新校验，共 4 个 I/O；RAID 6 有两份校验，约 6 个。全条带写可以避免读旧数据，只写新数据和校验；EC 的大块顺序写也是同理。小随机写多的工作负载，RAID 6/EC 的写放大可能比容量节省更贵。

算例：12 块 20 TB 盘，raw = 240 TB。

RAID 6：可用 10 × 20 = 200 TB（83.3%）
EC 8+2：可用 240 × 8/10 = 192 TB（80%）
3 副本：可用 240 / 3 = 80 TB（33.3%）

重建时间（按已用容量 U、重建速率 R）：

T_rebuild = U / R
20 TB / 200 MB/s = 100,000 s ≈ 27.8 h
20 TB / 100 MB/s = 200,000 s ≈ 55.6 h
20 TB / 50 MB/s  = 400,000 s ≈ 111.1 h

重建期间再坏一块盘的概率，可以用“年化故障率 × 重建窗口”粗估。AFR = 2%，重建 27.8 h：

单盘在窗口内故障概率 = 0.02 × 27.8 / (365×24) ≈ 6.4×10⁻⁵
RAID 6 剩余 11 块盘中再坏一块 ≈ 11 × 6.4×10⁻⁵ ≈ 7.0×10⁻⁴（0.07%）

单看一次很低，但如果有 1,000 个阵列、每年多次重建，累计风险不可忽略；而且重建压力会让实际故障率高于 AFR。大容量盘 + 高负载 + 慢重建，是 RAID 6/EC 的真实风险来源。

2.2 快照与克隆：空间、一致性与删除代价

快照不是“复制一份数据”，而是“保留旧数据块的引用”。两种实现：

  • COW（Copy-on-Write）：覆盖旧块前先复制到快照区；读旧快照时读副本。写路径多一次复制，快照空间随“被覆盖的旧块”增长。
  • ROW（Redirect-on-Write）：新写写到新位置，快照继续指向旧块；写路径不需要复制，但元数据映射更复杂，删除快照要回收大量块。

快照空间估算：

快照空间 ≈ 数据量 × 每日变化率 × 保留天数 × 共享折扣

例：10 TB 卷，每日变化 20%，保留 7 天，最坏 14 TB；实际因块共享/未变化块会低一些。容量规划要留 20%–30% 的快照/克隆余量，不能只按“当前已用”算。

一致性比空间更容易被忽视：

  • 崩溃一致：快照时刻的缓存/写入状态不确定，恢复后可能需要 fsck/日志重放。
  • 应用一致：先 quiesce 数据库/文件系统，再打快照；需要 VSS/agent/脚本配合。
  • 克隆：完整克隆复制数据，链接克隆共享块；链接克隆的删除/分裂要注意依赖链。

2.3 复制与双活：RPO/RTO 与带宽

模式 RPO 写延迟 距离 风险
同步复制 0 本地写 + RTT + 远端写 受 RTT 限制（通常同城） 远端慢会拖慢本地
异步复制 复制 lag 本地写 可跨城 灾备丢数据 = lag
双活/Active-Active 0（同城） 两端写 + 仲裁 低延迟 脑裂、仲裁、跨站一致性
快照复制 快照周期 低 任意 依赖快照一致性

同步复制的带宽：

带宽 ≈ 写吞吐 × (1 + 协议/快照开销)
例：10,000 IOPS × 8 KiB × 30% 写比例 = 24 MB/s

RTT 对写延迟的影响是直接的：RTT 2 ms，同步写至少多 2 ms；如果业务 SLO 是 1 ms，跨 2 ms RTT 的同步复制不可能达标。双活还要考虑仲裁站点、quorum、split-brain 策略和跨站锁。

2.4 备份、归档与防勒索

  • 快照不是备份：同一阵列、同一管理员域，勒索软件/管理员误删可以一起删。
  • 3-2-1：3 份数据、2 种介质、1 份离线/异地；现代补充“1 份不可变、0 错误恢复验证”。
  • 不可变/空气隙：对象锁、WORM、离线副本、AirGap；防的是“删除/加密”而不是“读取”。
  • 恢复验证：备份成功率不等于可恢复率；要定期做恢复演练，记录 RTO 和校验结果。
  • 勒索检测：文件扩展名、异常 I/O、熵值、快照元数据变化；检测到后先保护快照，再隔离，再恢复。

3. 协议与网络：把延迟拆到每一跳

3.1 FC：WWN、Zoning 与 LUN Masking

FC 网络里三个容易混淆的概念：

  • WWN：端口的唯一标识（WWPN 端口名、WWNN 节点名）。
  • Zoning：交换机侧定义“哪些端口能互相看到”，是 fabric 层的访问控制。
  • LUN Masking：存储侧定义“哪个主机 HBA 能看到哪个 LUN”，是阵列层的映射。

两者都要配置，缺一不可：Zoning 放开但 LUN Masking 没配，主机看不到 LUN；LUN Masking 配了但 Zoning 不通，链路建不起来。

其他关键机制：

  • FLOGI/PLOGI：节点/端口登录 fabric 和目标；登录风暴会导致端口拥塞。
  • RSCN：fabric 拓扑变化通知；大规模变更时可能引发主机重扫。
  • NPIV：一个物理 HBA 端口虚拟出多个 WWPN，用于虚拟化/多租户。
  • BB Credit：交换机端口缓冲区信用；信用耗尽会导致发送暂停，表现为间歇性延迟/超时。

FC 的端到端延迟通常很低（几十到几百微秒），但拥塞、信用耗尽、错误重传、zone 变更会让尾延迟突然变长。

3.2 iSCSI：TCP 上的块协议

iSCSI 把 SCSI 命令封装进 TCP：

  • 认证常用 CHAP；多路径用 MPIO（DM-Multipath）。
  • 依赖 TCP 重传/拥塞控制；丢包会导致毫秒级甚至秒级重传。
  • 可以用 TOE/网卡卸载降低 CPU；但卸载配置不一致会导致性能差异。
  • 与 FC 相比，iSCSI 更易部署、成本低，但延迟抖动和 CPU 开销更高。

诊断 iSCSI 尾延迟时，除了存储指标，还要看：网卡队列/丢包、TCP 重传、交换机端口错包、MTU/巨帧配置、多路径策略。

3.3 NVMe-oF：队列、拥塞与无损网络

NVMe-oF 把 NVMe 命令通过网络传输，常见三种：

传输 优势 关键配置/风险
NVMe/TCP 通用、无需 RDMA CPU 开销、TCP 重传、拥塞窗口
RoCEv2 低延迟、低 CPU PFC/ECN、无损配置、丢包敏感
FC-NVMe 复用 FC 运维体系 兼容性、zoning、成本

RoCE 的“无损”不是天然属性：PFC 按优先级暂停上游发送，ECN 标记拥塞让发送端降速。配置不当会出现：

  • PFC 暂停帧扩散 → 队头阻塞 → 整个端口卡住；
  • ECN 阈值不合理 → 要么不降速（丢包），要么过度降速（带宽浪费）；
  • 多路径哈希不均 → 单链路拥塞，其他链路空闲。

3.4 NAS：元数据、锁与租约

NFS：

  • NFSv3 无状态，依赖锁管理器（NLM）；客户端缓存和属性超时会影响“看到的延迟”。
  • NFSv4.1 有会话、租约、delegation；客户端可以在本地缓存/延迟写，故障恢复时重放。
  • pNFS 把数据路径分到多个 DS，元数据仍在 MDS；布局（layout）和客户端并行度影响吞吐。

SMB：

  • SMB3 有 oplock/lease、持久句柄、多通道、加密；租约让客户端缓存读/写，减少往返。
  • 目录热点、锁竞争、签名/加密 CPU 开销会拖慢元数据操作。

文件存储的 SLO 必须拆成元数据延迟、数据延迟、元数据 IOPS、数据带宽。一个 readdir 慢和一个 1 MiB 顺序读慢，根因完全不同。

3.5 S3：一致性、分片与重试

  • S3 语义通常是强一致（新对象立即可见；覆盖/删除也一致），但不同实现/网关可能有差异，要以具体产品文档为准。
  • Multipart：Amazon S3 的对象上限约 48.8 TiB，每次上传最多 10,000 个 part，每个 part 为 5 MiB–5 GiB，最后一个 part 无最小值。对十进制 1 TB 对象，固定 part 大小至少 100 MB。兼容 S3 的其他实现需查各自规格。 Amazon S3 multipart 限额
  • LIST：按前缀分页，大桶/热前缀会放大延迟；避免用 LIST 做实时统计。
  • 重试：5xx/SlowDown 要指数退避 + 抖动；无限制重试会放大后端拥塞。
  • 网关：认证、限流、桶索引、EC 编码都可能成为瓶颈；对象 SLO 要按 GET/PUT/LIST、状态码、对象大小拆分。

段 P50 P99 证据
应用/文件系统 0.05 ms 0.2 ms 应用埋点
客户端队列/多路径 0.10 ms 1.5 ms 主机 iostat/队列
网络（FC/iSCSI） 0.10 ms 0.5 ms 交换机端口/重传

4. 文件、对象与 Ceph 内部：命名空间和数据放置

4.1 文件系统：MDS、目录与锁

分布式文件系统通常把元数据和数据分开：

客户端 → MDS（目录、inode、权限、锁、布局）→ 元数据池
客户端 → OSD/DS（实际数据块）→ 数据池

关键机制：

  • inode/dentry 缓存：客户端缓存属性/目录项，减少往返；缓存一致性靠租约/回调。
  • 锁：读/写锁、范围锁、委托；并发写同一文件/目录会竞争。
  • delegation/lease：把部分权限委托给客户端，允许本地缓存；故障恢复时要收回。
  • 目录分片/子树分区：大目录拆成多个分片，避免单 MDS 热点；但跨分片 rename/readdir 更贵。
  • 热点目录：大量小文件 create/unlink 会让元数据池和 MDS CPU 成为瓶颈，数据盘可能很闲。

小文件问题的本质是元数据操作占比高：1 万个 4 KiB 文件的写入量只有 40 MiB，但可能产生几万次元数据 RPC、锁和日志写。SLO 要单独定义 metadata ops latency。

4.2 对象存储：桶索引、分片与 GC

对象存储的“对象”不是文件系统里的文件：

bucket → 对象键 → 桶索引（分片）→ 对象元数据 → 数据块/EC 条带
  • 桶索引分片：大桶/高并发前缀会把索引分片打热；对象键设计要避免单调前缀（如时间戳开头）造成热点。
  • multipart：分片上传、ETag、完成/中止；未完成的 multipart 会占空间，需要生命周期清理。
  • EC 池：对象按条带编码到多个 OSD；小对象可能被合并/内联，大对象按条带切分。
  • GC：删除对象后空间异步回收；大量删除会造成后台 GC 压力，影响前台。
  • 一致性：现代对象存储多为强一致，但网关缓存、跨区域复制会引入滞后；SLO 要区分本地读和跨区读。

4.3 Ceph：CRUSH、PG 与恢复

Ceph 的对象放置：

object → hash(object_name) → PG ID → CRUSH(pgid, cluster map) → OSD 集合
  • CRUSH 是伪随机、确定性的放置算法；相同输入 + 相同 map 得到相同 OSD 集合。它支持故障域（host/rack/row/site）和权重。
  • PG 是放置和复制的单位；PG 数太少会导致数据不均，太多会增加 peering/内存开销。
  • PG 数估算（经验值，目标每 OSD 约 100 个 PG）：
pg_num ≈ (OSD 数 × 每 OSD 目标 PG 数) / 副本数
例：100 OSD × 100 / 3 ≈ 3,333 → 取 2 的幂 4,096

4,096 个 PG、3 副本时，每 OSD 平均承载 4096×3/100 ≈ 123 个 PG，略高于 100；也可以选 2,048（约 61 个/OSD）。实际用 pg_autoscaler 和容量/负载监控调优，不要只看公式。

  • Peering：PG 的主/从 OSD 协商数据版本，确定权威副本；期间 PG 可能 peering/inactive，不能服务。
  • Recovery/Backfill：恢复缺失副本；backfill 用于新 OSD/重映射，扫描整个 PG。两者都消耗网络/磁盘/CPU。
  • Scrub：轻量校验元数据，deep-scrub 校验数据校验和；发现不一致时 repair。
  • BlueStore：直接管理块设备，元数据在 RocksDB，数据带校验和；没有本地文件系统层，减少双写。
  • mClock：按客户端/恢复/scrub 等类别分配 reservation/limit/weight；调参要看版本和 osd_op_queue 模式。
  • Map epoch：osdmap/pgmap/CRUSH map 都有 epoch；排障时要记录“当时看到的 epoch”，否则无法复现放置。

常见 PG 状态与含义：

状态 含义 下一步
active+clean 可服务，对象已达到配置副本数 仍需查看其他健康项和 scrub 结果
active+degraded 可服务但副本不足 看 down/out OSD、恢复进度
active+undersized acting 集合小于期望 看 CRUSH、可用 OSD
undersized+degraded+peered 已完成 peering，但可用副本未达到 min_size，当前不能处理客户端 I/O 检查 min_size、可用副本与恢复进度
inactive 不能服务 看 peering 卡住、unfound objects
stale PG 映射变更后，Monitor 尚未收到该 PG 的状态更新 看主 OSD 状态及其到 Monitor 的通信
down 持有必要数据的副本不可用，PG 离线 查所需副本、OSD 与 PG 状态

排障顺序：ceph health detail → ceph osd tree → ceph pg dump_stuck → ceph pg <pgid> query → 看 up/acting、peering、unfound、scrub 错误 → 再查主机/网络/磁盘。

4.4 故障域：为什么“副本数”不等于“可靠性”

3 副本如果全在同一个机柜，机柜断电就全丢；EC 8+2 如果 10 个块分布在 5 个 host，坏 2 个 host 可能丢数据。可靠性取决于：

副本/校验数 × 故障域隔离 × 重建速度 × 静默错误检测

CRUSH rule 要显式指定 failure domain（host/rack/row/site），EC 还要考虑 crush-failure-domain。跨站点时还要考虑仲裁、延迟和脑裂。

5. 性能与容量建模：从指标到决策

5.1 USE 与 RED：先定位资源，再谈异常

  • USE（Utilization、Saturation、Errors）：每个资源看利用率、饱和度、错误。CPU、内存、网络、磁盘、控制器、队列都适用。
  • RED（Rate、Errors、Duration）：每个服务看请求速率、错误、持续时间。适合 SLO 和端到端。

存储排障的最小检查表：

资源 Utilization Saturation Errors
CPU 使用率 run queue/steal MCE/温度
内存 使用率 swap/回收 OOM
网络 带宽/端口 队列/暂停帧/重传 CRC/丢包
磁盘 利用率/IOPS 队列深度/await 介质错误
控制器 CPU/缓存 队列/脏页 降级/电池
池/PG 容量/IOPS 恢复队列/backfill degraded/scrub

“利用率高”不等于“瓶颈”：如果队列不深、延迟不升，可能是正常高负载；如果利用率不高但延迟高，可能有锁、重传、GC、后台任务或上游限流。

5.2 Little 定律、排队与 USL

Little 定律：

L = λ × W
并发数 = 吞吐 × 延迟

例：50,000 IOPS × 0.5 ms = 25 个在途请求；20,000 IOPS × 2 ms = 40 个。队列深度突增往往意味着服务时间变长，而不是流量变大。

M/M/1 给出非线性直觉：

R = S / (1 − ρ)
ρ=80% → 5×S；ρ=90% → 10×S；ρ=95% → 20×S

USL（Universal Scalability Law）描述多核/多节点的扩展性：

X(N) = N / (1 + α(N−1) + βN(N−1))
  • α：争用（串行化）导致的饱和；
  • β：一致性/缓存同步导致的回退（retrograde）。

例：α=0.1，β=0.01：

N=1: 1
N=8: 8 / (1 + 0.7 + 0.56) = 3.54（效率 44%）
N=16: 16 / (1 + 1.5 + 2.4) = 3.27（效率 20%，已回退）

这解释了为什么“加节点”不总是线性提升：共享锁、元数据服务、一致性协议、网络会成为瓶颈。扩容前先测 USL 参数，比盲目加硬件更有效。

5.3 IOPS、带宽、缓存与混合负载

带宽 = Σ (IOPS_i × 块大小_i)
平均延迟 = 命中率 × 命中延迟 + (1 − 命中率) × 未命中延迟

例：70% 4 KiB 读 + 30% 8 KiB 写，总 100,000 IOPS：

读带宽 = 70,000 × 4 KiB = 286.7 MB/s
写带宽 = 30,000 × 8 KiB = 245.8 MB/s
合计 ≈ 532.5 MB/s

写还要考虑写惩罚/WA：RAID 6 的部分条带写、SSD 的 GC、EC 的条带更新都会让“业务带宽”和“介质带宽”不一致。容量规划要按介质写入量算，不是只按业务写入量。

缓存平均延迟：命中率 90%，命中 0.1 ms，未命中 4 ms：

0.9 × 0.1 + 0.1 × 4 = 0.49 ms
命中率 70%：0.7 × 0.1 + 0.3 × 4 = 1.27 ms

命中率从 90% 降到 70%，平均延迟涨 2.6 倍；尾延迟涨得更多。缓存不是“越大越好”，命中率、污染、预取策略和写回策略同样重要。

5.4 容量、TCO 与扩容窗口

容量账本：

raw → usable（RAID/EC/副本）→ effective（快照/克隆/元数据/回收站/安全水位）
可分配容量 = effective × (1 − 安全水位)

例：100 节点 × 12 盘 × 20 TB = 24,000 TB raw；EC 8+3 效率 8/11 = 72.7%：

usable = 24,000 × 8/11 ≈ 17,455 TB
10% 安全水位 → 15,709 TB
当前已用 12,000 TB；90% 告警线 = 14,138 TB
剩余可增长 = 2,138 TB；50 TB/天 → 42.8 天

扩容不能只看“到 90% 的天数”，还要看：采购/上架/布线/初始化/数据重平衡时间；故障域预留（N+1）；重建期间不能写满；快照/克隆增长；业务峰值。

TCO 至少包括：介质、控制器、机柜/电力/制冷、网络、软件许可、维保、运维人力、迁移/停机成本。只比“每 TB 单价”会忽略性能和可靠性成本。

5.5 SLO 与容量/性能的联动

  • SLO 决定“可接受的延迟/错误”，容量决定“还能撑多久”，两者要用同一时间窗口和同一测量点。
  • 错误预算快烧完时，扩容/优化是“止血”；但如果是代码/配置/热点导致，扩容可能只是延后故障。
  • 容量告警要带“预计到阈值时间 + 置信区间 + 假设（增长率/业务变化）”；不要只报“剩余 20%”。

6.1 异常检测：从稳健统计到变化点

方法 适合 关键假设 主要坑
固定阈值 硬边界、合规 业务语义稳定 工作负载变化就失效
中位数 + MAD 单指标、平稳、有离群 分布近似对称、样本足够 MAD=0、季节性
EWMA 缓慢漂移、在线 近期更重要 对突变滞后

6.2 生存分析：硬盘预测的正确统计语言

硬盘故障是“时间到事件”问题，不是普通二分类：

  • 删失（censoring）：观测结束时还没坏、被主动更换、迁移走；不能当负例。
  • 竞争风险：真实故障 vs 主动退役 vs 迁移，处理方式不同。
  • 时变特征：SMART 每天变化；用当时可见的特征，不能泄漏未来。
  • Kaplan-Meier：估计生存曲线，不依赖分布。
  • Cox 比例风险：特征对风险的影响，需检验比例风险假设。
  • 校准：预测 10% 风险的盘，实际故障率是否约 10%；PR-AUC 和校准曲线都要看。

固定窗口二分类（未来 H 天是否故障）也可以做，但样本构造要避免同盘泄漏、时间泄漏和运维反馈偏差。

6.3 因果推断：存储里的“自然实验”

存储没有随机对照，但有很多自然实验：

  • 维护窗口让一个 OSD 下线 → 观察同 PG 的前台延迟；
  • 限速 backfill → 观察 P99 是否下降；
  • 分批升级 → 比较升级/未升级集群；
  • 同集群不同池/不同租户 → 对照；
  • 变更前后 → 中断时间序列（ITS）/差异中的差异（DiD）。

因果图（DAG）要先画清楚：共同原因（业务峰值同时导致高 IOPS 和高延迟）、对撞（两个原因都导致告警）、中介（维护 → backfill → 延迟）。后门准则/do-calculus 用来判断“控制哪些变量才不引入偏差”。

一个典型错误：控制“IOPS”来估计“backfill → 延迟”的因果效应。如果 backfill 也影响 IOPS，控制 IOPS 会挡住部分因果路径（过度控制）。正确做法是先画 DAG，再决定调整集。

6.4 贝叶斯网络与故障树

故障树用 AND/OR 门表达“多个原因同时/任一导致现象”；贝叶斯网络给每个节点条件概率，能做诊断推理：

P(根因 | 证据) ∝ P(证据 | 根因) × P(根因)

Noisy-OR 适合“多个独立原因任一导致告警”的场景：

P(告警 | 原因集合) = 1 − Π(1 − p_i)

产品里的故障树通常是专家维护的确定性规则；贝叶斯网络需要历史数据/专家先验，校准更难。两者可以结合：故障树生成候选，贝叶斯/统计排序。

6.5 图算法：影响范围、路径与中心性

  • BFS/DFS：从故障实体沿边找影响范围；BFS 适合最短跳数。
  • 最短路径：确认两个实体之间是否有可达路径；边可带延迟/带宽权重。
  • 连通分量：找出共享故障域的一组实体。
  • 中心性（度/介数/接近）：识别关键交换机、控制器、共享池。
  • 社区发现：把拓扑聚类成业务域/故障域；注意别把“同一机柜”误当“同一业务”。
  • 时态图：边带有效期；查询要按时间切片，不能用当前图跑历史。

6.6 优化：放置、容量与 QoS

常见问题：

  • 放置/装箱：把卷/租户放到池/控制器，约束容量、性能、故障域、亲和/反亲和；小规模用 ILP/CP-SAT，大规模用贪心/启发式。
  • QoS 分配：在租户间分 IOPS/带宽，最大化满足 SLO；可以用排队论/优化，但要留安全余量。
  • 扩容/迁移：最小化停机/迁移量/成本；多目标（性能、成本、风险）通常需要加权或 Pareto 前沿。
  • 备份窗口：在 RPO/RTO 和业务低峰之间排程；本质是调度问题。

存储优化不要追求“全局最优”而忽略可解释性/可执行性；运维需要的是“可批准、可回滚、可验证”的方案。

6.7 LLM Agent：规划、工具与验证

Agent 的核心不是“更长的 prompt”，而是：

状态 → 计划 → 工具调用 → 观察 → 证据 → 判断是否足够 → 报告/停止

关键设计：

  • 有界：最大步数、时间、token、查询行数；无界 Agent 会烧钱/打爆后端。
  • 工具契约：输入/输出 schema、时间语义、权限、错误类型、证据 ID。
  • 验证器：引用存在、单位/数值、时间截止、权限、schema；模型自评不算验证。
  • 记忆：工作记忆（当前事故）+ 长期记忆（Runbook/历史工单），长期记忆要版本/ACL。
  • 反思：让模型生成反证/替代假设，而不是只证明自己对。
  • 评测：任务成功率、证据正确率、工具成本、越权拒绝、缺数据暂缓、轨迹可复现。

ReAct/Plan-and-Execute 只是编排方式；决定成败的是工具质量和验证层。

7.1 最小数据模型

不用一上来就上图数据库。PostgreSQL + 时序库 + 对象存储可以支撑第一版。核心表：

-- 实体：稳定身份 + 别名 + 生命周期
CREATE TABLE entity (
  entity_id    TEXT PRIMARY KEY,          -- tenant/cluster/type/uuid
  tenant_id    TEXT NOT NULL,
  cluster_id   TEXT,
  entity_type  TEXT NOT NULL,             -- host/switch/array/pool/lun/fs/osd/disk
  native_uuid  TEXT,
  display_name TEXT,
  lifecycle    TEXT NOT NULL DEFAULT 'active',
  first_seen   TIMESTAMPTZ NOT NULL,
  last_seen    TIMESTAMPTZ NOT NULL,
  attrs        JSONB NOT NULL DEFAULT '{}'
);

CREATE TABLE entity_alias (
  entity_id  TEXT NOT NULL REFERENCES entity(entity_id),
  alias_type TEXT NOT NULL,               -- hostname/wwn/serial/ip/k8s_uid
  alias_value TEXT NOT NULL,
  valid_from TIMESTAMPTZ NOT NULL,
  valid_to   TIMESTAMPTZ,
  PRIMARY KEY (entity_id, alias_type, alias_value, valid_from)
);

-- 时态边：保留有效时间和每次修订的知识时间
CREATE TABLE edge (
  src_id      TEXT NOT NULL,
  dst_id      TEXT NOT NULL,
  relation    TEXT NOT NULL,              -- runs_on/maps_to/replicates_to/depends_on
  valid_from  TIMESTAMPTZ NOT NULL,
  valid_to    TIMESTAMPTZ,
  observed_at TIMESTAMPTZ NOT NULL,
  known_from  TIMESTAMPTZ NOT NULL,
  known_to    TIMESTAMPTZ,
  source      TEXT NOT NULL,
  confidence  REAL NOT NULL DEFAULT 1.0,
  attrs       JSONB NOT NULL DEFAULT '{}',
  CHECK (valid_to IS NULL OR valid_from < valid_to),
  CHECK (known_to IS NULL OR known_from < known_to),
  PRIMARY KEY (src_id, dst_id, relation, valid_from, source, known_from)
);

CREATE INDEX edge_src_time ON edge (src_id, valid_from, valid_to);
CREATE INDEX edge_dst_time ON edge (dst_id, valid_from, valid_to);

-- 事件/变更：事件时间与观测时间分开
CREATE TABLE event (
  event_id    TEXT PRIMARY KEY,
  event_type  TEXT NOT NULL,              -- change/alert/deploy/maintenance
  entity_id   TEXT,
  event_time  TIMESTAMPTZ NOT NULL,
  observed_at TIMESTAMPTZ NOT NULL,
  source      TEXT NOT NULL,
  source_ref  TEXT,
  payload     JSONB NOT NULL
);

-- 证据对象：不可变引用
CREATE TABLE evidence (
  evidence_id TEXT PRIMARY KEY,
  incident_id TEXT,
  query_id    TEXT NOT NULL,
  source      TEXT NOT NULL,
  entity_id   TEXT,
  window_start TIMESTAMPTZ,
  window_end   TIMESTAMPTZ,
  observed_at  TIMESTAMPTZ NOT NULL,
  quality      JSONB NOT NULL,            -- coverage/missing/units
  payload_ref  TEXT NOT NULL,             -- 对象存储路径
  summary      TEXT NOT NULL
);

关键约束：

  • entity_id 不含可变名称；别名单独表。
  • observed_at 保留来源观测时间，known_from/known_to 记录该修订对调查者可见的区间。收到补录或纠正时，在同一事务关闭旧修订的 known_to 并插入新修订，保留旧修订的 valid_from/valid_to。例如 02:20 得知边于 02:10 结束，旧修订保留原开放区间，新修订的 valid_to 为 02:10、known_from 为 02:20。关系撤销时关闭旧修订，按需记录撤销事件。并发写入对同一来源和逻辑边串行化，查询使用两组半开区间。
  • 证据只追加不修改；删除用 tombstone/审计。
  • 所有时间存 UTC，展示时再转本地时区。

7.2 as-of 查询

用 PostgreSQL 的 tstzrange 更简洁：

CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE edge ADD COLUMN valid_range TSTZRANGE
  GENERATED ALWAYS AS (tstzrange(valid_from, valid_to, '[)')) STORED;
ALTER TABLE edge ADD COLUMN knowledge_range TSTZRANGE
  GENERATED ALWAYS AS (tstzrange(known_from, known_to, '[)')) STORED;
CREATE INDEX edge_range_gist ON edge USING GIST (src_id, relation, valid_range, knowledge_range);

-- 事发时刻 t、知识截止 cutoff 的有效拓扑
SELECT src_id, dst_id, relation, source, confidence
FROM edge
WHERE src_id = :entity_id
  AND valid_range @> CAST(:t AS TIMESTAMPTZ)
  AND knowledge_range @> CAST(:cutoff AS TIMESTAMPTZ)
ORDER BY relation, dst_id;

多跳（递归 CTE，限制深度）：

WITH RECURSIVE reach(entity_id, depth, path) AS (
  SELECT CAST(:start_id AS TEXT), 0, ARRAY[CAST(:start_id AS TEXT)]
  UNION ALL
  SELECT e.dst_id, r.depth + 1, r.path || e.dst_id
  FROM reach r
  JOIN edge e ON e.src_id = r.entity_id
  WHERE r.depth < :max_depth
    AND e.valid_range @> CAST(:t AS TIMESTAMPTZ)
    AND e.knowledge_range @> CAST(:cutoff AS TIMESTAMPTZ)
    AND NOT e.dst_id = ANY(r.path)       -- 防环
)
SELECT DISTINCT entity_id, depth FROM reach ORDER BY depth;

注意：递归 CTE 在大图上可能很慢；生产要限制深度/边类型/租户，或把多跳放到图数据库/预计算。

7.3 PromQL：SLO、覆盖率和异常

好请求比例（成功且 ≤20 ms）：

sum(rate(http_request_duration_seconds_bucket{le="0.02",code=~"2.."}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))

燃烧率（SLO 99.9%）：

(1 - (
  sum(rate(http_request_duration_seconds_bucket{le="0.02",code=~"2.."}[1h]))
  /
  sum(rate(http_request_duration_seconds_count[1h]))
)) / (1 - 0.999)

采集覆盖率。将 CMDB 中的期望 OSD 导出为 expected_osd（值为 1）。用 osd_telemetry_fresh 表示目标指标在指定窗口内是否新鲜。两者都按 (cluster, osd) 唯一。以下表达式分别按集群统计，期望数为零时无覆盖率，全部期望 OSD 停报时返回 0。

(
  sum by (cluster) ((osd_telemetry_fresh == 1) and on (cluster, osd) (expected_osd == 1))
  or on (cluster) (0 * sum by (cluster) (expected_osd == 1))
)
/
(sum by (cluster) (expected_osd == 1) > 0)

up 表示当前发现的抓取目标是否抓取成功。经统一 exporter 抓取时，还需逐 OSD 检查实际数据的 freshness，分母来自独立资产清单。 Prometheus 抓取目标

异常分数（以毫秒为单位的延迟指标为例）。启用 --enable-feature=promql-experimental-functions 后，使用截至 5 分钟前的一小时作为基线。

0.6745 * (latency_ms - quantile_over_time(0.5, latency_ms[1h] offset 5m))
/
clamp_min(mad_over_time(latency_ms[1h] offset 5m), 1)

7.5 Agent 循环与验证器

state = init(symptom, window, scope, budget)
for step in range(max_steps):
    if state.budget_exhausted():
        return undecided(state, reason="budget")
    plan = llm.plan(state, tools=available_tools(state.scope))
    call = validate_schema(plan.tool_call)
    if not authorize(call, state.principal):
        state.add_refusal(call)
        continue
    obs = execute(call, timeout=state.timeout)
    state.add_evidence(make_evidence(obs, call))
    if state.sufficient() or state.no_discriminating_query():
        break

report = llm.compose(state, schema=REPORT_SCHEMA)
errors = verify(report, state)
if errors:
    report = llm.repair(report, errors, state)  # 有界重试
    errors = verify(report, state)
if errors:
    return undecided(state, reason="report_validation_failed")
return report

验证器至少检查：

每个事实有 evidence_id
evidence_id 在 state 中存在
证据对调查者的可见时间 ≤ 报告知识截止
单位/量纲一致（ms/s、MiB/MB、IOPS/BW）
数值在证据范围内
没有越权实体/租户
结论强度与覆盖率匹配（coverage 低 → 不得给高置信）

结论：当前证据最支持 H1。报表作业集中创建小文件，备份目录扫描可能进一步增加元数据开销。控制器 A CPU 与元数据操作延迟同时上升，观测到的磁盘和网络信号未支持 H2。finance 位于不同控制器和文件系统，可用作影响范围对照。需要单独调整扫描或创建并发，才能进一步区分两者贡献。
