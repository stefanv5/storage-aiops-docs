1. 先看同一条业务告警

凌晨 02:16，订单写入变慢。值班工程师要先回答三个问题。受影响的是哪些应用和卷？几种可能原因中哪一种最符合证据？现在可以做什么，怎么确认做完有效？

如果只接了阵列数据，系统可以检查存储路径和后台活动。要判断一次应用发布是否改变了写入方式，还要拿到发布记录和请求数据。两边都接上之后，Agent 仍要识别数据断点、区分同一时间出现的事件与真正有解释力的证据，并把处置交给有权限的执行方。这些设计比“是否带 AI 助手”更能区分产品。

  • DME 的长项在设备侧。 对受支持的 OceanStor 环境，DME 能把资源、I/O 路径、设备状态、告警、故障树和恢复工作台连起来。看闪存路径、控制器或后端异常时，这些是通用 SRE Agent 必须额外接入的信号。 H
  • 同类存储产品提供了三个可直接拆解的设计。 Everpure 展示如何开放细粒度工具和读写控制，NetApp 展示如何先验证证据覆盖再调查，Dell 展示如何把预期区间和异常偏差交给值班员判断。 E · N · L
  • 跨域平台把调查和动作组织成可检查的过程。 AWS 可查看调查轨迹并比较重放结果，Datadog 将动作限定到具体资源，记录批准和执行，再触发恢复复查。移植到存储时还需设备作业对账和数据保护验收。 A · B

产品能力以 2026-11-21 核验的公开版本为对比基准，本地模型与诊断专题于 2026-11-22 补充，并按交叉审核校正了产品边界、回放与验收口径。下文以公开文档能观察到的产品行为为依据。故障场景和数值均为教学示例。DME 对照以 25.1.0 容器化白皮书为基准，联合项目、云服务和预览能力分别注明。准确率、速度与成本需要在同一套现场数据和权限下测试。

同一条告警为何走出六条调查路径

用一个固定问题看差异。02:16，订单写入 P99 到 46 ms。请给出最可能的原因和下一步。 这一行告警只能触发调查。系统还得知道哪个租户、哪个服务、哪些实例和卷，并找到能区分后台活动争用、网络退化、写入变化的证据。下表是按公开能力推导的排查路线，假设对应集成和角色已启用。实验数据来自 Ceph 合成回放，原厂设备用其同类观测点类比，表内步骤不是厂商模型的内部调用轨迹。

Dell PowerStore / Dell AIOps 从本地历史区间的偏离点，或已接入云端的健康风险开始 用设备级视图定位偏离点；另查卷曲线，高精度和覆盖按接口核对 结合 I/O 大小、字节吞吐、IOPS 与时延。可以识别“请求数近似稳定、写入字节显著变化”；应用触发需变更证据 云端助手给建议。指定健康检查可按配置 Auto-Repair，其余走人工或支持流程 已有检查核对修复结果和告警状态，应用与存储保护另取证 区分本地趋势、云端对话和健康检查记录
AWS DevOps Agent 应用告警、事件关联或人工调查；先确认 Agent Space 具备相关账号和集成 从服务拓扑和发布范围找受影响实例，按应用→资源→外部存储工具查 对比发布前后、旧版或其他服务，增查日志和链路，再用设备证据验证应用假设 后台调查形成建议；操作者在对话中请求处置。执行时校验覆盖操作和目标的有效批准，设备动作需相应执行器 CloudTrail 或外部任务记录追踪动作，另查 SLO 和保护状态 比较根因、评分、耗时、工具、技能和时间线。重放重查在线数据
Datadog Bits 已配置的 Monitor、合成检查、RUM 或人工问题 从受影响监控、服务与链路进入，优先沿已采集业务上下文查证 用同一调查收集指标、信号和变更。遇到关键证据缺口可保留未决 受支持的 AWS/Kubernetes 资源走 Guardrails、审查和执行角色，当前存在 Preview 边界 操作员触发 Verify Resolution 复查可见症状；储存保护由设备侧证明 回看原调查结论、动作历史与复查窗口

有五处差异会改变工程结果。 H · E · N · L · A · B

  1. 采集链决定系统有权说什么。 DII 能从源级状态说明数据缺在哪。Fusion 要先分清设备群成员与性能覆盖。DME 有设备秒级证据，但能回查的粒度与时间受设备侧留存制约。每种限制都会改变根因报告的有效范围。
  2. 资产关联决定能否把业务问题连到同一设备。 假设新版本只有半数实例，且凌晨有卷迁移。依照当前拓扑查旧告警，可能查到迁移后的卷。DME 供原厂对象和路径，AWS/Datadog 供已接入服务和变更。合并两边时要给映射加时间、来源和缺失标记。
  3. 分析器与 Agent 的判断不同。 Dell 算一条序列是否偏离历史；DME 可用路径和故障树给出设备域候选；通用 Agent 决定接下来去哪里取证。看到时延偏离只能确认一处异常。定位发布、后台争用还是网络，还要看有区分力的证据与对照。
  4. 查询权限、调查权限和写入权限是三件事。 NetApp DII MCP 的调用可以完全只读；Datadog 发起调查不代表获批修改资源；DME 设备审核有自己的角色；Fusion 的 MCP 写入确认也要受阵列权限约束。组合架构要明确哪个系统是最终执行权威。
  5. 系统关单条件不同。 云平台验证业务信号，设备平台验证实际配置和保护状态。一次处置可能让 P99 回落，但原厂任务未结束或复制仍滞后。把两路验证记录回同一工单才能给出业务已缓解、保护待恢复的明确状态。

华为 DME 与 DataMaster

DME 的起点是已纳管的存储和基础设施。一次订单慢写调查可以从卷、主机或告警入手，沿可见 I/O 路径找到受影响的设备与端口，再由智能分析区分性能、中断或配置问题。关键信号由设备和分析模块提供，DataMaster 负责识别问题、调用工具与汇总结果。 H

DME 25.1.0 容器版已公开功能

  1. 资源纳管。 登记阵列与资源关系。通过受支持的 REST、SNMP 等采集库存、性能与告警。按兼容清单连接 SAN 交换机、主机、虚拟化和 Kubernetes 等环境。验收时分别记录可发现、可监控、可诊断和可操作的型号范围。
  2. 设备性能。 可从存储设备、池、LUN、磁盘、前端端口等对象查看相应性能。支持历史曲线和两个时间窗对比。受支持的 Dorado V6 及后续系列可按需回取设备侧留存的 5 秒数据，白皮书所述最大查看周期为一周。设备侧需要先开启相应留存，秒级历史视图与平台长期库的留存分别核对。
  3. 告警与预警。 检查策略、性能阈值、巡检、健康、历史基线和预测承担不同职责。判断是告警触发、趋势异常还是容量风险时，记录具体对象、计算窗和适用设备。白皮书披露的 64% 是故障智能体对所述闪存故障场景的覆盖口径。白皮书另列不覆盖的相关主机、交换机等资源，不能与 DME 全部纳管或性能分析范围合并。
  4. 智能分析。 性能问题可沿路径结合时延、瓶颈、亚健康或配置，推荐原因与修复；涉及 OceanStor A 系列或分布式存储且发生 I/O 错误的受支持业务中断，可用首错模块定界。故障树适合把若干关联告警组织成具体传播候选。报告可给出关联根因、传播和处置建议，逐结论样本引用的接口字段待验。
  5. 对话和告警调查。 运维助手支持对象及时间窗的指标查询、健康诊断和智能分析入口。故障智能体按已匹配场景调用健康、关联告警、瓶颈、风险和故障树等工具。白皮书描述通过北向 API 对接用户侧跨域智能体。需要现场看 API 返回粒度、角色限制、可见范围和任务跟踪。
  6. 作业与审批。 资源发放覆盖受支持的块和文件场景。待办任务支持分组、参数预检、权限化审核与条件下定期执行。工作流可定义预检、主流程和异常流程，提供执行跟踪。问题处理工作台有诊断与恢复入口，特定自定义动作按规定角色执行。审批者如何绑定跨系统计划、超时如何找回原生作业，应以使用的接口或 ITSM 实测。

联合项目的另一条跨域链

交通银行联合项目披露的 1+1+N 由知识图谱与 RAG 决策、流程编排、计算/存储/基础设施域 Agent 组成。常见模式走规则匹配，复杂故障结合统计特征、语义编码、LLM 和故障知识图谱。例如果异常先被某条存储规则命中，站点编排可把只读观察任务发到相关域，再由值班流程审核处置。这种分工是可借鉴的联合架构，具体任务契约、知识库与设备能力需对应拟部署版本。DME IQ 的云运维、Call Home 和支持能力属于另有说明的产品链。 H

适用位置。 OceanStor 为主时，优先让 DME 回答哪条设备路径异常、哪些原厂证据支持、可走哪个设备流程。业务 SLO、部署与跨站旧拓扑可由总控接入，按数据实际覆盖组合。

Everpure Pure1 与 Fusion 2.0

这里有两个可以分别接入的查询面。Pure1 Manage MCP 给设备群管理视角，Fusion MCP 给可连接阵列的对象及配置视角。一个 AI 客户端能分别接入这两套工具，设备和授权范围各自计算。内置 Copilot 有自己的调查入口。 E

  1. 管理面盘点。 Pure1 Manage MCP 正式可用，开放受支持的只读 Pure1 Manage API。适于先找告警、容量风险和异常设备群。Pure1 自带 Copilot 另有性能异常调查功能。
  2. 发现应用关系。 厂商介绍 Purity 6.10.0 在适用阵列上发现支持的数据库应用与文件上下文，可补充应用、工作负载与存储的关联。事故中的实际发布、业务请求或远端调用还需相应应用观测。
  3. 阵列层工具。 Fusion 提供设备群、阵列、FlashArray 卷、文件系统、工作负载和预设查询。可用专用工具查 IOPS、吞吐及时延，也有通用只读配置查询。设备群总览能列出的成员范围可能比直接配置的性能查询范围大。
  4. 配置与工作负载操作。 Fusion 2.0 区分精选写工具与通用写工具，两类默认关闭。精选工具覆盖文档列出的放置建议、预设、部署、卷、主机及快照等操作，具体支持按阵列类型确认。
  5. 确认与记录。 启用写工具后，保留默认服务端确认时，客户端必须支持 MCP 询问交互，否则服务端拒绝运行。阵列令牌、工具开关和客户端确认共同约束操作。该版本还用会话标识、工具来源帮助关联服务端与阵列请求记录。企业工单和业务验收还要接入各自的流程。

与 DME 对照。 Fusion 给出了版本固定的工具和参数，可以直接验证“八台可见，哪五台能查性能”“没有确认功能的客户端会如何失败”。代价是 Token 覆盖、版本与 Agent 集成需要维护。DME 在 OceanStor 的 I/O 路径、故障树、受支持中断的首错和工作台更接近存储值班端。可对照 Fusion 的能力测试方法验收 DME API，保留 DME 原厂诊断深度。 E · H

NetApp DII 与 Digital Advisor

DII 负责把多源对象和基础设施指标组成调查视图。Digital Advisor 主要消费受支持 ONTAP 的 AutoSupport 遥测，提供风险与生命周期建议。两条线可同时使用，证据来源和许可分别检查。 N

  1. Digital Advisor 规划。 将设备遥测与诊断信息用于健康、风险、容量、性能和升级规划。适合评估某设备是否有已知风险，以及怎样安排升级或扩容。
  2. DII 异构接入。 通过受支持的采集单元及采集器获取存储、交换机、虚拟化、容器等对象。先核对型号和实际字段。带有 GPU 或 HPC 需求时，可查看 11 月更新记录中 NVIDIA Base Command Manager 采集器的预览范围。
  3. 采集事实优先。 可查采集单元连接状态、数据源状态、最后上报或采集结果、对象类型和 Collector 版本。用有权访问的资产台账与调用身份的授权范围交集作预期对象分母，再核对数据源的最近成功采集时间。可见清单与授权边界未知时报告 unknown_coverage，不从空查询枚举账号外资产。
  4. 查询约束。 DII 配方先发现对象类型、读取字段元数据，再精确定位对象。按支持的指标和单位查事故窗和健康对照窗，核对粒度；该配方单次所述窗口不超过 30 天。再查告警和日志，并区分观察、相关、推断和未知。历史对象关系需要相应历史数据。
  5. 两个 AI 入口。 DII Assistant 在所述 AWS 托管站点正式可用，发布记录披露按问题生成可视化。面向外部 Agent 的 DII MCP 仍为租户内只读 Preview。调查完成后把设备写操作交给具有目标设备权限的工作流。

Dell PowerStore 与 Dell AIOps

PowerStoreOS 4.2 的本地异常视图、Dell 云端分析和设备 Health Checks 形成三条路径。部署时分别验证可见指标、建议范围，以及自动修复支持清单。 L

  1. 历史区间。 PowerStore Manager 按设备历史行为和季节性形成带状的预期范围。在时延、IOPS、带宽或 I/O 大小超出范围的点上显示偏离值和时间，允许调节灵敏度。该本地功能本身不发直接告警。异常视图针对 appliance，所述 4.2 手册的近 24 小时或一周视图为 5 分钟粒度，近两周或一月为一小时。单卷或较高精度数据另查相应性能视图和留存。
  2. 同一请求数下的负载量。 例如写 IOPS 近似不变、均写大小从 8 KiB 到 64 KiB，则提交字节量约扩大八倍。再看同设备不同卷是否同步恶化、网络是否拥塞和是否有其他变更，判断是单一负载还是资源争用。设备级聚合可能隐藏单卷尖峰。
  3. 连接云端。 产品受支持、配置 Support Connectivity 后，可上传相关性能、容量、告警、配置和支持数据。基于上传的数据比较跨设备健康和趋势，接入需要按现场遥测出域要求验证。
  4. 云端分析。 关注容量突增、性能波动与争用。公开健康评分说明按影响最大问题扣分，风险分用于队列排序，判断原因仍应下钻到具体对象和证据。
  5. 云端助手。 在适用账号可用 @系统名 指定已接入实例，查健康、异常、IOPS、时延和带宽，并用所述 PowerStore 更新建议能力做计划。按账号、站点、设备和指标验收。云端助手的建议与现场执行记录分别保存。
  6. 已知问题自动修复。 PowerStoreOS 4.2 起通过相应 Health Check 包交付 RxDefinitions。对检查命中的、明确支持修复的问题，按配置走 Alert Only 或 Auto-Repair；部分检查和条件仍需人工。验收可核对一项适用问题的告警与修复记录。普通慢写仍走诊断，不能由此推定云端助手能执行任意阵列变更。

与 DME 对照。 判定‘哪段路径慢’优先看 DME 的受支持设备诊断，判定‘设备偏离自己的历史有多大’可借鉴 Dell 的区间和 I/O 大小。处置另用一个已知问题验证，比较 DME 的预置作业与 Dell 定域 Health Check 能否给出触发条件、适用对象、结果及人工接管状态。 L · H

AWS DevOps Agent

AWS 的调查从应用、告警或部署开始。Agent Space 把账号、可查数据与工具目录限定在范围内。它的价值在于从应用层向下拼装证据，并把过程留到复盘。 A

  1. 接入与触发。 连接监控、日志、链路、代码库、部署流水线、工单等受支持的集成。调查可由告警、Webhook 或操作者发起。能否读某个日志或应用拓扑取决于实际连接和账号权限。

  4. 分层授权。 默认可用的是只读调查。官方批准交互在对话中出现，后台自动调查直接调用变更工具会失败。变更资源的定向动作默认关闭，启用需配置、账号角色和工具分类，执行时校验操作者批准的范围。官方 API 流程允许批准一次性动作，也可给匹配的操作和目标设置最长四小时的重用窗。记录批准范围、有效期及撤销。通过 API 登记第三方 MCP 时，未分类工具按 READ_ONLY 处理，需显式核对分类、凭据和网关实际权限。受支持的 AWS 操作可在 CloudTrail 关联审核和执行。设备原厂动作还要有独立可调用接口及实际授权。
  5. 报告、评价和回放。 查看候选根因、证据和时间线，对已完成调查重新执行，比较根因、评分、时间、技能和工具。重放重新查询在线系统。需要严格比较两个版本时，另固定一份含知识截止、资产关系和工具版本的不可变快照。

Datadog Bits

Bits 的入口围绕监控告警和线上事故。它可以查现有调查，也能把建议、人工批准、受支持的基础设施处置和复查挂在同一次调查上。 B

  1. 调查触发。 可从受支持的 Monitor 告警自动或手动发起，也可从合成测试、RUM、Error Tracking 或人工问题发起。已有监控指标、日志、链路和相关变更决定调查能看多深。
  2. 证据不足处理。 跟踪活动和推理结果，必要时结论保持未决。按权限和站点可通过 MCP、Bits API 或 pup CLI 查询和发起调查。MCP investigator 还公开支持为运行中的调查补充上下文。发起调查的权限与批准基础设施动作分别检查。
  3. 把建议变成拟议动作。 在受支持资源上给出目标、参数和动作。例如订单服务对应的 Kubernetes Deployment 回滚。若无策略覆盖具体动作和资源，可以形成建议，执行仍需另行授权。
  4. 两条执行路径。 Kubernetes 按 Private Action Runner 的允许清单和集群权限执行；AWS 使用相应集成角色。Guardrails 可限定动作、资源与批准者。当前文档的一键基础设施动作和相关策略有 Preview 或站点边界。
  5. 复查和留痕。 查询动作记录、状态和关联调查。操作员在调查中点击 Verify Resolution。若时间窗仍包含处置前失败请求，可等待相关 Monitor 恢复后点击 Check Again，记录检查窗口。存储事故的冗余恢复、复制或恢复点校验仍从设备侧和业务验收服务取得。

与 DME 对照。 Bits 把跨域症状、干预与复查串成一次调查，优势是受支持资源的授权及事后可查。DME 的原厂存储设备作业更贴近 OceanStor。两者合在一起时，用调查 ID、工单、计划版本与原厂任务 ID 关联，并让业务和数据保护各自出具验证结果。 B · H

  3. 从计划到设备作业的关联和双验收。 将审批、请求、原厂任务、实际对象状态、业务与保护的证据关联到同一调查 ID。用超时和拓扑变化测试对账。只有目标状态时保留本次作业的待对账状态。

任务二 把一项卷扩容做成可验收作业

值班员要求给一个订单卷扩容。接到需求后先由 Agent 取证形成计划，再由审批和执行系统处理。

5. 迁移到 PB 级平台的模块分工

设备和采集层。 复用 DME 与其他原厂平台能稳定提供的接口，补应用 SLO、部署、主机多路径、交换网络和工单。维护“资产、支持指标、采集时效”三份清单。在 PB 环境中，采集与推理预算看对象数量、标签基数、频率、保留期和并发调查，与业务存储容量分别估算。例如 2 万个卷、每卷 12 项指标、15 秒一次，在每指标每次一个样本的假设下约 1.6 万样本/秒，还没计入路径标签和日志。常态调查可先用汇总趋势缩小范围，再按需读取特定对象的高精度窗口。

证据与知识层。 把设备样本和日志保留在时序及日志系统，事故窗口保留原始引用和实际覆盖。知识图谱存应用到卷到设备的有时间效力的关系，以及型号、固件、已知模式和 Runbook。运行状态和手册分开取证，例如用指标证明何时退化，用手册解释当前设备为什么会呈现这一模式。

调查和执行层。 保留规则与统计检测的快速路径，复杂问题由 Agent 选择只读工具、切换调查域、比较假设和整理证据。单独用确定性流程做授权、计划版本、设备任务核对和验收。在第一期让调查输出统一的调查 ID、对象、时间窗、输入覆盖、证据链接和未决项。用它贯通 DME、应用监控和工单之后，再接受监督的设备作业。

评估。 每次保存调查截止时间、关键证据、当时拓扑、工具和规则版本、判断与人工复核结论。先用缺采集、共享路径、审批后变化、响应丢失与保护未恢复五类用例做回归，再扩大站点。对于纯 OceanStor 环境，先吃透 DME 的设备能力；对于异构阵列和多业务域，优先确定各产品覆盖与跨域证据契约。建设细节见 PB 级建设手册。

怎么取得可验收的准确率

两份对照实验。

  1. 评估取证链。 给同一批事故固定原始证据、可见截止、权限和查询预算。在同一模型配置下分别跑静态 RAG、纯快照、文档加快照、快照加只读工具，另设规则或原厂诊断基线。各组最终拿到的信息有差异，报告取证覆盖、延迟、总成本和端到端诊断。
  2. 评估模型推理。 固定实际输入的证据体、排序后的文档、工具回执及可达集，只改模型或推理模式。避免跨组带上上一轮会话、额外在线数据和标签。无法冻结输入的商用 Agent 在此列记为不适用，另提供原生端到端结果。

事故真值和截止时是否可判分别标注。 审核人员先用事后证据标 true_cause，再用独立的冻结快照标 decidable_as_of 和合格行为。B 完整例和 B 缺网络变体是同一起教学事故。两者事后原因相同，截止时前者可给优先候选，后者应暂缓。未确认真值的事故记录为 unknown，可评价证据和决策边界。按母事故、近重复、站点及时间分组切分，不把同一次事故的变体、事故复盘答案或能暴露标签的 ID 放进盲测索引或会话。A/B/C 及缺数变体先用于流程试验。
