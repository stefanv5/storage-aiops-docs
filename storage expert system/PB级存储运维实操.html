建设手册 · 基础 Ceph 回放

四站依次练习接入实验 Ceph 集群、用证据区分相同症状的不同原因、在进程重启后找回已受理的作业，以及从写入报错一路查到容量事故结案。第二至第四站从仓库根目录运行。第三、四站需要 Python 3.10 或以上，第三站另需 SQLite 3.35 或以上。运行 python -c "import sqlite3; print(sqlite3.sqlite_version)" 查看 SQLite 版本。

1. 接入一个实验 Ceph 集群

收集并对照三类事实

在能访问实验集群管理面的节点或 cephadm shell 运行下列命令。换成环境中的配置和 keyring 路径，使用已授权的只读身份。记录站点、责任人、Ceph 版本和集群 FSID。已有测试业务时，再记录 workload ID、稳定卷或共享 ID，以及所用池。 Ceph 监控 · Ceph 设备管理

ceph_read() {
  ceph -c /etc/ceph/ceph.conf -n client.ops-observer \
    -k /etc/ceph/ceph.client.ops-observer.keyring "$@"
}
ceph_read fsid
ceph_read status --format json
ceph_read osd tree --format json
ceph_read osd dump --format json
ceph_read device ls --format json
ceph_read health detail --format json
ceph_read mgr services --format json
  1. 哪些资产应当上报？ 用完整快照建立清单。从 OSD 树取主机和故障域，从 OSD map 取 epoch 与 up/in，从设备映射确认物理盘身份。找不到物理盘的 OSD 标为待核对。记录采集时间、发布时间和原文位置。
  2. 实际收到了哪些指标？ 在 Prometheus 查 OSD 状态和进程性能计数器。抽一个 OSD，对照资产身份、状态和采样时间。只聚合测量点和单位相同的指标，覆盖率用期望资产数作分母。
  3. 这期间发生了什么？ 收集健康事件和维护记录。比较前后快照，把差异记为事件。同一次变化沿用同一个 ID，并记下在哪次快照看到。之后可接入推送或 ITSM 事件。已有测试业务时，另采应用成功率和尾延迟。

用 inventory_snapshot(snapshot_id, collected_at, complete, source_ref) 记下快照是否完整，用 entity_revision(entity_id, native_id, source_id, valid_from/to, known_from/to) 保存每版资产。要还原历史拓扑，再建关系表，记录两端实体 ID、关系类型、生效时间和可查时间。调查前查 source_health(source_id, expected_count, reporting_count, watermark, missing_ids)，查哪些资产已上报、数据已处理到哪个时点。

验收与故障变体

先保存健康快照作基线，再用本地采集副本或回放文件试下表。模拟漏读分页时，只截短副本，继续观测实验集群。

变体 预期
资产快照缺最后一页 标记本轮快照不完整，沿用上次完整清单中的期望资产
同一事件重复回放 按 source + event_id 去重，持久化后再推进游标
一个 OSD 指标源停报 期望数不变，上报数减少，并列出缺失实体
拓扑修订晚到 按旧调查截止查询仍能复现原快照，按新截止查询能看到修订后的关系
OSD 编号被新实例复用 历史事故仍关联原 OSD UUID 或代次，新实例使用新身份

验收表写明数据源、权限、期望数、覆盖率、采样频率、去重测试结果、断连时间和补传后的数据水位。附一条能查回原始样本的证据。手头没有实验集群时，先用第二站的 CSV 练统计和对照，之后补做接入验收。

2. 从同一个症状识别三种原因

打开跨层回放 CSV。A、B、C 是三个独立的合成事故，应用写 P99 都升到 46 ms。三例都只查 2026-11-21T02:16:00Z 前能看到的记录，以 observed_at 为准。网络值是已映射路径的当前值除以同一路径的基线。对照业务走另一条路径和另一个池。每次只给模型当前案例已查到的证据，A 的晚到数据留到复盘。

$replay = Import-Csv -LiteralPath '.\storage expert system\lab\cross-layer-replay.csv'
$cutoff = [DateTimeOffset]'2026-11-21T02:16:00Z'
$replay | Where-Object { $_.case_id -eq 'A' -and [DateTimeOffset]$_.observed_at -le $cutoff }

任务与比较方法

  1. 三例都用“写 P99 超过 20 ms”告警。记下只凭这个告警能确认什么。
  2. 先给模型业务告警、时间和来源名称。将 application、network、ceph、device、changes、control 当作查询工具，每次只返回该来源在截止前可见的数据。独立来源可以并行查。也可由你用同样的规则选下一项查询。每轮记下查了什么、返回哪些证据 ID、还有什么没查清。
  3. 输出 impact、hypotheses、evidence_for、evidence_against、next_check。按证据强弱给候选原因排序，列出缺的信息，以及哪项检查可能推翻当前判断。
  4. 从 B 的快照删掉 B04、B05、B08、B10，注明缺少网络和相关变更记录，再答一次。网络路径仍可列为待查候选，结论置信度应降低。
参考证据与评分
案例 支持最强的候选 排除其他路径还需要什么
A A06–A08 支持 PG 映射变化后 backfill 与前台争用。A02–A05 削弱了提交量突增或已观测网络拥塞的解释 查实际 acting 路径和 OSD 服务时延。A10 到 02:16 时尚未可见
B B04、B05、B08、B10 支持有效链路减少后该路径拥塞。B06、B07 削弱了后端恢复争用的解释 核对主机和交换机两端的时间与流量，确认该链路确实承载受影响业务
C C03、C08、C10 支持单次写入量增加、池吞吐上升。C07 的队列上升，C06 未观察到 backfill 查块大小分布、并发和同池其他负载，核对批量导出与设备压力出现的先后

每例 5 分，根因排序和证据引用与反证各 2 分，可执行的下一步 1 分。单记提前引用晚到数据和编造证据的错误。缺数据时，看报告是否仍能确认业务影响，并把根因留在待查状态。两种方法用同一份来源快照，比较找到首条能区分候选原因的证据所用时间、调用次数和人工复核耗时。

3. 验证一次跨进程的卷扩容任务

工作流模拟器用 SQLite 保存执行器状态和设备作业，两者分开提交。审批已预设。按顺序运行，每条命令启动一个新进程。先看丢响应后能否找回同一作业，再看审批后的拓扑改变会不会拦住提交。

路线 A：设备已受理，执行器丢了响应

从仓库根目录运行下列 PowerShell 命令。每次演练创建新的临时数据库，方便回查此前结果。

$script = '.\storage expert system\lab\workflow_replay.py'
$db = Join-Path ([IO.Path]::GetTempPath()) ('storage-replay-' + [Guid]::NewGuid() + '.sqlite')
python $script $db init
python $script $db step
python $script $db step
python $script $db step
python $script $db step
python $script $db step
python $script $db verify-protection
python $script $db step
调用 预期状态 验收点
init approved 审批与设备拓扑修订均为 7
第 1 次 step submission_unknown 设备任务数为 1，执行器没有拿到 job ID
第 2 次 step tracking 新进程用原请求键找回 job ID，设备任务数仍为 1
第 3 次 step tracking 设备作业仍在运行
第 4 次 step verifying 作业完成，业务验证通过，保护验证待完成
第 5 次 step verifying 保护信号缺失，工作流仍开放
verify-protection verifying 保护验证通过，等待状态机读取验证结果
最后一次 step succeeded 业务与保护验证均通过，设备受理作业数为 1

路线 B：审批后的拓扑发生变化

沿用路线 A 的 $script。如果另开了 PowerShell，先在仓库根目录执行路线 A 中给 $script 赋值的那一行。

$driftDb = Join-Path ([IO.Path]::GetTempPath()) ('storage-drift-' + [Guid]::NewGuid() + '.sqlite')
python $script $driftDb init
python $script $driftDb drift-topology
python $script $driftDb step
python $script $driftDb status

用 status 确认审批仍绑定修订 7，现场拓扑已到修订 8。此时应为 needs_reapproval，设备任务数为 0。重新规划前，写明要复查哪些容量、影响路径和保护依赖。

复盘与迁移到真实接口

模拟器只有一个执行者，审批和验收结果均已预设。接入真实设备时，从厂商 API 或集群管理器查作业。例如 ONTAP 从异步响应返回 job ID，用它跟踪进度。接口支持按客户端请求键查受理状态时，先用原键核对。查不清是否受理时，转人工处理。扩容前查数据面和文件系统是否支持扩容、池水位和保护关系。扩容后查应用可用空间和实际读写。遇到不能原样回退的扩容，先定好补偿和交接办法。 ONTAP 异步作业

在对照记录里写下 request_id、设备 job_id、审批版本、每次推进前后的状态、业务与保护的验收证据，以及设备受理的作业数。换盘、固件升级、迁移和恢复演练可以沿用这份记录格式。

4. 处理一次写入空间不足的容量事故

订单写入报空间不足。用合成数据和本地模拟器查明哪一层的空间用完了，再从批准扩容走到结案。每条命令启动一个进程，同一时间只有一个执行者。脚本只用 Python 标准库，状态写入临时 SQLite 文件，全程在本地模拟。

查清写入失败的原因并批准计划

  1. 查哪一层满了。 INC-ENOSPC-01 的应用写入报 ENOSPC（E01）。目标卷 ceph-lab/pool-7/image-9f 上的文件系统为 20 GiB，可用空间为 0，还有可用 inode（E02）。租户配额还剩 10 GiB（E03），池还剩 16 GiB（E04）。四条证据在 2026-11-22T02:16:00Z 调查截止前均可查，diagnose 应返回 filesystem_full。
  2. 算扩完还剩多少。 计划把卷和文件系统从 20 GiB 扩到 24 GiB。本题按新增 4 GiB 同时扣减池和配额，扩完后配额剩 6 GiB，池剩 12 GiB，满足池至少留 8 GiB 的要求。plan 生成的哈希绑定事故、目标、动作、扩容参数、拓扑版本、池的最低余量和证据 ID。
  3. 核对计划，再批准。 看清 $plan.plan 的目标卷和扩容大小，再用教学角色 lab-approver 批准确切目标与计划哈希。批准从模拟时钟当前时刻生效，满 10 分钟失效。首次 step 会重新核对审批、卷当前大小、拓扑版本、配额和池余量。

从仓库根目录运行下列 PowerShell 命令。每次用新的临时数据库，后续步骤沿用同一个 $caseDb。脚本会拒绝用错的数据库。

$chain = '.\storage expert system\lab\incident_chain.py'
$caseDb = Join-Path ([IO.Path]::GetTempPath()) ('incident-chain-' + [Guid]::NewGuid() + '.sqlite')
$scenario = 'success'
python $chain $caseDb init --scenario $scenario
python $chain $caseDb diagnose
$plan = python $chain $caseDb plan | ConvertFrom-Json
$plan.plan | ConvertTo-Json

先读上一步打印的计划。确认目标卷和扩容大小后，在同一个 PowerShell 会话运行这条审批命令。

python $chain $caseDb approve --approver lab-approver --target $plan.target --plan-hash $plan.plan_hash --valid-minutes 10

找回作业并分别验收

批准后按下列顺序运行。第一次 step 先保存提交意图，模拟设备受理后丢响应。第二次 step 用原 request_id 查作业，核对目标和扩容大小。查不到作业或参数对不上时，进入 needs_review，等人工核对。第三次 step 模拟设备报扩容完成，接着还要验业务和保护。

模拟时钟从 02:16 开始，作业于 02:17 完成。再推进 1 分钟，两个正常探针的样本才可见。验收只用同一目标在作业完成后观测的样本，并要求样本距当前检查不超过 5 分钟。结案时两项都要通过，且样本都在有效期内。

python $chain $caseDb step
python $chain $caseDb step
python $chain $caseDb step
python $chain $caseDb advance-clock --minutes 1
python $chain $caseDb verify-business
python $chain $caseDb verify-protection
python $chain $caseDb status | ConvertFrom-Json |
    Select-Object incident_id, target, phase, device_jobs, job_id, volume_gib |
    ConvertTo-Json -Compress
命令 状态 核对内容
第 1 次 step submission_unknown device_jobs 为 1，执行器还没拿到 job_id
第 2 次 step tracking 原 request_id 找回 mock-job-001，device_jobs 仍为 1
第 3 次 step verifying 设备作业完成，等业务和保护验收
verify-business verifying V-B01 显示文件系统已到 24 GiB，可用 4 GiB，100/100 次写入成功且回读通过
verify-protection succeeded V-P01 显示受影响范围的 PG 均为 active+clean，退化 PG 和 scrub 错误均为 0。业务样本仍有效，两项均通过

用最后一行输出核对事故、目标、结案状态、作业数、作业 ID 和扩容后的大小。

重跑失败路线

每个变体从第四站的第一段命令重来，生成新的 $caseDb。按表改 $scenario 或在指定位置插入命令，再看 phase、device_jobs 和拦截原因。

变体 改哪一步 应看到的结果
缺保护样本 令 $scenario = 'missing-protection'，其余照常 业务通过，保护为 missing。继续 verifying，作业数 1
等保护样本时，业务证据过期 在缺保护样本的路线中，业务验收后执行 python $chain $caseDb advance-clock --minutes 6，再查保护 业务变为 stale，保护仍为 missing。继续 verifying，作业数 1
保护样本早于作业完成 令 $scenario = 'stale-protection'，其余照常 V-P00 观测于作业完成前，保护为 stale。继续 verifying，作业数 1
拓扑在批准后改变 批准后执行 python $chain $caseDb drift-topology，再执行一次 step needs_reapproval，原因为 topology_changed，作业数 0
审批过期 批准后执行 python $chain $caseDb advance-clock --minutes 10，再执行一次 step needs_reapproval，原因为 approval_expired，作业数 0
角色、目标或哈希不符 分别把审批命令的 --approver、--target 或 --plan-hash 换成错误值，再执行一次 step 审批被拒，仍是 planned，step 返回 approval_required，作业数 0
池余量突然降到 10 GiB 批准后执行 python $chain $caseDb tighten-pool，再执行一次 step 扩 4 GiB 后只剩 6 GiB，低于 8 GiB。进入 blocked，作业数 0
