学习导览 · 原理与实现 · 存储实操 · 厂商能力对照

本手册以三个站点、约 10 PB 原始容量、块/文件/对象混合部署为例。先接入设备并采集证据，再用 Agent 调查和拟计划，经审批后执行，最后验收业务和数据保护。初版选一个 Ceph 集群、一条应用写入路径和一个可查询状态的设备异步作业。接入第二家厂商后，用同一任务协议检验适配器。容量、采样和验收数字均为算例，上线时按业务 SLO、采购周期和设备实测确定。

1. 定容与部署

按下表分别估算业务与保护、遥测、资产与清单、运维任务。各项使用各自的统计口径。

算例。 20 万条活跃序列每 15 秒采一次，约 13,333 样本/秒、11.52 亿样本/天。某站平均接收 12 MB/s 遥测，按断链 6 小时计算，需要缓冲约 259.2 GB。恢复后若要在一小时内补齐，额外需要 72 MB/s。连同新数据，共需 84 MB/s 有效吞吐。再按峰值、压缩、磁盘预算和站点设备管理接口的承载能力复算。若 30 天新增 1 PB 运维数据，平均入口约 386 MB/s，写放大、索引和副本另计。以上均用十进制单位。

故障域算例。 假设三站业务各留在本站，分别演练每站失去一个机柜。已按剩余设备重新算冗余效率、固定占用和一次预留，三站在各自的故障情景下可分配容量为 220、260、280 TB。三站当前各用 190 TB，每天分别净增 2、1、1 TB。按可分配容量的 95% 告警，到线分别需 9.5、57、76 天。第一站最先到线。若采购、上线和重平衡至少需 7 天，按此情景扩容需在 2.5 天内启动。实际还要核对剩余机柜能否重建，以及容量和增长能否跨池或跨站调剂。

2. 多厂商接入与数据管道

新设备从登记到上线

  1. 登记。 录入站点、设备所有者、管理端点、厂家型号、固件、设备标识范围和权限。给适配器单独的只读凭据，试查设备身份和设备时钟。
  2. 能力探测。 试查盘、卷、端口和指标。记录历史能查多久、事件如何订阅、如何翻页、如何限流，以及各项能力所需版本。异步作业查询和写入能力单独登记。
  3. 首轮全量。 把各页写入暂存清单，记录来源、快照 ID 或版本和扫描状态。各页必须来自同一稳定快照，且所用权限与资产范围一致。读完并对账后再发布新清单。某页失败、跨页版本变化时保留上次完整清单，标为过期。支持范围内确认资产确已消失后，才标为待核对或退役。
  4. 增量与对账。 从已提交的游标续订，收到通知后查相关对象，并定期用全量或摘要对账。全量期间先缓冲变化，再按可比较的快照边界和源版本重放，避免旧记录覆盖新记录。游标过期、来源重置或无法补齐断点时，标出缺口，重新获取基线和可续订游标，数据发布成功后再保存进度。没有稳定快照或版本的接口，全部分页成功也只能表示这次扫描读完。用按 ID 回查、重复扫描或供应商账本验证差异，确认前不凭某次缺项退役。
  5. 上线验收。 对照设备界面抽查身份、单位、数量和路径。模拟凭据失效、分页错误、事件丢失和限流。增加扫描中途插入和删除资产、游标过期及采集进程重启的对照。检查是否保留上次完整清单、避免误退役，重建后能否与设备实物对齐。升级固件后重新探测。设备退役后保留历史身份和证据引用。

按设备支持的能力选用厂商 REST、Redfish/Swordfish、Ceph、SNMP 或受限的只读采集器。Swordfish 提供通用的存储资源模型，仍要核对各型号实际支持哪些字段和操作。Ceph Manager 的 Prometheus 模块提供集群级监控，ceph_exporter 提供进程性能计数器。应用端 SLO 从业务侧测量。 SNIA Swordfish · Ceph Tentacle 监控

数据 关键字段 写入与查询规则
资产和拓扑 source_id、原生 UUID、entity_id、版本、observed_at、valid_from/to、known_from/to 保存资产和关系历史。各页来自同一可核验快照并对账后才发布完整结果。补录时保留旧版本

日志、追踪、支持包 实体、窗口、采集范围、脱敏版本、原文指针、访问范围 站点或区域留存原件，调查返回片段、采样范围与证据 ID
Runbook 和历史案例 产品、型号、固件范围、生效期、原文位置、审核状态 复用现有知识图谱。先按权限、版本和生效时间过滤，再用关键词和语义检索

按来源、信号和分区记录水位，并按查询窗口报告预期资产、实际收到有效样本的资产、缺报列表、最新样本时间、延迟和丢弃量。预期分母用该窗口的资产清单与当前授权范围。区分未上报、过期、不适用和没有权限。分母不清时标覆盖未知；关键 I/O 路径缺样时只报告已观测子集，即使全站覆盖率很高。

断链恢复后先补关键事件和台账，再补明细。缓冲满时记录哪类信号、哪些实体和时间段无法补齐，查询返回 PARTIAL_COVERAGE。统计窗口标明暂定、完整或已修订。补传后发新版本，保留旧报告对应的快照、截止时间和证据 ID，避免事后覆盖原判定。事件按 (source_id, event_id) 去重，其他记录用对应来源的稳定记录键。

3. 业务到物理设备的映射

实体目录分别记录 I/O 路径、放置与保护关系、共享故障域。

关系 典型路径 用于回答
I/O 路径 应用 → 主机/容器 → 卷或共享 → 前端端口 → 控制器/网关 → 池 → 介质 这个慢请求经过哪里？哪些观测点缺失？
放置与保护 卷 → 池 → PG → up/acting OSD，或 卷 → 快照 → 复制对 → 远端恢复点 下线一块盘会失去哪些副本？本次变更会否影响 RPO？
共享故障域 盘 → 盘柜 → 控制器 → 机架/电源/交换机 → 站点 多个告警是否共享背板、链路或供电？能否同批处置？

容器场景沿业务、Pod、PVC、PV 找到 CSI volumeHandle，再用驱动或后端接口查卷的稳定 UUID。FC 按主机 WWPN、交换网络和阵列卷映射核对。Ceph 同时记录 OSD map epoch、up 和 acting，分别核对放置目标和当前服务路径。资产表区分同一物理盘改名、同一槽位换盘和 OSD 重新部署。置信度低的匹配可以查看，须明确标注。执行设备变更前先确认目标。 Kubernetes 持久卷 · Ceph OSD 与 PG 状态

证据服务从认证会话和调查记录绑定授权、事发时点、知识截止和冻结快照。模型可用实体和窗口缩小范围。查询事件和证据按 available_at 筛选，查拓扑匹配有效时间与同一知识截止。observed_at 保留采集端看到的时间。结果带数据新鲜度、来源、单位、原始查询和证据 ID。先查应用与影响范围，再看事发拓扑，缩小到候选路径后读取设备明细。更新关系后仍须能够还原事故当时看到的拓扑。表和索引见进阶篇时态查询。

4. 按设备与故障域诊断

故障面 支持证据与对照 处置与验证
介质、背板与盘柜 查看介质错误和延迟，与同盘柜、同型号的盘比较。多盘同时异常时，重查共享链路、电源和控制器 按物理标识和所在故障域评估风险。核对新盘身份、数据迁移、冗余和业务影响
主机、多路径与 SAN 应用慢且主机队列升高时，分别查写量、块大小、路径切换、交换机拥塞和阵列端口 按实际在用的路径对照，查重试、队列、错误和端到端好请求比例
控制器与共享池 比较控制器 CPU、缓存、端口和池延迟。分别对照同池和异池负载 评估 QoS、安置位置或迁移，追踪受影响的租户和控制器余量
Ceph 恢复与重平衡 查 OSD/PG、up/acting、backfill 和恢复速率。按时间对照前台请求强度、网络和设备队列 在监督下评估后台调度和维护窗口。确认前台恢复、PG 冗余恢复
文件与对象元数据 文件关注客户端、MDS/元数据池与数据路径。对象关注网关、单租户/桶热点、索引与后端 文件操作按 create/stat/readdir 与读写分开验收，对象按 GET/PUT/LIST、状态码和对象大小分开
复制、快照与备份 查复制滞后、恢复点年龄、完整性校验、失败任务、保护目标和远端水位 恢复到隔离目标。检查数据是否一致、应用能否读取，再计算实测 RPO/RTO

处理风险盘时，先核对预测和物理身份，再判断能否更换，最后验收。接收盘寿命预测时记录模型、阈值和预测窗口。Agent 对照同机框信号和历史故障，查是否同时有链路或固件问题。维护前按故障域排序，核对副本、min_size、设备余量、正在恢复的任务、备件和当班工单。作业中监控恢复速度及业务 SLO，结束后核对硬件序列号并验业务读写。升级还需要查兼容矩阵、分批窗口、回退限制和混合版本约束。 Ceph 设备管理 · Ceph OSD 服务 · CephFS 排障 · AWS Backup 恢复验证

算例。 两块盘都报风险。盘 A 的介质错误持续增加，同机框其他盘没有类似变化，可先把 A 列为换盘候选。盘 B 的介质错误平稳，但同机框多盘的链路重试同时增加，需查背板、控制器端口和电源。若 A 所在池仍在恢复，即使预测风险高，也要先复验冗余。若要迁移 12 TB，按有效恢复速率 200 MB/s 估算，理想耗时约 16.7 小时。若维护窗口只有 4 小时，先评估窗口外继续恢复会怎样影响业务和保护，再决定改期或调整批次。

5. Agent 怎样承接不同运维任务

对话、告警和工单可发起多类运维任务。系统根据请求确定任务类型、设备范围、限制和交付物，各技能规定查证顺序和完成条件。

需求 技能输入 Agent 工作 完成交付
“早班巡检哪些站点要关注？” 站点、时间窗、责任队列 先核对数据覆盖，再合并故障域告警、容量风险与保护异常 带优先级、负责人、缺测站点和原始证据的巡检单
“订单写入为什么突然变慢？” 业务、症状、开始窗口 查 SLO 和对照，沿拓扑并行读取主机/网络/阵列，再根据结果挑选反证 影响范围、竞争假设、待验证项和下一步动作
“这批高风险盘能安排本周换吗？” 设备范围、维护窗口、备件 校验身份、风险、冗余、容量和共享故障域，选择可安排批次 能换、应推迟、需人工确认三类对象及各自原因
“池还能撑过采购周期吗？” 池、用量口径、采购/上架时间 查高增长情景、最紧张故障域、快照牵连与回收影响 到阈值区间、提前量、扩容与回收选项
“验证这份备份能在半小时内恢复” 恢复点、目标、RTO/RPO、应用检查 查所有依赖与恢复资格，生成受监督的隔离恢复任务，读取状态与结果 实测时间、恢复点、校验结果、未达项

每个技能记录 skill_id/version、输入与授权范围、可用工具、要找的证据与候选原因、降级条件、时长与工具开销上限、输出结构、退出与交接条件。模型理解请求，选下一项最能区分候选原因的查询，再写说明和计划。规则和统计模型算阈值、趋势、硬盘风险和候选分数。工具网关检查用户身份、租户范围、参数类型和查询预算，并写审计记录。执行器只执行符合策略且已审批的动作版本。

先查业务影响、采集情况和拓扑。再并行查网络、设备和近期变更，按结果补查仍待区分的候选原因。例如 MDS 元数据延迟升高、数据路径稳定时，查 create/stat、缓存回收和目录扫描。证据收集中断时，返回已确认事实、未决假设和下一步。保存技能、规则、模型、证据快照和调用记录，便于比较升级前后的结果。 AWS DevOps Agent 技能与调查模式 · 已有工具契约

写下目标稳定 ID、事实快照、预期配置差异、策略版本、风险限制、验收和补偿办法。把审批绑定到计划哈希、目标和有效期。执行前重读配置、拓扑、容量和冗余，并检查有无维护冲突。用单独的服务身份在规定范围内执行，持续跟踪厂商作业或集群状态。长时任务保存作业 ID、游标、已完成步骤和复查截止时间，工作进程重启后可从记录继续。

客户端超时时，设备可能已经受理请求。提交前保存请求意图和幂等键，重启或超时后按幂等键、作业 ID 和设备状态核对。幂等键绑定不可变的请求内容。接口支持原生幂等时，重试沿用同一个键。只有确认先前动作未受理，才考虑重新提交。无法确认时交给人工。按集群、池或故障域限制并发影响范围，用租约和版本在写入网关校验执行权，拦截已过期的执行者。ONTAP 返回异步 202 表示已受理，完成状态要查设备 job。 ONTAP 异步作业 · Temporal 活动与重试

区域恢复后怎样重新开放写入

区域运维中心不可用时，站点继续采集、缓存和本地告警。备份采集配置、授权和密钥引用、拓扑与事件版本、可追溯的证据目录及原文、审批和作业账本。按目标恢复点先恢复身份和策略，再恢复拓扑、数据及原文引用，最后恢复审批和作业账本。先开放只读查验。能分辨设备已受理、本次待对账和仅观察到目标状态后，再按权限逐批开放写入。

启用备用执行者前，在设备写入网关隔离旧执行者，吊销旧凭据或阻断其直连路径，核对当前执行代次。逐项核对在途和结果未知的请求，避免照旧账本重发。无法证明旧执行者已经隔离、或无法核对原任务的目标保持只读，交人工处理。验例包括区域故障时恰遇“设备已受理、客户端丢了响应”。记录运维平台自身的 RPO/RTO，核对历史证据、审批和作业状态，确认旧执行者写入被拒且设备受理的作业仍只有一个。

验收时读取设备实际状态和业务指标。恢复操作还要确认校验通过、应用可读以及复制进度符合预期。可逆配置按预案撤回。卷扩容等操作按产品能力提前确定补偿、隔离、人工接管或恢复办法。分批部署时用同类设备作对照，并查样本量和查询质量。 Google SRE 金丝雀发布

7. PB 级数据资产运营

要归档、迁移或回收空间时，建立资产清单和生命周期任务。原始数据留在存储侧。区域目录记录文件或对象的版本、大小、时间、租户、保护状态、能取得的访问特征和位置。用访问记录或产品统计判断数据访问热度。先建清单，再用增量事件追踪变化，定期对账找出删除、改名、版本变更和遗漏。记录 inode 时带上所属文件系统和生命周期，路径扫描结果只代表当次观测。

例如归档 200 TB 文件或对象，按持续可用带宽 400 MB/s 计算，搬运约需 139 小时。排期时再计入小文件元数据开销、校验、重试、回读成本和业务高峰。先查访问热度和归属，再排除受保留期限、法务保全、快照引用、合规或恢复时限约束的对象。逐批保存清单、迁移状态和校验结果。策略允许且核验通过后才处理源数据。若快照或版本仍保留，实际释放容量可能和逻辑删除量不同。 Amazon S3 Inventory · S3 Lifecycle 行为

模型上线前的只读验收

先用相同的冻结证据、权限、工具回执和预算比较规则、现用模型和候选模型。固定模型时可另测查询工具带来的改善。验证拒绝越权、忽略晚到证据、缺证时暂缓、超预算退出和报告能追溯到证据。再接现场做影子调查，系统用只读身份运行，记录人工复核时间及对设备接口的压力。事先约定何为通过以及谁签收。聚合或源数据迟到、关键路径全缺而站点平均覆盖仍高、以及跨租户引用都要纳入回归。通过这一轮后再扩大站点；任何写操作另走受监督流程。对标的固定证据评测
