0. 三条流

业务 I/O
  应用 → 客户端/协议网关 → 存储池/PG → OSD/控制器 → 介质

遥测与知识
  指标/日志/事件/变更/拓扑 → 采集与实体对齐
  → 时序库/事件库/历史拓扑/文档索引 → 异常/预测/证据

调查与处置
  投诉/告警 → 工具查询 + 文档检索 → 假设/反证/影响范围
  → 受监督处置 → 业务+冗余双验收 → 回放/学习

业务 I/O 按毫秒计，遥测按秒或分钟计，调查按分钟或小时计。调查时，把三条流中的记录对应到同一个实体和时间窗。

1. 存储语义与服务目标

先看各类请求经过哪些组件。

块：应用 → 客户端队列 → FC/iSCSI/NVMe-oF → 前端端口 → 控制器/缓存
    → 后端 → 池/extent → SSD/HDD

文件：客户端 → 元数据服务（目录/锁/权限）→ 元数据池
      客户端 → 数据服务 → 数据池

对象：S3 客户端 → 网关/认证 → 桶索引/元数据 → 对象数据 → EC/池

Ceph：对象 → hash → PG → CRUSH → OSD 集合 → BlueStore → 介质

块存储要确认何时向主机应答，区分写回和写穿。文件存储分元数据和数据两条路径。对象存储分 GET、PUT、LIST。Ceph 要分别看 PG 的 active/clean/degraded 和 OSD 的 up/down/in/out。按路径找瓶颈。

定义 SLO 时，写清在哪里测、什么算好请求、哪些请求计入分母。

好请求 = 成功 且 端到端延迟 ≤20ms 的写请求
SLO = 好请求数 / 纳入统计的写请求数 ≥99.9%/30 天

直方图的桶边界相同时，先按 le 汇总桶计数，再算全局 P99。流量低的窗口同时报告样本量。

订单写 P99 从 6ms 升到 46ms，IOPS 从 1000 降到 990，错误率略升。IOPS 接近原水平，先查后端队列、backfill、缓存和网络，确认是否是单次请求耗时变长，再判断是否需要扩容。

参考见 Ceph OSD/PG 监控 · Ceph 健康检查 · Prometheus 直方图

2. 采集、时序与海量成本

采集后的数据按用途入库。

设备/主机/应用
   │ 拉取/推送：REST、SNMP、SSH、OTLP、syslog
   ▼
采集与缓冲（去重、水位、背压）
   │
   ├─ 时序库（指标/直方图）
   ├─ 事件库（告警/变更/工单）
   ├─ 对象存储（日志/证据快照）
   └─ 文档索引（Runbook/复盘）

每个指标写清实体、单位和标签。标签放可分组查询的维度，流水号留在日志或事件里。计数器先处理重置再求速率。缺报单独标记。分别记录事件发生的 event_time、采集端看到数据的 observed_at，以及接入服务发布后首次可查的 available_at。应用可用 OpenTelemetry 采集，通过 OTLP 发送到采集器或后端。调查时从监控、日志或追踪后端查询。一半 OSD 停报时，平均延迟可能下降，查覆盖率才能发现样本少了一半。

以每 15 秒采样为例。

50,000 序列 × 86,400/15 = 288,000,000 样本/天
2 字节/样本 ≈ 576 MB/天（单副本）
3 副本 ≈ 1.7 GB/天；一年 ≈ 0.63 TB

可将原始数据保留 7–30 天，聚合数据保留 6–12 个月，天级数据保留 2–5 年。秒级数据用于现场调查。DME 保留分钟级数据 7 天、30 分钟聚合数据 6 个月、天级数据 2 年。5 秒历史按需从设备读取，最长一周。

先查集群趋势，再缩到池、OSD 和变更窗口。每次查询都带上覆盖率和查询预算。若 coverage <80%，只报告已观测子集。

参考见 OpenTelemetry 日志模型 · Ceph Prometheus 模块 · Prometheus 原生直方图

3. 资产、身份与时态拓扑

图里的边表示实体之间的关系。

Workload → Volume/LUN/FS/Bucket
Volume   → Pool → PG → OSD → Disk
Host     → HBA/Port → Switch Port → Array Port → Controller
Array    → Site/Rack/Power/FailureDomain
Change   → Target
Incident → Symptom/Entity
Runbook  → Product/Version/FaultCode/Symptom

给实体记录稳定 ID、别名和生命周期。OSD 数字编号可能复用，因此还要记 UUID。每版关系都记录有效区间、知识区间和来源观测时间。查询“02:16 可见、02:10:30 有效”的拓扑时，分别用 02:10:30 匹配 [valid_from, valid_to)，用 02:16 匹配 [known_from, known_to)。晚到的纠正另存一版，旧版供历史回放。

维护 osd.11 前后各有一版拓扑。

T01 02:00–02:10:30：orders → vol01 → hot → PG1 → osd.11/12/13
T02 02:10:30 起：  orders → vol01 → hot → PG1 → osd.12/17/18

02:16 的报告用 T02 解释 backfill 目标，用 T01 解释维护前的路径。两版都保留。

参考见 Ceph OSD/PG 监控 · AWS DevOps Agent 服务卡

4. 异常检测与告警聚合

检测到异常后，再用持续时间、幅度和样本量决定是否告警。

指标/日志/事件
   ├─ 规则（硬边界/合规）
   ├─ 统计基线（同组/同时段/滚动中位数+MAD）
   ├─ 变化点（CUSUM/PELT）
   └─ 多指标模型（隔离森林/矩阵画像）
        │
        ▼
异常候选 → 持续性/效应量/最小样本 → 告警
        │
        ▼
按拓扑/时间/因果聚合 → 业务 SLO 分级

固定阈值适合容量水位等硬边界。存在周期规律或工作负载变化时，可按组建基线。用 MAD 算异常分数时，要处理分母为零的情况。假设每条序列服从正态分布，按双侧 3.5σ 判定，5 万条序列每轮采样期望约有 23 个单点超限。用历史回放估计实际通知量，计入连续窗口、异常幅度、最小样本量和聚合规则。聚合后保留原始告警 ID 和合并理由。

M01–M05 P99=5,6,5,7,6，中位数为 6，MAD 为 1。M06=33，z=18.21。M07=46，z=26.98。若要求连续 2 点超限，M07 才触发。M07 的好请求比例是 93.27%，M08 对照组是 99.97%。分别记录设备告警和业务受影响的时间，两者可能有先后。

参考见 NetApp DII Monitor · Dell PowerStore 可观测性

5. 容量与硬盘风险预测

先算池还能用多久。

raw × 冗余效率 = 冗余后容量
（冗余后容量 − 单列固定占用）×（1 − 预留比例）= 可分配容量
到阈值天数 = (可分配容量 × 告警比例 − 同口径已用容量) / 净增

硬盘预测按盘、按天组织样本。

样本 = (disk_id, day, 当时可见特征)
正例 = 未来 H 天内真实故障
排除/删失 = 主动更换、迁移、观测结束
切分 = 按时间 + 按设备，禁止同盘泄漏
评测 = PR-AUC、召回@告警预算、提前量、校准

预测容量前，统一冗余后容量和用量口径。已计入用量的占用无需另扣。预留只扣一次，告警比例单独应用。预测硬盘故障前，确认哪些记录是真实故障，哪些在观察结束前换盘、迁移或停止跟踪。比较厂商的“14 天”“30 天”和“健康度 60 分”时，分别核对预测窗口和评分定义，再判断能否与故障概率对应。

原始容量 2,400 TB，EC 8+2 之后有 1,920 TB 冗余后容量。无另列的固定占用，扣一次 5% 预留后可分配 1,824 TB，再按该容量的 95% 告警。已用 1,500 TB、每天净增 6 TB 时，约 38.8 天到阈值。每天净增 3 或 9 TB 时，分别约 77.6 或 25.9 天。10,000 块硬盘，AFR 2%、召回率 80%、精确率 20% 时，平均每天有 2.19 次告警，其中误报 1.75 次。

参考见 FAST ’20 硬盘预测 · Backblaze Drive Stats

6. 根因、证据与反证

沿着事发时的拓扑，找发生在症状前的变更。

症状/影响范围
   │
   ├─ 时间上先于症状的变更
   ├─ 事发拓扑可达的实体
   ├─ 同故障域共现异常
   ├─ 已知故障树/历史工单
   └─ 对照（未受影响业务）
        │
        ▼
候选假设 → 每项写：支持/反证/鉴别查询/停止条件
        │
        ▼
根因 + 传播 + 系统性原因（三层）

要判断因果，检查事件是否先于症状、事发路径是否连通、压力越大时症状是否越重、症状是否只出现在相关范围，以及对照组和干预后的结果。用故障树查已知设备故障，用因果图查共同原因和传播路径。LLM 可从日志或工单提出假设，再由证据验证。

维护 osd.11 后，怀疑 backfill 与前台写争用。E01/E02/T02/M06/M07 支持 H1。还缺实际服务的 OSD、各 OSD 的队列和恢复速率。也可检查限制 backfill 后 P99 是否下降。E03 的备份在另一站点，T03 未记录共享路径，M08 对照组正常。H2 的可能性较低。已观测的 TCP 重传持平，交换机端口丢包仍待查。

参考见 Ceph OSD/PG 监控 · RCAEval

7. 大模型怎样查数据和手册

先查采集覆盖率，再判断业务影响和可查的路径。

症状/窗口/权限
   → 查采集健康/覆盖率
   → 查业务影响（SLO）
   → 查事发拓扑
   → 查变更/事件
   → 生成候选假设
   → 对每个假设选最有区分度的查询
   → 证据足够/预算耗尽/需人工 → 报告/未决

每个工具都要约定输入、输出、时间口径、权限、错误类型和查询 ID。服务端绑定身份、授权、冻结快照和 knowledge_cutoff。模型只可收窄范围。查事件、证据和拓扑时共用同一知识截止，事件按可信来源和原生事件 ID 去重。

query_metric(entity_id, metric, start, end, step)
  → unit, samples, missing_intervals, coverage, query_id, source

RAG 先按 ACL、租户、产品、型号、版本、故障码、审批状态和生效时间筛选，再用关键词和向量检索并重排。文档冲突时，列出各自的版本、出处和适用范围。证据对象带 evidence_id/query_id/source_id/entity_id/window/observed_at/available_at/quality/payload_ref。报告分开写事实、推断和未决问题。

用 02:16 的快照直接问模型，模型可能把 P99 的 46ms 写成“平均值”。用工具查 M06/M07，可拿到窗口、单位、覆盖率和查询 ID。验证器还能拒绝 E04，因为这条证据在 02:18 才可见。实验中的 observed_utc 表示可见时间，生产用 available_at 单列。

参考见 Fusion MCP 指南 · DII MCP · AWS 服务卡

8. 处置、验证与评测

执行前复核状态，执行后同时检查业务和数据保护。

调查结论
   → 变更请求（目标/前置/预期/幂等/回滚/观察窗/审批）
   → 再次读取状态（拓扑/授权/冗余）
   → 执行（A2/A3/A4 分级）
   → 业务 SLO 验收 + 冗余/耐久性验收
   → 写回事故库/评测集

调查与处置分开授权。读工具默认开，写工具默认关。每次变更要有幂等键、回滚方案、影响范围和观察窗。业务恢复后，还要查副本、复制和备份是否恢复。

Ceph 回放模拟调整调度后，02:25 窗口的写 P99 为 14 ms，好请求比例约 99.95%。业务窗口已达标，但仍有 11 个退化 PG。继续查冗余、恢复进度和新故障域的压力。实验验收

用同一快照比较规则、规则+统计、Agent+工具、Agent+工具+拓扑/RAG。评估检测结果、根因 Top-k、证据正确率、缺数据暂缓率、越权拒绝率和成本。回放集覆盖正常、真实故障、缺数据、数据晚到和负对照案例。按事故、时间和集群切分，隐藏答案。

参考见 Ceph mClock · AIOpsLab · RCAEval · ORCA-bench

9. 多集群与落地

站点、区域和全局各保存不同粒度的数据。

站点边缘：就近采集、缓冲、脱敏、粗聚合、断链续传
区域中心：跨站资产目录、拓扑快照、证据索引、查询路由
全局：策略、模型、评测、审计（不存明细）

尽量在站点内执行查询，按需回查明细。断链时记下采集进度，恢复后补数并标记迟到。在采集层确定租户隔离和数据驻留规则。统一维护目录，证据明细按需查询。

各阶段按交付项验收。

阶段 交付 验收
0–1 月 实体表、SLO、覆盖率、事件时间 能查到事发状态并列出缺失数据
1–3 月 规则+稳健基线、告警聚合、时间线 每集群每天误报数在预算内，MTTD 下降
3–6 月 时态拓扑、变更关联、证据对象、RAG 记录前三个根因候选的命中率，每条证据可复核
6–12 月 工具层/MCP、Agent 调查、回放评测 同一快照可复现，数据不足时暂缓下结论
12 月+ 受监督处置、双验收、有限自治 越权为零，可演练回滚
