一句话立场：存储专家系统的难点不在“让模型说得像专家”，而在让每句结论都能回到一个带时间、实体、单位和出处的证据，并且知道自己在什么条件下必须沉默。海量存储把这件事放大了：实体多、指标多、故障域深、处置代价不对称。

0. 先建立坐标系：专家系统的五个面与五级成熟度

一个可运行的存储专家系统至少有五个面。少任何一面，系统都会退化成“会说话的看板”。

面 回答的问题 典型组件 失败表现
状态面 现在和当时发生了什么？ 指标、日志、事件、变更、拓扑快照 数据缺失被当成“变好了”
知识面 这类现象通常意味着什么？ 本体、故障模式、Runbook、版本约束 检索到过期或不适用的手册
推理面 哪条因果链最可信？还缺什么证据？ 规则、统计、因果图、故障树、LLM 规划 把相关当因果，或只给一个答案
行动面 能不能动、谁来批、怎么回滚？ 工单、审批、编排、幂等接口 业务恢复了，冗余却还没恢复
评测面 这套系统到底比人强在哪？ 回放集、盲评、负对照、成本账 只展示成功案例

成熟度不要按“模型多聪明”划分，而要按证据强度和授权范围划分：

级别 能力 必要证据 授权
L0 可视 看到资源、指标、拓扑 实体 ID、单位、采集时间 只读
L1 检测 发现异常并分级 基线、样本量、覆盖率、误报预算 只读 + 通知
L2 诊断 给出候选根因与反证 时间 precedence、拓扑可达、对照、证据出处 只读 + 建议
L3 处置 执行可逆变更并验证 前置条件、幂等键、回滚、双验收 人工审批 + 受监督执行
L4 自治 在限定域内闭环 L3 的全部 + 长期回放 + 熔断与审计 白名单 + 预算 + 熔断

绝大多数团队应该先把 L1/L2 做扎实。没有 L2 的证据链，L3 只是把人工误操作换成了自动误操作。

存储还有四个硬约束，决定了它的推理和互联网微服务不一样：

  1. 耐久性优先于性能。延迟升高可以忍，数据丢了不能忍；任何“优化”都要先问副本、校验、快照和恢复窗口。
  2. 故障域是物理的。控制器、机框、机柜、站点、双活对、EC 条带，决定了“影响范围”不是一个逻辑标签，而是一组共享失效单元的集合。
  3. 后台任务会反噬前台。重建、backfill、scrub、GC、快照删除、克隆、迁移都会争用同一批 CPU、内存、网络和介质。
  4. 版本和配置是语义的一部分。同一个告警码在 V6 与 V7、不同补丁、不同 license 下可能含义不同；Runbook 不标版本就是隐患。

0.1 经典专家系统与现代 Agent 的分工

“专家系统”这个词有两代含义，混用会导致架构错位。

经典专家系统（MYCIN 时代）由四部分组成：知识库（事实 + 规则）、工作记忆（当前事实）、推理机（前向/后向链）、解释器（为什么得出这个结论）。它的优点是确定性、可审计、可解释；缺点是知识获取瓶颈、规则脆弱、难处理非结构化输入和大规模不确定性。

现代 LLM Agent 由模型、工具、记忆、规划器、验证器组成。优点是能读日志/工单/手册、生成假设、用自然语言交互；缺点是幻觉、非确定、成本高、权限风险。

存储场景的正确组合不是二选一，而是：

确定性内核：规则、阈值、故障树、SLO、权限、动作契约、验证器
概率性外壳：异常检测、预测、LLM 假设生成、RAG 检索、报告组织

具体分工：

职责 交给谁 原因
硬约束（副本数、SLO、权限、窗口） 规则/策略引擎 必须确定、可审计
异常/预测 统计/ML 需要从数据学分布
候选根因 故障树 + 拓扑 + 因果图 需要领域机制，不是语言模式
假设生成/证据选择 LLM 擅长非结构化线索和下一步查询
事实陈述 工具/数据库 模型不应“回忆”设备状态
结论校验 确定性验证器 引用、单位、时间、权限、数值
最终动作 人或受监督工作流 代价不对称

一句话：LLM 不负责“知道”，负责“提问和解释”；系统负责“证明”。 DME 的故障树/智能分析是确定性内核，运维助手/故障智能体是概率性外壳；它缺的正是两者之间的开放证据层和工具契约。

1. 一条 I/O 的完整生命周期

1.1 块存储：从 initiator 到介质

一次块写请求的路径可以粗分为：

应用 write()
  → 文件系统 / 数据库页缓存
  → 多路径（DM-Multipath）与 HBA 队列
  → FC/iSCSI/NVMe-oF 织物
  → 存储前端端口 → 控制器
  → 写缓存（镜像 / NVRAM / 掉电保护）
  → 后端总线 → 存储池 / extent
  → SSD 或 HDD → 介质队列 → 完成

读路径在缓存命中时很短，未命中时要走后端；预取、读缓存和顺序性会显著改变尾延迟。写路径的关键是什么时候向主机确认：写回（write-back）在缓存镜像完成后就确认，写穿（write-through）要等介质。写回带来低延迟，也带来掉电保护和缓存降级的问题。

把端到端延迟拆开，比只看一个 P99 有用得多：

T_end2end = T_client_queue + T_fabric + T_frontend + T_cache_lookup
          + T_backend_queue + T_media + T_retry + T_software_overhead

每一段都要有独立的测量点。缺少某一段时，结论必须降级为“在已观测段内，瓶颈位于 X 之前/之后”，而不是“根因是 X”。

队列论给出一个非常有用的直觉。对 M/M/1 队列，利用率 ρ、服务时间 S：

平均排队时间 W = ρS / (1 − ρ)
平均响应时间 R = S / (1 − ρ)
利用率 ρ 响应时间是服务时间的倍数
50% 2×
70% 3.3×
80% 5×
90% 10×
95% 20×

真实系统不是 M/M/1，SSD 有内部并行、控制器有多队列，不能用这个公式算绝对值；但它解释了为什么“利用率只涨了 10 个点，延迟翻倍”。也解释了为什么在 85% 利用率以上做容量规划很危险：余量不是线性的。

IOPS、带宽和块大小的关系必须写清楚：

IOPS = 带宽 / 块大小

4 KiB 随机读 100 万 IOPS 约等于 3.8 GiB/s；1 MiB 顺序读 3.8 GiB/s 只有约 3,900 IOPS。把两者混在一个“性能”指标里，结论一定错。

SSD 还有垃圾回收（GC）、写放大（WA）和预留空间（OP）。持续随机写会把可用块耗尽，GC 与前台写争用，尾延迟出现长尾；写放大让“业务写了 1 GiB”变成“介质写了 2–4 GiB”。这些都要在看 IOPS 的同时看介质写量、GC 次数、磨损和预留。

1.2 文件存储：元数据路径与数据路径

文件存储至少有两条路径：

客户端 → 元数据服务（MDS / 文件系统管理） → 目录、锁、权限、布局
客户端 → 数据服务（DS / 存储节点）       → 实际读写

元数据操作（create、stat、readdir、rename、unlink）和数据操作的成本模型不同。小文件、深目录、大量并发 create、目录热点、锁竞争，都会让元数据路径先于数据路径成为瓶颈。NFS 的 delegation/lease、SMB 的 oplock、客户端的 attribute cache，会改变“看起来的延迟”。客户端重连、会话恢复、锁回收也会在故障后制造第二波压力。

因此文件存储的 SLO 至少要拆成：元数据操作延迟、数据读写延迟、元数据 IOPS、数据带宽、错误码分布。只报一个“文件系统延迟”无法定位。

1.3 对象存储：网关、索引与后端

对象路径通常是：

S3 客户端 → 网关 / 负载均衡 → 认证与桶索引 → 元数据服务
          → 对象数据落到池 / 纠删码条带 → 后端节点

对象存储的尾延迟常来自：网关排队、桶索引热点、单对象过大、multipart 分片不均、LIST 操作扫描、慢节点拖尾、EC 重建。S3 的 5xx、SlowDown、连接复用和重试策略会把后端的一次抖动放大成客户端的长尾。对象存储的 SLO 要按操作类型和状态码拆分，不能把 GET 和 LIST 混在一起。

1.4 分布式存储：以 Ceph 为例

Ceph 的 RADOS 层：

对象 → pool → PG（placement group）→ CRUSH 映射 → OSD 集合
OSD → BlueStore → 块设备 → 介质

几个必须区分的状态：

  • active：PG 可以服务；clean：对象已达到配置的副本数。active+clean 是期望的 PG 状态，完整性仍要看 scrub 与其他健康项。
  • up/down：OSD 进程是否可用；in/out：是否参与数据放置。两组状态要同时保留。
  • degraded：部分对象未达到期望冗余；undersized：PG 的副本集合小于期望；stale：PG 映射变更后 Monitor 尚未收到其状态更新。
  • recovering / backfilling：恢复与回填；scrubbing / deep-scrub：校验。

维护中 OSD 下线后仍可能为 in。若它被标记 out 且 PG 映射改变，可能触发 backfill，和前台写竞争网络、CPU 和介质资源。P99 与队列上升、提交 IOPS 接近基线，支持争用假设。仍应检查块大小、读写比例、请求并发和更细粒度的突发。 Ceph PG 状态 · Ceph OSD/PG 监控

Ceph Tentacle 的 mClock 对客户端、后台 recovery、后台 best-effort 三组分配保底、上限与权重。Backfill、scrub、快照裁剪和 PG 删除都归入 best-effort。调度变更应核对版本、当前 profile、参数是否生效与冗余状态。 Ceph mClock

1.5 尾延迟放大：为什么平均值会骗人

一个请求要扇出到 k 个下游，每个下游独立地有 1% 的概率超过自己的 P99。整个请求至少命中一个慢下游的概率：

P(至少一个慢) = 1 − (1 − 0.01)^k
k 概率
10 9.6%
100 63.4%
1,000 99.996%

所以“每个服务 P99 都达标”不等于“端到端 P99 达标”。如果每个下游是 P99.9，k=1000 时仍有 63.2% 的请求会碰到至少一个慢调用。存储侧的扇出（多副本、EC 条带、多路径、元数据与数据分离）也在制造同样的放大。

还有两个常被忽略的效应：

  • 协调遗漏（coordinated omission）：压测工具在目标延迟被突破后降低发送速率，会系统性低估尾延迟。记录“计划发送时间”和“实际发送时间”的差，才能得到真实的服务时间分布。
  • 后台任务的长尾：GC、重建、快照、scrub 的延迟尖峰会污染 P99；如果采样窗口刚好覆盖，结论会随窗口漂移。

1.6 SLO：定义、聚合与燃烧率

SLO 的三要素：测量点、好事件、分母。以订单写请求为例：

好请求 = 成功 且 端到端延迟 ≤ 20 ms 的写请求
SLO = 好请求数 / 纳入统计的写请求数 ≥ 99.9% / 30 天

错误预算：

预算 = (1 − SLO) × 总请求数
请求量近似均匀时，99.9% / 30 天 ≈ 43 分 12 秒的完全不可用等价时间
同一假设下，99.95% / 30 天 ≈ 21 分 36 秒

燃烧率（burn rate）：

burn_rate = 观测窗口内的错误率 / (1 − SLO)

燃烧率为 1 且持续整个 SLO 周期时，刚好耗尽该周期预算。请求量近似均匀时，14.4 倍燃烧率持续 1 小时会用掉 30 天预算的 2%。流量不均时，用观测窗内坏请求数除以整个周期的预算请求数。多窗口规则可要求 1 小时和 5 分钟燃烧率都超过 14.4。 Google SRE

分位数不能直接平均。 三个客户端各自 P99 = 10/20/30 ms，不代表全局 P99 是 20 ms；全局 P99 取决于各客户端的请求量分布和尾部形状。正确做法是保留相同桶边界的直方图，按桶求和后再算分位：

histogram_quantile(
  0.99,
  sum by (le) (rate(request_duration_seconds_bucket[5m]))
)

如果没有桶，只有各客户端的预计算分位，就只能报“各客户端分位”，并明确不能合成全局分位。低流量窗口还要报样本量；100 个请求的 P99 只是一个请求的延迟，不应该触发事故级告警。

1.7 失败模式与验收

失败模式 后果 纠正
在阵列侧测延迟，却宣称应用 SLO 漏掉客户端队列、网络、重试 应用侧埋点 + 端到端分解
对客户端 P99 取平均 全局分位失真 合并直方图桶
分母只算成功请求 错误被隐藏 分母含错误和超时
忽略低流量窗口 1 个慢请求触发告警 最小样本量 + 置信区间
把 IOPS 当性能 块大小变化时结论反转 IOPS/带宽/块大小一起看
只看前台，不看后台 恢复任务被忽视 恢复速率、队列、介质写量

练习（答案见答案册第 1 部分）：给一个 3 客户端、不同请求量的场景，手工合并直方图并计算全局 P99；再写出一次 Ceph 维护导致的延迟分解，标出哪一段有直接证据、哪一段只能推断。

2. 遥测：数据模型、采集与海量成本

2.1 信号分类

信号 适合回答 典型来源 注意

2.2 指标模型与基数

一条时间序列由指标名和标签集唯一确定：

storage_pool_used_bytes{site="sh", cluster="ceph-a", pool="hot", unit="byte"}

标签设计的铁律：标签是维度，不是身份流水号。把 request_id、session_id、文件名、卷快照 ID 放进标签，会制造无限基数。实体身份用稳定的 entity_id，把可变的显示名、别名、序列号放在实体表里。

基数估算：

序列数 ≈ 实体数 × 每实体指标数 × 维度组合数

10,000 个 OSD × 100 个指标 = 100 万序列；15 秒采样就是每天 57.6 亿样本。即使压缩到 2 字节/样本，也是每天 11.5 GB（单副本），还没算索引和查询放大。海量存储的“海量”首先体现在这里。

2.3 容量与成本估算

以 50,000 条活跃序列、15 秒采样为例：

每天样本数 = 50,000 × 86,400 / 15 = 288,000,000
按 2 字节/样本压缩 ≈ 576 MB/天（单副本）
按 8 字节/样本 ≈ 2.3 GB/天（单副本）
三副本 ≈ 1.7–6.9 GB/天
一年 ≈ 0.6–2.5 TB（三副本，未计索引）

看起来不大，但这是一个集群的原始指标。再乘上设备数、租户、日志、追踪、拓扑快照和查询副本，成本会迅速上升。分层的常见做法：

层 粒度 保留 用途
原始 15s–1min 7–30 天 事故取证、短窗口
聚合 5–30min 6–12 个月 趋势、容量、周同比
日级 1 天 2–5 年 容量规划、审计
事件/变更 事件粒度 多年 根因、合规
原始日志 原始 7–30 天，冷存更久 深度取证

DME 25.1.0 白皮书的实际保留策略可以作为产品参照：分钟级保存 7 天，30 分钟聚合保存 6 个月，天级聚合保存 2 年；5 秒历史性能数据不落 DME，而是按需从 Dorado V6+ 设备侧读取，最长一周。这个设计说明：秒级数据用于现场，不用于长期存储。详见外部资料拆解 §11。

2.4 时间语义：事件时间、观测时间、知识时间

这是存储取证最容易错的地方。至少有三个时间：

  • event_time：事情实际发生的时间（设备时钟、日志时间）。
  • observed_time：采集/上报系统看到它的时间（可能晚于事件时间）。
  • knowledge_time：这条记录进入证据库、可被查询的时间。

回放一个 02:16 的事故时，只能使用 knowledge_time ≤ 02:16 的数据。否则模型会“未卜先知”：用 02:18 才上报的应用日志解释 02:16 的告警。拓扑同理：要按事件时间选择当时有效的版本，而不是用当前拓扑。

晚到数据、时钟漂移、补数、重复上报都要处理：

  • 用 event_id 做幂等，重复写入不产生双份。
  • 用水位（watermark）判断“这个窗口是否还可能来数据”。
  • 计数器重置时先识别重置点，再算速率；不要直接 rate() 跨重置。
  • 缺失不等于 0。缺失要进入“数据质量”维度，并影响结论强度。

2.5 缺失机制与选择偏差

缺失至少分三类：

  • 完全随机缺失（MCAR）：丢包与值无关。
  • 随机缺失（MAR）：缺失与已观测变量有关（例如高负载时采集器更容易丢）。
  • 非随机缺失（MNAR）：缺失与未观测的值有关（例如设备快坏了，agent 先挂了）。

存储里最常见的是 MAR/MNAR。一个典型陷阱：一半 OSD 停止上报，剩下健康 OSD 的平均延迟下降，dashboard 看起来“变好了”。正确做法是同时看采集覆盖率：

coverage = 实际上报的期望实体数 / 期望实体总数

并把 coverage 作为一等指标告警。任何聚合都要带 coverage；覆盖率不足时，均值/分位只能作为“已观测子集”的描述，不能代表全局。

3. 资产、身份与时态拓扑

3.1 身份比名称重要

存储实体的“名字”极不稳定：主机名会改，LUN ID 会重用，OSD 数字编号会在重建后复用，WWN 可能因为换卡改变，容器 Pod 名每次部署都不同。专家系统必须建立稳定身份 + 别名 + 生命周期：

entity_id = tenant / cluster_fsid / entity_type / native_uuid
alias     = 显示名、旧主机名、序列号、WWN、IP、K8s UID
lifecycle = 上线、维护、下线、退役

如果只能拿到数字编号（例如 osd.11），必须同时保存 UUID 和“该编号在这一代生命周期内有效”的区间。否则历史事故会被错误地归到新设备上。

3.2 双时态：有效时间与知识时间

每条拓扑边的修订记录应包含以下字段：

edge: (src, dst, relation)
valid_from, valid_to      # 这条关系在现实中何时有效
observed_at               # 观测系统何时看到它
known_from, known_to      # 该修订何时对调查者可见
source, confidence        # 谁说的、有多确定

查询“02:16 时刻的拓扑”要用半开区间：

SELECT * FROM edge
WHERE src_id = :workload
  AND valid_from <= :t AND (valid_to IS NULL OR :t < valid_to)
  AND known_from <= :knowledge_cutoff
  AND (known_to IS NULL OR :knowledge_cutoff < known_to);

有效区间决定关系在哪个事发时点成立，知识区间决定调查当时能看到哪个修订。观测时间保留为来源证据。例如 02:20 才得知某边于 02:10 结束，关闭旧修订的知识区间并新增一条含正确结束时间的修订。旧修订保留原有效区间，所以 02:16 的调查仍可复现。实现见进阶篇 §7.1。

3.3 图模式

存储依赖图至少有这些节点和边：

Workload → Volume/LUN/FileSystem/Bucket
Volume   → Pool → PG → OSD → Disk
Host     → HBA/Port → Switch Port → Array Port → Controller
Array    → Site/Rack/Power/FailureDomain
Snapshot/Clone/Replication → Source/Target
Change   → Target
Incident → Symptom/Entity
Runbook  → Product/Version/FaultCode/Symptom

边的语义要明确方向：runs_on、maps_to、replicates_to、depends_on、hosted_by、protects。不要把“网络可达”和“数据依赖”混成一种边；前者影响连通性，后者影响数据完整性。

3.4 实现选择

3.5 实体解析与证据置信

真实环境里同一个东西会有多个名字：多路径让一个 LUN 出现多个设备名；NPIV 让一个端口有多个 WWPN；容器里 PVC/PV/StorageClass 多层抽象；第三方阵列的序列号格式各不相同。实体解析要输出置信度，并把“无法解析/歧义/拓扑过期”作为有类型的结果返回，而不是静默丢弃。

3.6 事发拓扑重建：一个例子

事故：02:10:30 维护 osd.11 所在主机，PG 重映射到 osd.17/18，02:14 起订单写 P99 升高。

时间 拓扑版本 用途
02:00–02:10:30 orders → vol01 → hot → PG1 → osd.11/12/13 解释维护前路径
02:10:30 起 orders → vol01 → hot → PG1 → osd.12/17/18 解释 backfill 目标与前台争用

如果 02:16 的报告使用第二版拓扑，它能解释“为什么是 osd.17/18 忙”；如果使用第一版，它会错误地怀疑 osd.11。两版都要保留，并标注有效期。PG 映射还要带 CRUSH map epoch 或快照 ID，否则无法证明“当时确实是这组 OSD”。

3.7 知识图谱：Runbook 也是有时态的实体

知识图谱不只是设备关系。Runbook、故障码、产品版本、症状、处置步骤、审批状态、适用机型，都是带版本的实体。一次检索要同时过滤：

产品 = OceanStor Dorado
版本 ∈ [V6.1.6, V7.0)
故障码 = 0x...
审批状态 = 已发布
生效时间 ≤ 事发时间
ACL 允许当前用户

冲突的 Runbook 不能“让模型选一个”，而要返回多个版本、适用范围、出处和冲突点。知识图谱的价值在于把“适用性”变成可查询的边，而不是把文档塞进向量库。

4. 异常检测与告警工程

4.1 先选信号，再选算法

异常检测的第一问题不是“用什么模型”，而是“这个信号能不能支撑这个结论”。

信号 适合的检测 不适合
低基数、平稳指标 阈值、滚动基线、CUSUM 深度模型（样本不够）
强季节、日/周周期 STL 分解、季节基线 固定阈值
多指标组合异常 隔离森林、矩阵画像、AutoEncoder 单指标阈值
计数器/速率 先做重置处理，再检测 直接对原始计数器建模
事件/日志 模板、频次、序列模式 只看单条日志
高基数实体 分组基线 + 分层模型 全局一个阈值

规则不是“低级”，而是可解释、可审计、可回归的基线。任何 ML 检测都应该先和规则并跑，证明它在同一事故集上更好，否则只会增加运维负担。

4.2 稳健基线：中位数与 MAD

对一组基线样本 x1..xn：

median = 中位数(x)
MAD    = 中位数(|xi − median|)
z      = 0.6745 × (x − median) / max(MAD, ε)

0.6745 让 MAD 在正态分布下与标准差可比。MAD 为 0 时（例如量化到 1 ms 的平稳序列），分母要用 ε 或退化为 IQR，否则一个 1 ms 的抖动会产生巨大的 z。

用实验室数据验算：M01–M05 的 P99 为 5, 6, 5, 7, 6，中位数 6，绝对偏差 1, 0, 1, 1, 0，MAD = 1。M06 = 33 ms：

z = 0.6745 × (33 − 6) / 1 = 18.21

M07 = 46 ms：

z = 0.6745 × (46 − 6) / 1 = 26.98

数值上很显著，但要注意：z 大不等于影响大。如果基线是 0.1 ms、MAD 是 0.01 ms，涨到 0.2 ms 也会有巨大的 z，但业务可能无感。所以还要加效应量门槛（例如绝对增量 ≥ 5 ms 或相对倍数 ≥ 2）和持续窗口（连续 2 个采样点）。实验室里 M06 已超阈值，M07 再次超过，才构成“持续异常”。

4.3 变化点与累积和

CUSUM 适合检测“均值发生小幅持续偏移”：

S_t = max(0, S_{t−1} + (x_t − μ0 − k))
若 S_t > h，报警

k 是容忍偏移（通常取 0.5σ），h 是决策阈值（通常 4–5σ）。它对缓慢劣化（例如 SSD 磨损、端口误码、容量泄漏）比单点 z 更敏感。PELT/Bayesian change point 适合离线分段，用来回答“这次事故从哪一刻开始”。

4.4 多重检验：50,000 条序列的假阳性

如果 50,000 条序列相互独立、服从正态，使用双侧 3.5σ 阈值，单条序列单次误报概率约 0.000465。每采样一次，期望误报：

50,000 × 0.000465 ≈ 23.3 条/次

15 秒采样对应每天约 13.4 万次单点超限。给定相同的边际误报概率，序列间相关性会改变超限聚集程度，期望次数仍可相加。持续窗口与告警聚合会改变实际通知量，连续采样相关时应通过正常窗口回放估计。

常用控制手段：

  • 连续 N 个点超限才报（降低瞬时噪声）。
  • 要求效应量超过业务可感知阈值。
  • 按实体组做分层检验，再用 FDR/Bonferroni 控制组内误报。
  • 对同源序列做聚合，先在组级别检测，再下钻。
  • 维护“已知良性模式”白名单，但要有过期时间和审计。

4.5 告警聚合与因果抑制

聚合的目标不是“少报”，而是“一页纸说清一个事故”。可以按三个维度合并：

  • 拓扑：同一故障域、同一共享依赖、同一路径。
  • 时间：窗口重叠、传播延迟在合理范围内。
  • 因果：父告警/子告警、上游/下游、根因/衍生。

但聚合有风险：把两个独立根因合成一个，会掩盖第二个故障。因此要保留原始告警 ID、聚合规则版本和“为什么合并”的理由。DME 的告警规则里有屏蔽、闪断/振荡、汇聚、相关性、自动确认、重定义、远程通知等，这是很成熟的产品化做法；但相关性规则是用户定义的父子关系，不是自动学出来的因果图。详见外部资料拆解 §11。

4.6 影响分级：用 SLO 而不是拍脑袋

告警级别应该由业务影响决定，而不是设备型号。最简单的做法是看 SLO 燃烧率：

severity = P1  若 1h burn_rate ≥ 14.4 且 5m burn_rate ≥ 14.4
         = P2  若 6h burn_rate ≥ 6
         = P3  若 3d burn_rate ≥ 1

再叠加冗余状态：如果业务 SLO 还在，但冗余已经 degraded，应该是“高优先级修复、非事故”；如果业务 SLO 破了且冗余不足，才是“事故”。这比“硬盘告警 = P1”合理得多。

5. 预测：容量、性能与介质

5.1 容量预测的账本

容量预测最常见的错误不是模型，而是口径。至少分清：

raw       = 裸容量
usable    = raw × 冗余效率 × (1 − 预留)
usable    = 副本：raw / 副本数
          = EC k+m：raw × k / (k + m)
effective = usable − 快照 − 克隆 − 元数据 − 回收站 − 安全水位

例子：10 个节点 × 12 块 20 TB = 2,400 TB raw。EC 8+2 的效率是 80%，可用 1,920 TB；再留 5% 安全水位，有效 1,824 TB。若当前已用 1,500 TB、净增 6 TB/天：

到 95% 水位的天数 = (1,824 × 0.95 − 1,500) / 6 ≈ 38.8 天

如果净增是 3 或 9 TB/天，分别是 77.6 天和 25.9 天。报区间，不报单点；并把“扩容/清理/生命周期变更”作为切换点，切换后重新拟合。

5.2 模型与回测

方法 适合 注意
稳健线性回归 稳定增长 对突变不敏感
分位数回归 要区间 需要足够样本
ARIMA/SARIMA 自相关、季节 参数敏感、解释弱
季节分解 + 趋势 日/周周期 需要至少数周
结构模型/Prophet 类 节假日、变点 不要盲信默认
集成/融合 多模式 可解释性下降

回测要用滚动原点（rolling origin）：在历史每个时点只用当时可见的数据训练，预测未来 H 天，再向前滚动。指标：

MAE / MAPE / RMSE        # 点预测
pinball loss             # 分位预测
区间覆盖率               # 80%/95% 区间是否覆盖
跨阈值时间误差           # 预测“何时到 90%”的误差天数

随机切分会让未来信息泄漏到训练集，指标虚高。

5.3 性能预测与动态阈值

性能预测比容量难，因为负载会变、季节性强、故障会突变。常见做法是：

  • 用过去 1 个月预测未来 2 周（DME 白皮书披露的做法）。
  • 用过去 30 天预测未来 1 天，做“预测对比”健康扣分。
  • 用同工作负载、同时段的分位数作为动态阈值。
  • 对突变用变化点检测，而不是让模型硬拟合。

预测的价值不是“精确到毫秒”，而是提前发现趋势性劣化：缓存命中率持续下降、端口误码上升、GC 时间变长、容量斜率变陡。这些都比单点延迟更有预警意义。

5.4 硬盘故障预测：标签、截尾与竞争风险

硬盘预测的第一个问题是标签：

样本 = (disk_id, day t, 当时可见的特征)
正例 = 该盘在 (t, t+H] 内发生“故障事件”
负例 = 该盘在 (t, t+H] 内没有故障，且观测未截尾
排除 = 主动退役、迁移、数据销毁、观测结束

如果“主动换盘”被当成故障，模型会学到运维策略；如果观测结束的盘被当成负例，会低估风险；如果同一块盘的相邻日期同时进入训练和测试，会泄漏。正确切分是按设备 + 按时间：训练集和测试集不能共享同一块盘的同一次故障。

特征用当时可见的 SMART/NVMe 指标及其变化率：重分配扇区、待定扇区、不可纠正错误、命令超时、CRC 错误、磨损、通电小时、温度、型号、固件、批次。树模型（GBDT）通常比 Logistic 回归强，但可解释性和校准要单独做。

评测不要只看 AUC。类别极不平衡时，看：

PR-AUC
召回率 @ 告警预算
每千盘日误报数
提前量分布（lead time）
概率校准（Brier / 校准曲线）

告警预算的算法：10,000 块盘，年故障率 2% → 每年 200 次故障，约 0.55 次/天。若召回 80%、精确率 20%：

TP/天 = 0.55 × 0.8 = 0.44
总告警/天 = 0.44 / 0.2 = 2.2
误报/天 = 1.76

如果精确率只有 5%，总告警 8.8 条/天，运维就会开始忽略。先定运维能处理的告警量，再反推阈值，比追求高召回更现实。

5.5 产品预测能力的读法

DME 25.1.0 白皮书披露了几组不同口径的能力，读的时候不要混为一谈：

  • 容量：最多用过去 180 天，预测未来 1 年，日粒度；安装后需 14 天且至少 11 天有效数据；算法是 SVM（多核）、ARIMA、对数回归、线性回归的融合。
  • 性能：过去 1 个月预测未来 2 周；健康度里用过去 30 天预测未来 1 天做“预测对比”；算法是 Lasso、岭回归、随机森林的融合。
  • 硬盘健康度：每天凌晨预测未来 14 天健康度，低于 60 分判为风险盘；支持 SSD、NVMe SSD、SATA/SAS HDD、NL-SAS。
  • 硬盘故障：对希捷/日立 SAS HDD，基于 10 天 SMART 预测未来 30 天是否故障。
  • DME IQ 页面：提前 14 天硬盘故障、提前 2 个月性能趋势、提前 365 天容量趋势。

这些数字的定义、分母、故障类型、误报率、测试集都没有公开，不能直接当作采购验收值。尤其“健康度 60 分”是产品评分，不是校准后的故障概率；“14 天”和“30 天”是不同介质、不同模型、不同目标，不能相加或互换。详见外部资料拆解 §11。

5.6 漂移与反馈回路

模型上线后，数据分布会变：新固件、新批次、新 workload、新业务峰谷、运维策略变化。监控：

  • 特征分布漂移（PSI/KL/KS）。
  • 预测分布漂移。
  • 校准漂移（预测 20% 的盘实际故障率是多少）。
  • 告警处置结果（真故障/误报/主动更换）。

反馈回路很危险：模型报警 → 运维换盘 → 该盘不再故障 → 标签变成“误报”。如果不记录“因告警而更换”，模型会被自己的行动误导。必须把“干预”作为单独标签。

5.7 失败模式

失败模式 后果 纠正
容量口径混用 提前/延后扩容 raw/usable/effective 分开
随机切分 指标虚高 按时间/设备切分
主动换盘当故障 学到运维策略 单独标签/竞争风险
只看 AUC 高误报 PR-AUC + 告警预算
预测无区间 决策过度自信 分位预测 + 回测
不监控漂移 慢慢失效 漂移 + 校准监控

练习（答案见答案册第 1 部分）：用 2,400 TB raw、EC 8+2、5% 水位、已用 1,500 TB、净增 6 TB/天，算三情景到 95% 水位的天数；再用 10,000 块盘、AFR 2%、召回 80%、精确率 20%，算每日告警量，并说明运维是否接得住。

6. 根因、证据与反证

6.1 相关、干预与反事实

存储运维没有随机对照试验，但有三层证据强度：

  1. 相关：A 和 B 同时异常。最弱，容易把共同原因当成因果。
  2. 干预：改变 A 后 B 按预期变化。强，但现场干预有风险，通常只在受控窗口做。
  3. 反事实：如果没做 A，B 会怎样。最强，但需要模型或对照，不能直接观测。

因此根因报告不应该只给“最可能”，还要给“如果这个假设成立，应该还能看到什么；如果看到相反结果，假设就被推翻”。这就是可证伪性。

6.2 候选生成

候选不是从所有实体里猜，而是从约束里收窄：

候选 = 时间上先于症状的变更
     ∪ 事发拓扑上可达的实体
     ∪ 同故障域内共现异常的实体
     ∪ 已知故障树/历史工单匹配的模式
     ∪ 影响范围与对照不吻合的共享依赖

给传播留出合理的时间窗口。维护于 02:10:30 生效，02:11 开始 backfill，02:14 结束的窗口观测到尾延迟上升。02:18 收到晚到日志后，才可在复盘中补上 02:12:30 的应用积压时间。若可靠证据显示 02:09 已开始变慢，就要重新检查触发事件和时钟。

6.3 证据评分

给每个候选打四项分，再保留原始证据：

维度 问题 例子
时间领先 候选是否先于症状？ 02:16 可看到 02:14 窗口异常；02:18 后可补上 02:12:30 的积压日志
路径可达 沿拓扑能否传到受影响实体？ PG 重映射到 osd.17/18
剂量响应 强度/范围是否与症状吻合？ backfill 615 MiB/s 时 P99 46 ms
特异性 是否能解释“为什么是这些而不是那些”？ 只有 hot 池受影响，cold 池正常
对照 未受影响的对照是否符合预期？ audit 走另一组 OSD，SLO 正常
干预响应 改变后是否按预期恢复？ 调度调整后 P99 下降、恢复继续

评分可以是加权和，也可以是贝叶斯网络的似然；但不要把加权和直接叫“概率”，除非做过校准。权重应该从回放集里学，而不是拍脑袋。

6.4 故障树、因果图与 LLM

三者不是替代关系：

  • 故障树：专家把“现象 → 子现象 → 根因”写成树，适合已知、边界清晰的设备故障；可审计，但覆盖有限。
  • 因果图：节点是变量/事件，边是假设的因果机制；适合表达共同原因、混杂和传播；需要领域知识维护。
  • LLM：适合从非结构化日志/工单里提取线索、生成假设、组织报告；不适合单独承担因果判断。

DME 的“智能分析”把 I/O 全路径时延分解、资源瓶颈、故障分析、亚健康、配置分析、故障树结合起来，输出根因、传播和修复建议；这是典型的“规则/故障树 + 产品知识”路线，优势是可解释、可落地，边界是覆盖场景有限。详见外部资料拆解 §11。

6.5 鉴别诊断模板

每个假设都写成可检验的形式：

假设 H1：维护导致的 backfill 与前台写争用
机制：OSD 重映射 → backfill 读旧副本、写新副本 → 后端队列上升 → 前台 P99 上升
预测：受影响 OSD 队列上升；backfill 速率与 P99 同向；停止/限速 backfill 后 P99 下降；其他池不受影响
02:16 可见的支持证据：E01/E02、T02、M06/M07
处置后补充检验：E05、M09–M11
反证/竞争：备份流量（E03 在另一站点，T03 无共享路径）；网络（重传未升）
鉴别检查：交换机端口丢包、其他客户端、设备服务耗时
停止条件：若限速后 P99 不降，H1 降级

这比“根因是 backfill”有用得多，因为它告诉值班人员下一步查什么、什么结果会改变结论。

6.6 三个深度：触发、机制、系统性

同一个事故要分三层写，否则改进会停在“重启解决”：

层 问题 例子
触发 什么事件启动了链条？ 维护让 osd.11 下线
机制 为什么会导致症状？ backfill 与前台写争用后端
系统性 为什么系统允许这件事发生？ 维护前没有恢复预算/SLO 检查

每一层独立引用证据。系统性原因往往没有单一证据，需要流程/配置/历史事故的支持；不能把它写成“根因”却不给证据。

6.7 评测

根因评测至少看：

Top-1 / Top-3 根因实体与类型
候选召回率（正确根因是否在候选里）
证据精确率/召回率（引用的证据是否真的支持结论）
首次定位时间（TTL）
结论强度校准（说“高置信”的时候是否真的更准）

只评“答案对不对”会奖励猜中；要同时评“证据对不对”和“该沉默时是否沉默”。

6.8 失败模式

失败模式 后果 纠正
把共现当因果 根因错 时间 + 路径 + 对照
只找支持证据 确认偏误 强制写反证
用事后数据 不可复现 知识时间截断
症状当根因 反复发生 三层深度
置信度无校准 决策失真 回放校准
只给一个答案 漏掉竞争假设 鉴别诊断

练习（答案见答案册第 1 部分）：对实验室事故写 H1（backfill 争用）、H2（备份流量）、H3（网络）三个假设，各写两条支持、两条反证、一个鉴别检查和一个停止条件。

7. Agent、工具契约与 RAG

7.1 有界状态机，而不是自由聊天

把调查实现为有界状态机：

初始化（症状、窗口、资产、权限）
  → 查采集健康/覆盖率
  → 查业务影响（SLO、错误、范围）
  → 查拓扑（事发时刻）
  → 查变更/事件
  → 生成候选假设
  → 对每个假设选择最有区分度的查询
  → 证据足够/预算耗尽/需要人工 → 输出

每一步都要有预算：最大工具调用数、最大时间窗、最大返回行数、最大 token、最大并行度。没有预算的 Agent 会在大规模环境里把查询打爆。

7.2 工具契约

一个好工具不是“能查指标”，而是“查询语义明确、结果可引用、失败可解释”。最少包含：

{
  "name": "query_metric",
  "description": "按实体、指标、时间窗查询聚合指标；返回样本、单位、缺失区间和查询 ID",
  "input": {
    "entity_id": "string",
    "metric": "enum",
    "start": "RFC3339",
    "end": "RFC3339",
    "step": "duration",
    "aggregation": "enum"
  },
  "output": {
    "unit": "string",
    "samples": "array",
    "missing_intervals": "array",
    "coverage": "number",
    "query_id": "string",
    "source": "string"
  },
  "constraints": {
    "max_range": "7d",
    "max_samples": 10000,
    "read_only": true
  }
}

关键点：

  • 时间参数用绝对时间 + 时区，不用“最近一小时”这种相对语义。
  • 返回必须带单位、缺失区间、覆盖率和查询 ID；否则证据不可复核。
  • 枚举值要稳定；不要让模型自由拼指标名。
  • 错误要分类型：无权限、无数据、超时、参数错、后端错；不同错误触发不同下一步。
  • 写工具单独授权，默认不暴露。

7.3 MCP：把工具变成可组合的协议

Model Context Protocol（MCP）用 JSON-RPC 连接模型客户端和工具服务端，通常暴露 tools、resources、prompts。它的价值不是“又一个 API”，而是工具的描述、调用和权限可以标准化，不同 Agent 可以复用同一套存储工具。

截至本资料核验日，公开资料里的存储 MCP 状态：

系统 公开状态 范围
Pure1 Manage MCP 已正式可用 只读管理面查询
Fusion MCP 开源，文档公开 阵列、卷、文件系统、工作负载、拓扑；部分性能查询依赖直连令牌
NetApp DII MCP Preview（2026-09 文档） 租户内只读：性能、容量、日志、告警、采集健康
华为 DME 公开材料未见 MCP 服务 北向 RESTful/SNMP/Ansible/CSI；故障智能体可通过北向 API 接入跨域智能体

DME 的北向开放是真实的，但它不是 MCP：没有公开的工具清单、JSON Schema、资源模型和 Agent 侧发现机制。要接入通用 Agent，通常需要自己写适配层。详见外部资料拆解 §11、§6、§8。

7.4 RAG：检索的是“适用知识”，不是“相似文本”

RAG 的失败大多不是向量模型，而是过滤条件。一个存储 Runbook 的检索至少要过滤：

租户/ACL → 产品 → 型号 → 版本区间 → 故障码/症状 → 审批状态 → 生效时间

然后再做关键词 + 向量混合召回，再重排。分块要保留章节标题、表格、图注和原文链接；故障码用精确匹配，工单/复盘用语义召回。冲突的文档要返回多个候选和冲突点，不要强行合并。

GraphRAG 适合“实体关系 + 多跳”的问题（例如“这个型号的控制器在哪个版本修复了这个问题”），但不适合替代精确的配置查询。知识图谱和向量库是互补的，不是二选一。

7.5 上下文与防幻觉

把证据作为结构化对象传给模型，而不是一段散文：

evidence_id, query_id, source, entity_id, window,
observed_at, quality, payload_ref, summary

报告必须：

  • 每个事实引用 evidence_id。
  • 区分“观测到的事实”和“推断”。
  • 明确知识截止时间；不能引用晚于截止时间的数据。
  • 数据不足时输出“未决 + 下一步查询”，而不是编一个答案。
  • 数值做单位/量纲校验（ms vs s、MiB vs MB、IOPS vs 带宽）。

验证层要做：引用存在性、引用与结论的一致性、时间边界、数值范围、权限范围、输出 schema。模型自评不能替代外部校验。

7.6 安全：日志和文档也是不可信输入

Agent 读到的告警描述、日志、文件名、工单、Runbook 都可能包含提示注入。防护：

  • 工具输出标记为 untrusted_data，不进入系统指令。
  • 工具白名单 + 参数校验 + 只读默认。
  • 写操作走独立通道、人工审批、幂等键、回滚。
  • 沙箱/网络白名单；限制可访问的租户和实体。
  • 全链路审计：谁、什么时候、用什么工具、看了什么、改了什么。

7.7 评测 Agent

不能只看最终答案。至少记录：

任务成功率 / 根因 Top-k
证据引用正确率
工具调用次数与成本
调查时长（P50/P95）
越权尝试拒绝率
缺数据时正确暂缓率
轨迹可复现性（同一快照重跑是否一致）

同一组快照，比较“规则”“规则 + 统计”“Agent + 工具”“Agent + 工具 + RAG + 拓扑”，做消融，才能知道增益来自哪里。

7.8 失败模式

失败模式 后果 纠正
工具语义模糊 模型乱查 严格 schema + 枚举
无预算 查询风暴 步数/行数/超时
RAG 不过滤版本 用错手册 版本/ACL/生效时间
证据不落 ID 无法复核 证据对象 + 查询 ID
提示注入 越权/错误动作 不可信标记 + 白名单
只评答案 奖励瞎猜 轨迹 + 证据 + 沉默

练习（答案见答案册第 1 部分）：为 get_collection_status、get_topology_at、query_metric、list_changes、search_runbooks 写五份工具契约；再用同一份 02:16 快照，比较“直接问模型”和“工具约束 + 证据 ID”的回答差异。

8. 处置、验证与回放评测

8.1 动作分级与授权

存储动作的代价不对称，必须分级：

级别 例子 默认授权 必要控制
A0 只读 查指标、拓扑、日志 Agent 自主 租户/实体范围
A1 建议 生成变更方案 Agent 自主 证据、影响范围
A2 可逆配置 QoS 调整、分级策略、限速 人工一键批准 幂等、回滚、观察窗
A3 状态变更 主从切换、迁移、扩容 双人审批 + 窗口 预检、回滚、双验收
A4 破坏性 重启、隔离盘/端口、删除 严格人工 + 厂商支持 爆炸半径、熔断、审计

Agent 默认只到 A0/A1；A2 以上必须是独立通道，不能和“聊天”共用一个工具权限。

8.2 变更契约

每次处置请求至少包含：

目标实体 + 当前版本/配置哈希
变更前后预期（指标、状态、冗余）
前置条件（健康、冗余、窗口、无冲突变更）
幂等键
回滚方案与回滚触发条件
观察窗口与成功/失败判据
审批人、执行人、审计 ID

执行前再次读取状态；如果拓扑、授权、冗余条件已变，重新评估。执行后先看业务 SLO，再看耐久性。

8.3 存储特有的验证

“P99 降了”不等于“修好了”。至少双验收：

维度 指标 失败例子
业务 好请求比例、错误率、P99、吞吐 降级 QoS 让延迟好看，但业务被限速
冗余 degraded PG、副本同步、重建速率、校验错误 前台恢复，但副本还没同步
数据 快照年龄、复制 lag、备份成功、一致性 主可用，备不可用
容量 水位、预留、增长斜率 清理了日志，但快照仍在涨
配置 版本、参数、许可、拓扑 改了调度，但重启后回退

Ceph 场景：p99 恢复后继续看 degraded_pgs、恢复速率、scrub 错误、OSD 是否再次 down。DME/ Dorado 场景：看控制器 CPU、缓存命中、端口误码、复制/双活状态、硬盘健康。不同产品指标不同，但“业务 + 冗余”的双验收是通用的。

8.4 从处置回到学习

每次事故要写回事故库：

症状、时间线、候选假设、证据、反证
实际根因、人工裁定、处置、验证结果
哪些证据缺失、哪些查询最有区分度
模型/规则版本、工具版本、数据快照 ID

这些记录是下一轮评测集和规则迭代的原料。没有写回，系统不会变聪明，只会换一个模型继续犯同样的错。

8.5 评测集设计

一个像样的存储评测集至少包含：

  • 真实事故回放：固定快照、隐藏答案、按知识时间截断。
  • 合成故障：在实验环境注入磁盘慢、网络丢包、OSD down、元数据热点。
  • 负对照：没有事故的窗口，检查误报。
  • 缺数据变体：隐藏关键证据，检查是否降低结论强度。
  • 晚到数据变体：事故结束后才到的日志，检查是否使用未来数据。
  • 新版本/新型号：检查迁移能力。
  • 跨租户/权限：检查越权。

切分按事故、集群、时间、版本，不按行随机。答案和复盘原文要隔离，评分用独立裁定表。

8.6 指标与消融

维度 指标
检测 事故级召回、误报/集群日、首次告警延迟
定位 根因 Top-1/Top-3、候选召回、TTL
证据 引用正确率、关键事实支持率、缺数据暂缓率
处置 建议可执行率、越权拒绝率、SLO 恢复时间、冗余恢复时间
成本 工具调用数、P95 调查时长、每事故 token/查询成本、人工核实时间

消融：规则 → 规则 + 统计 → + 工具 Agent → + 拓扑/RAG → + 因果/故障树。每一层都要在同一快照上比较，否则不知道增益来自哪里。

8.7 公开基准与边界

AIOpsLab、RCAEval、ORCA-bench 提供了任务框架、盲测和候选召回/重排分解，但它们主要覆盖云应用/微服务。存储的特殊性——物理故障域、后台恢复、介质退化、双验收——需要自建案例。Backblaze/FAST ’20 可以支撑硬盘预测支线，但不能替代存储 RCA 评测。

8.8 多集群与数据主权

多集群架构的常见分层：

站点边缘：就近采集、缓冲、脱敏、粗聚合
区域中心：跨站资产目录、证据索引、查询路由
全局：策略、模型、评测、审计

查询尽量下推，明细按需回查；站点断链时保留缓冲和水位，恢复后补数并标记“迟到”。租户隔离、数据驻留、跨境合规要在采集层就设计，不能等集中后再补。

8.9 落地路线

阶段 交付 验收
0–1 月 实体表、SLO、采集覆盖率、事件时间语义 能回答“当时是什么、缺了什么”
1–3 月 规则 + 稳健基线、告警聚合、事故时间线 误报/集群日可接受，MTTD 下降
3–6 月 时态拓扑、变更关联、证据对象、RAG 根因 Top-3 + 证据可复核
6–12 月 MCP/工具层、Agent 调查、回放评测 同快照可复现，缺数据会暂缓
12 月+ 受监督处置、双验收、有限自治 越权为零，回滚可演练

不要跳过“实体 + 时间 + 覆盖率”。这是所有上层能力的地基。

8.10 失败模式

失败模式 后果 纠正
只验业务，不验冗余 数据风险累积 双验收
无幂等/回滚 重试造成二次事故 变更契约
评测用未来数据 指标虚高 知识时间截断
只有成功案例 过度自信 负对照 + 缺数据
集中所有明细 成本/合规爆炸 边缘聚合 + 按需下钻
直接跳到自治 事故放大 L1→L2→L3 逐级

练习（答案见答案册第 1 部分）：为一次“维护导致 backfill 争用”的处置写变更契约（目标、前置、幂等、回滚、观察窗、双验收）；再设计一个包含正常、缺数据、晚到数据、负对照的回放集。
