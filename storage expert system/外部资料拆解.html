0. 为什么不能只贴链接

链接有三个问题：

  1. 它会变：产品页改版、文档下线、版本更新，结论就失效。
  2. 它不解释上下文：同一句“支持 MCP”，可能只是博客愿景，也可能是已 GA 的工具；不拆开就会误判。
  3. 它不能直接变成设计：知道“有故障树”不等于知道故障树怎么建、输入输出是什么、怎么评测。

所以本文的写法是：先把链接背后的机制讲成一个可画出来的系统，再用一个具体例子跑一遍，最后才给出处。这样即使链接失效，知识还在。

1. Ceph 的数据放置与健康

一句话：Ceph 把对象经哈希映射到 PG，再由 CRUSH 把 PG 映射到一组 OSD；PG 的 active/clean/degraded 和 OSD 的 up/in 是两套不同状态。

流程图：

客户端对象
   │ hash(object)
   ▼
PG（placement group）
   │ CRUSH(pgid, osdmap, crushmap)
   ▼
OSD 集合（主 + 副本/EC 块）
   │
   ▼
BlueStore → 块设备 → HDD/SSD

状态：
  PG: active / clean / degraded / undersized / peering / stale / inactive
  OSD: up/down（进程可用） × in/out（参与放置）

机制拆解：

  • active 表示 PG 可以服务；clean 表示所有副本一致。active+clean 才是完全健康。
  • degraded 表示副本数不足但仍可服务；undersized 表示 acting 集合小于期望；peering 是主从协商数据版本的过程，期间可能不能服务。
  • OSD 的 up/down 与 in/out 正交：down+in 表示进程挂了但仍在 CRUSH 里；up+out 表示进程活着但被移出放置。把两者混成一个“健康/不健康”会误判。
  • 维护让 OSD 下线会触发 PG 重映射，随后 backfill；backfill 与前台 I/O 争用，是“IOPS 不变但延迟升高”的典型机制。

例子：维护 osd.11 下线，PG 从 osd.11/12/13 重映射到 osd.12/17/18。此时 PG 可能是 active+undersized+degraded+peered：仍能服务，但副本不足；ceph health detail 会给出具体 PG 和原因。不要只看到 active 就认为健康。

对专家系统的启示：状态要保留原始枚举和两组正交状态；不要把 degraded 直接映射成“业务故障”。根因分析要沿“维护 → 重映射 → backfill → 前台争用”这条链，而不是只看一个健康分。

原文：Ceph OSD/PG 监控 · Ceph 健康检查 · Ceph 文档总入口

2. Ceph Prometheus 模块

一句话：ceph-mgr 内置 Prometheus exporter，把集群/OSD/PG/池指标暴露成 /metrics，由 Prometheus 抓取，再用 Grafana/Alertmanager 展示和告警。

流程图：

ceph-mgr (prometheus module)
   │ HTTP /metrics
   ▼
Prometheus（scrape、存储、规则）
   ├─ Grafana（看板）
   ├─ Alertmanager（告警）
   └─ 远程写/长期存储（可选）

机制拆解：

  • exporter 在 mgr 进程里，不需要额外 agent；指标包括 ceph_osd_*、ceph_pg_*、ceph_pool_* 等。
  • 抓取间隔决定分辨率；默认 15s/30s 常见，但大规模集群要注意 scrape 超时和序列基数。
  • 高基数来自每个 OSD/PG 的标签；PG 数很多时，ceph_pg_* 序列会爆炸。要限制导出的指标集/标签，或做 recording rule 聚合。
  • mgr 故障会导致指标中断；监控系统本身要监控 mgr 和 scrape 健康。

例子：要算“OSD 停报率”，不能只看 ceph_osd_up 的平均值；要拿资产表的期望 OSD 数作分母：

coverage = count(ceph_osd_up == 1) / expected_osd_count

如果一半 OSD 停报，剩余 OSD 的平均延迟可能下降，但覆盖率会暴露问题。

对专家系统的启示：指标采集要带“期望数/覆盖率”；不要把 exporter 的 up 当成“所有实体健康”。PG 级指标要么聚合，要么按需查询，不能全量长期保留。

原文：Ceph Prometheus 模块 · Ceph 监控（Squid）

3. Ceph mClock

一句话：Ceph Tentacle 的 OSD mClock 用 reservation、limit、weight 分配客户端 I/O、后台 recovery、后台 best-effort 三类资源份额。Backfill、scrub、快照裁剪和 PG 删除属于后台 best-effort。

流程图：

请求 → 分类（client / background recovery / background best-effort）
        │
        ▼
   mClock 调度器
   ├─ reservation：保底份额
   ├─ limit：上限
   └─ weight：剩余能力按权重分
        │
        ▼
   OSD 后端（BlueStore/介质）

机制拆解：

  • reservation 保证某类请求至少有这么多能力；limit 防止某类请求吃满；weight 在剩余能力里分配。
  • 选用 profile 时同时考虑客户端延迟、recovery 和 backfill 完成时间。过度压缩后台份额会延长冗余不足的窗口。
  • 调参前确认 Ceph 版本、OSD 生效 profile 和调度模式。内置 profile 统一应用低层参数，手工修改前要核对支持的方式与参数覆盖条件。
  • 它不是“魔法 QoS”：如果介质本身饱和，任何调度都只能分配排队，不能创造能力。

例子：前台 P99 高、backfill 高、磁盘利用率 90%。受控演练可以比较当前 profile 与侧重前台的 profile，并同时观察 backfill 速率、PG 状态和业务 SLO。Backfill 属于 best-effort，单独改变 recovery 类的 limit 无法作为检验 backfill 限速的依据。若 P99 不降，先验证变更已生效且实际改变了 backfill，再检查网络、设备和客户端等路径。

对专家系统的启示：处置建议必须带“双向指标”（前台 + 恢复）和回滚条件；不能只优化 P99 而让冗余长期不恢复。

原文：Ceph mClock 配置

4. Prometheus 直方图与原生直方图

一句话：直方图用一组累计桶记录延迟分布，合并桶后才能算全局分位；原生直方图用稀疏桶/指数桶减少配置和存储成本。

流程图：

请求延迟
  │ 观察值落入桶
  ▼
桶计数（le=10ms, 20ms, 50ms, ...）
  │ 累计
  ▼
histogram_quantile(0.99, sum by (le) (rate(bucket[5m])))
  │ 桶内线性插值
  ▼
P99

机制拆解：

  • 经典直方图的桶边界是固定的；不同客户端/实例必须用相同边界才能合并。
  • 分位数不能平均：先按 le 求和，再算分位；直接平均各实例 P99 会失真。
  • 桶内插值假设桶内均匀分布；桶太粗会误差大，桶太细会 cardinality 高。
  • 原生直方图用稀疏桶/指数桶，减少“每个实例一套桶”的成本，但客户端/服务端支持要确认。

例子：三个客户端共 100 万请求，合并后 ≤20 ms 有 984,000，≤50 ms 有 996,900。P99 秩 990,000 落在 (20,50] ms 桶，按桶内线性插值约 33.95 ms。三个客户端 P99 的算术平均约 41.48 ms。 原始桶计数与计算

对专家系统的启示：SLO 计算要用桶合并，不要用预计算分位的平均；低流量窗口要带样本量，否则 P99 只是一个请求的延迟。

原文：Prometheus 直方图实践 · 原生直方图规范 · Prometheus 文档

5. OpenTelemetry 日志与时间语义

一句话：OTel 日志模型把日志记录分成 resource（谁产生）、scope（哪个库/模块）、record（事件本身），并区分事件时间与观测时间。

流程图：

Resource（service.name, host, k8s.pod）
   └─ Scope（instrumentation library）
        └─ LogRecord
             ├─ time_unix_nano（事件时间）
             ├─ observed_time_unix_nano（观测时间）
             ├─ severity / body / attributes
             └─ trace_id / span_id（可选关联）

机制拆解：

  • time_unix_nano 是事件发生时间；observed_time_unix_nano 是采集/写入时间；两者可能相差很大（设备时钟、缓冲、批处理）。
  • trace_id/span_id 把日志和追踪关联；没有关联时，只能靠实体/时间窗对齐。
  • 日志是半结构化数据；属性键要统一（服务名、集群、租户、实体 ID），否则无法聚合。
  • 采集端要处理背压/丢弃；丢弃要记录，不能静默。

例子：一条存储告警日志在 02:18 才被采集，但事件时间是 02:10:30。回放 02:16 的事故时，只能使用 observed_time <= 02:16 的记录；否则会用未来数据。报告里要同时保留两个时间。

对专家系统的启示：日志证据必须带事件时间、观测时间和来源；时间语义比日志内容更容易出错。

原文：OpenTelemetry 日志数据模型 · OpenTelemetry 文档

6. Everpure Pure1 + Fusion：设备群遥测与工具化调查

一句话：Pure1 是设备群管理面，收集阵列遥测并提供健康/容量/性能视图；Fusion 提供阵列内部关系与工作负载拓扑；两者通过 MCP 把查询暴露给 Copilot/Agent，写工具默认隐藏、需显式配置。

流程图：

阵列（Pure Storage FlashArray/FlashBlade）
   │ 遥测/健康/容量/性能
   ▼
Pure1 管理面（设备群视图、AI Copilot、MCP Server）
   │ 只读查询
   ├─ 健康/容量/性能/告警
   └─ 设备群/租户/站点

Fusion（阵列、卷、文件系统、工作负载、预设、拓扑）
   │ MCP / 直连令牌
   ├─ 拓扑与关系查询
   ├─ 部分性能查询（依赖直连令牌）
   └─ 可选受监督写工具（默认隐藏，需配置）

机制拆解：

  • 设备群视角：Pure1 把多阵列的遥测集中，回答“哪个站点/租户/设备不健康”。它不直接进入阵列内部拓扑。
  • 拓扑视角：Fusion 回答“这个卷在哪个阵列、属于哪个工作负载、和谁共享”。调查时先用 Pure1 找异常设备群，再用 Fusion 缩小到卷/工作负载。
  • 工具视角：MCP 把查询变成有 schema 的工具；Copilot/Agent 通过工具拿事实，而不是靠模型记忆。
  • 写权限：Fusion 文档记载写工具默认隐藏，需要显式配置并受令牌权限约束。这意味着“能查”不等于“能改”，调查与处置分开授权。

例子：值班收到“订单库延迟升高”。

1) Pure1 MCP: 查设备群健康/性能 → 发现 site-a 的 array-3 前端延迟升高
2) Fusion MCP: 查 array-3 上的卷/工作负载 → 定位 orders-vol
3) Fusion MCP: 查卷的拓扑/共享依赖 → 发现同阵列的 backup-vol 在同一池
4) 查变更：备份作业在 02:12 启动
5) 结论：备份与订单卷共享池/后端，可能是争用；列出反证（网络/磁盘/负载）

这个流程的关键不是“Copilot 很聪明”，而是每一步都有工具、实体、时间窗和返回数据。

对专家系统的启示：先管理面、再拓扑、再变更、再证据；读工具和写工具分开；工具返回要能落到实体和时间窗。

7. NetApp AutoSupport + Digital Advisor：遥测、资产与风险建议

一句话：ONTAP 的 AutoSupport 把设备遥测/日志/配置发给 NetApp，Active IQ/Digital Advisor 把遥测与资产、软件版本、支持合同关联，输出风险、容量、升级和生命周期建议。

流程图：

ONTAP 集群
   │ AutoSupport（遥测/日志/配置，周期或事件触发）
   ▼
NetApp 支持云（Active IQ）
   ├─ 资产/合同/版本
   ├─ 风险规则/健康评分
   ├─ 容量趋势
   └─ 升级/生命周期建议
        │
        ▼
Digital Advisor（看板/报告/建议）

机制拆解：

  • AutoSupport 不只是指标，还包括配置、日志、事件；这使“设备型号 + 版本 + 合同 + 风险”能关联。
  • 风险建议通常来自规则/知识库（已知 bug、EOL、配置最佳实践），不是纯 ML。
  • 容量趋势是时间序列预测；升级建议要结合版本兼容矩阵和合同。
  • 数据在厂商云；客户侧看到的是建议/报告，原始数据不一定可导出。

例子：某卷容量以 5%/周增长，当前 80%，合同还有 8 个月到期。Digital Advisor 输出“预计 6 周到达 90%，建议扩容/分层；当前版本接近 EOL，建议升级到 X”。这不是“预测未来”单一模型，而是容量 + 资产 + 合同 + 版本的联合判断。

对专家系统的启示：预测必须和设备清单、版本、合同、生命周期关联；否则只会给出“容量快满了”，无法变成可执行动作。

8. NetApp DII + MCP：先验证采集，再查容量/性能

一句话：Data Infrastructure Insights（DII）从多源采集资产/性能/容量/日志，先提供“采集健康/资产身份”，再提供 Monitor 和 MCP 只读查询。

流程图：

数据源（ONTAP、E-Series、StorageGRID、交换机、VMware、云）
   │ 采集器
   ▼
DII 数据层（资产、性能、容量、日志、告警、采集健康）
   ├─ Monitor（阈值/异常/容量/性能）
   ├─ 看板/报告
   └─ MCP（Preview，租户内只读：性能/容量/日志/告警/采集健康）

机制拆解：

  • DII 的价值不只是“有指标”，而是把采集覆盖/采集健康作为可查询对象。调查前先问“数据齐不齐”，再问“数值是多少”。
  • Monitor 支持阈值/异常/容量等类型；不同 Monitor 的输出是事件/告警，不是自动根因。
  • MCP 当前是 Preview，工具范围是租户内只读；这意味着它能做调查，不能做处置。

例子：应用 P99 升高，DII 显示某阵列性能异常。先查采集健康：该阵列 3 个采集器有 1 个断连，覆盖率 67%。此时不能直接用平均延迟下结论；应标注“数据缺口”，先恢复采集或只使用已覆盖子集。

对专家系统的启示：把 collection_status 作为第一个工具；覆盖率不足时，任何全局结论都要降级。

9. Dell AIOps / PowerStore：健康评分、预测与来源保留

一句话：Dell AIOps 把健康评分、预测分析和生成式助手组合；PowerStore 侧提供性能历史基线、资源争用和容量突增检测。

流程图：

PowerStore / 其他基础设施
   │ 遥测/性能/容量/告警
   ▼
Dell AIOps（CloudIQ 类）
   ├─ 健康评分（规则/加权）
   ├─ 预测分析（容量/性能）
   ├─ 异常/争用/突增检测
   └─ GenAI Assistant（解释/建议）
        │
        ▼
分级响应/工单/报告

机制拆解：

  • 健康评分通常是多指标加权/扣分，不是概率；不同型号/版本的分数可比性要确认。
  • 性能分析会把历史基线、资源争用、容量突增分开；这比单一“健康分”更有诊断价值。
  • GenAI Assistant 负责解释和建议；关键是能否引用底层指标/来源，否则只是“会说话的看板”。

例子：PowerStore 检测到某卷容量 24 小时突增 20%，同时性能基线显示 IOPS 未变。AIOps 可能给出“容量异常增长，建议检查快照/克隆/日志”；但“为什么增长”仍要查快照/备份/应用变更。

对专家系统的启示：健康分只能作为入口，不能作为根因；每个结论要能下钻到指标/事件/变更。

10. AWS DevOps Agent：跨栈调查与沙箱

一句话：AWS DevOps Agent 把应用拓扑、告警、日志、变更和工具放进一个受控的 Agent Space，用只读沙箱和网络白名单做跨栈调查。

流程图：

Agent Space
   ├─ 应用拓扑（服务/资源/依赖）
   ├─ 告警/日志/指标/变更
   ├─ 调查工具（只读 AWS API）
   └─ 沙箱（临时环境、网络白名单）
        │
        ▼
   调查结论/证据/建议

机制拆解：

  • Agent Space 是调查的边界：哪些应用、哪些账号、哪些数据可见。
  • 跨源调查把“应用症状”与“基础设施/变更/日志”放在同一时间线。
  • 沙箱只读 + 网络白名单限制爆炸半径；这是 Agent 安全的关键设计。
  • 服务卡会说明评估口径、用户角色和限制；读的时候要区分“能力”和“保证”。

例子：部署后 5 分钟错误率上升。Agent 查部署事件、服务拓扑、下游依赖、日志异常，形成“部署 → 配置变更 → 下游超时”的时间线；它不能直接改生产，只能给建议/在沙箱验证。

对专家系统的启示：先定义 Agent 的可见范围和动作边界，再谈模型能力；跨栈调查的核心是时间线和证据，不是聊天。

13. AIOpsLab：把检测/定位/诊断/缓解做成任务

一句话：AIOpsLab 把云应用的故障生命周期拆成检测、定位、诊断、缓解四类任务，提供测试环境、故障注入和 Agent 评测框架。

流程图：

AIOpsLab
   ├─ 应用/云测试环境（微服务、K8s、云资源）

14. RCAEval：候选召回与重排的分解

一句话：RCAEval 提供根因分析的评测数据和框架，把 RCA 拆成“候选召回”和“候选重排”，避免只用一个 Top-1 指标掩盖问题。

流程图：

故障数据/拓扑/指标/日志
   │
   ├─ 候选生成（拓扑/异常/变更/历史）
   ▼
候选集合（Top-N）
   │
   ├─ 重排（证据/因果/模型）
   ▼
Top-1/Top-3 根因
   │
   └─ 指标：召回率、重排准确率、MRR、证据

机制拆解：

  • 如果正确根因不在候选集合里，重排再强也没用；所以要分别评“召回”和“排序”。
  • 候选生成可以来自拓扑邻域、异常共现、变更、故障树、历史工单。
  • 重排可以用规则/统计/因果/LLM，但要有证据和校准。

例子：候选有 20 个实体，正确根因排第 7。召回率可能是 100%（在候选里），但 Top-1 准确率是 0；改进方向是重排，而不是扩大候选。

对专家系统的启示：报告里要写“候选怎么来的、正确根因是否在候选、排序依据是什么”，否则无法定位失败环节。

16. FAST ’20 硬盘故障预测：标签、特征与评测

一句话：论文用 38 万块盘、64 个站点、两个月的数据，基于 SMART 时序特征预测未来 10 天是否故障，报告平均 F-measure/MCC 约 0.95。

流程图：

每块盘每天的特征（SMART/型号/年龄/变化率）
   │
   ├─ 标签：未来 H 天内是否故障
   ├─ 切分：按时间/按设备，避免同盘泄漏
   ▼
模型（特征工程 + 分类器）
   │
   ├─ PR 曲线/阈值
   ├─ 提前量分布
   └─ 校准/误报

机制拆解：

  • 样本是“盘-日”，不是“盘”；同一块盘多天样本高度相关，随机切分会泄漏。
  • 标签要定义“故障窗口 H”；H 越长，越早预警但越难准。
  • 特征包括 SMART 原始值、变化率、型号/固件/年龄；不同厂商 SMART 属性不一致。
  • 评测要看 PR-AUC/召回@告警预算/提前量/校准，不只看准确率；故障是极少数类。

例子：一块盘今天 SMART 出现待定扇区，模型输出“未来 10 天故障概率 0.3”。如果告警预算允许，运维可以提前换盘；如果概率校准不好，0.3 可能实际只有 0.05，告警就会泛滥。

对专家系统的启示：硬盘预测的难点是标签和切分，不是模型；没有校准和告警预算，准确率没有意义。

18. MCP：把工具变成可发现、可调用的协议

一句话：Model Context Protocol 用 JSON-RPC 连接客户端和服务端，服务端暴露 tools/resources/prompts，客户端把工具描述给模型，模型选择调用。

流程图：

Host（Claude/IDE/Agent）
   │ MCP Client
   ▼ JSON-RPC
MCP Server（存储/监控/知识库）
   ├─ tools/list → 工具 schema
   ├─ tools/call → 执行并返回
   ├─ resources/list/read → 资源
   └─ prompts/list/get → 提示模板

  • 工具是“有名字、有描述、有输入/输出 schema”的可调用单元；模型根据描述选择工具。

19. NVMe 规范：队列、命令与命名空间

一句话：NVMe 用多对提交/完成队列、doorbell 和命名空间，把存储命令从 SAS/SATA 的单队列解放出来，降低延迟、提高并发。

流程图：

主机
 ├─ Admin 队列（创建/管理）
 └─ I/O 队列对（每核一对）
      │ 提交命令 → SQ tail doorbell
      ▼
   NVMe 控制器
      │ 执行 → 完成队列
      ▼
   命名空间（Namespace）→ NAND/介质

机制拆解：

  • 队列深度大、每核独立队列，减少锁竞争；轮询/中断模式影响延迟。
  • 命名空间是逻辑块设备；多路径/多控制器（NVMe-oF）要处理路径故障。
  • NVMe-oF 把命令放到 TCP/RoCE/FC；网络拥塞/PFC/ECN 会引入尾延迟。

例子：4 KiB 随机读，队列深度 64，单盘 500k IOPS；如果只开队列深度 1，IOPS 会低很多。延迟不是单命令服务时间，而是排队 + 服务。

对专家系统的启示：看到 IOPS 高但延迟高，要查队列深度/拥塞；不要只用“盘慢”解释。

原文：NVMe 规范

21. Google SRE Workbook：SLI、SLO、错误预算与燃烧率

一句话：SRE 用 SLI（指标）、SLO（目标）、错误预算（1−SLO）和燃烧率（错误率/预算率）把“可靠性”变成可运营的数值。

流程图：

SLI（好请求/总请求）
   │
   ▼
SLO（如 99.9%/30 天）
   │
   ├─ 错误预算 = 0.1%
   ├─ 燃烧率 = 实际错误率 / 0.1%
   └─ 多窗口告警（1h/5m）

机制拆解：

  • SLI 要定义测量点、好事件、分母；SLO 是内部目标，SLA 常带商务后果。
  • 错误预算让“可靠性”和“发布速度”可权衡；预算烧完就冻结变更。
  • 多窗口燃烧率兼顾快发现和少误报；单阈值容易翻页或漏报。
  • 存储 SLO 要加冗余/耐久性指标，不能只看请求成功率。

例子：请求型 SLO 为 30 天内 99.9% 好请求，预算为全周期请求数的 0.1%。请求量近似均匀时，相当于 43 分 12 秒完全不可用。1 小时坏请求率 1.44% 对应燃烧率 14.4，同一流量假设下用掉周期预算的 2%。多窗口告警可要求 1 小时和 5 分钟都超过阈值，通知级别由团队定义。

对专家系统的启示：告警级别应由 SLO 燃烧率决定，而不是设备型号；处置验收要同时看业务 SLO 和冗余。

原文：Google SRE Workbook
