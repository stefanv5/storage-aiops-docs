0. 运维系统要做什么

运维系统要能还原事发状态、找到适用的手册、用证据诊断故障，并跟踪审批和处置结果。事后用回放检验诊断和处置。

面 回答的问题 典型组件 失败表现
查状态 系统现在怎样？事发时发生了什么？ 指标、日志、事件、变更、拓扑快照 设备停报后，误判为性能好转
查知识 有哪些已知故障和适用手册？ 实体和关系定义、故障模式、操作手册（Runbook）、版本约束 检索到过期或不适用的手册
查原因 哪个原因最能解释现象？还缺什么证据？ 规则、统计、因果图、故障树、LLM 规划 把同时发生当成因果关系，或漏查其他原因
做处置 能否变更、谁来审批、怎样回滚？ 工单、审批、编排、幂等接口 只确认业务恢复，漏查冗余
做评测 系统在哪些任务上比人工做得好？ 回放集、盲评、负对照、成本记录 只展示成功案例

按证据要求和授权范围划分成熟度。

级别 能力 必要证据 授权
L0 可视 看到资源、指标、拓扑 实体 ID、单位、采集时间 只读
L1 检测 发现异常并分级 基线、样本量、覆盖率、误报预算 只读 + 通知
L2 诊断 给出候选根因与反证 原因先于症状、拓扑可达、对照、证据出处 只读 + 建议
L3 处置 执行可逆变更并验证 前置条件、幂等键、回滚、关单前检查业务与数据保护 人工审批 + 受监督执行
L4 自治 在批准的范围内自动处理 L3 的全部要求，加长期回放、自动停止和审计 白名单、执行限额和停止条件

先验收 L1 检测和 L2 诊断，再开放 L3 处置。未经证据验证的诊断可能触发错误变更。

存储诊断还要遵守四个约束。

  1. 优先保护数据。优化延迟前，先检查副本、校验、快照和恢复窗口。
  2. 按共享失效单元判断影响范围。检查控制器、机框、机柜、站点、双活对和 EC 条带。
  3. 重建、backfill、scrub、GC、快照删除、克隆和迁移都可能与前台争用 CPU、内存、网络和介质。
  4. 按版本、补丁和 license 核对告警码。同一告警码在 V6 与 V7 可能含义不同。Runbook 要注明适用版本和配置。

0.1 经典专家系统与现代 Agent 的分工

经典专家系统按规则推理，现代 Agent 可以读取文本并调用工具。

经典专家系统以 MYCIN 为例，由知识库、工作记忆、推理机和解释器组成。知识库保存事实和规则，工作记忆保存当前事实，推理机做前向或后向推理，解释器给出结论由来。相同输入下，结果可重复，也便于审计。难点在于维护脆弱的规则、获取专家知识，以及处理非结构化输入和大量不确定信息。

现代 LLM Agent由模型、工具、记忆、规划器和验证器组成。它能读日志、工单和手册，生成假设并用自然语言交互。也可能编造事实，多次运行的结果可能不同，还需控制成本和权限。

存储调查可以组合这两套机制。

规则和故障树负责阈值判断、SLO 验收、权限校验和执行前检查。
用统计和模型检测异常、做预测。让 LLM 提出假设、检索操作手册（RAG）并整理报告。

各组件按下表分工。

职责 交给谁 原因
硬约束（副本数、SLO、权限、窗口） 规则/策略引擎 必须确定、可审计
异常/预测 统计/ML 用历史数据估计正常范围和趋势
候选根因 故障树 + 拓扑 + 因果图 按故障机制和依赖路径筛选
假设生成/证据选择 LLM 从日志和工单找线索，再提出下一项查询
事实陈述 工具/数据库 从记录查询设备状态
结论校验 确定性验证器 引用、单位、时间、权限、数值
最终动作 人或受监督工作流 错误变更可能影响业务和数据保护

DME 可用运维助手和故障智能体发起调查，用故障树和智能分析查故障。要把调查与故障分析接起来，需要公开的证据格式和工具契约。

1. 一条 I/O 的完整生命周期

1.1 块存储：从 initiator 到介质

一次块写请求经过以下环节。

应用 write()
  → 文件系统 / 数据库页缓存
  → 多路径（DM-Multipath）与 HBA 队列
  → FC/iSCSI/NVMe-oF 织物
  → 存储前端端口 → 控制器
  → 写缓存（镜像 / NVRAM / 掉电保护）
  → 后端总线 → 存储池 / extent
  → SSD 或 HDD → 介质队列 → 完成

读命中缓存时可直接返回，未命中时要访问后端。预取、读缓存和访问顺序会影响尾延迟。写回（write-back）在缓存镜像完成后确认，写穿（write-through）等介质写完再确认。写回延迟低，还要检查掉电保护和缓存降级。

分别测量端到端路径中的各段延迟。

T_end2end = T_client_queue + T_fabric + T_frontend + T_cache_lookup
          + T_backend_queue + T_media + T_retry + T_software_overhead

为各段设置测量点。有一段没测到时，报告现有观测能把瓶颈缩小到哪一段。

用 M/M/1 队列说明利用率 ρ 和服务时间 S 如何影响响应时间。

平均排队时间 W = ρS / (1 − ρ)
平均响应时间 R = S / (1 − ρ)
利用率 ρ 响应时间是服务时间的倍数
50% 2×
70% 3.3×
80% 5×
90% 10×
95% 20×

SSD 内部并行，控制器也有多队列。M/M/1 可解释趋势，实际延迟以测量为准。表中利用率从 80% 升到 90%，响应时间从 5× 升到 10×。超过 85% 做容量规划时，要特别检查余量。

按下式换算 IOPS、带宽和块大小。

IOPS = 带宽 / 块大小

4 KiB 随机读 100 万 IOPS 约为 3.8 GiB/s。1 MiB 顺序读达到 3.8 GiB/s 时，约为 3,900 IOPS。比较性能时同时记录 IOPS、带宽、块大小和访问方式。

SSD 持续处理随机写时，可用块可能耗尽。垃圾回收（GC）随后与前台写争用，导致尾延迟升高。写放大（WA）可能让业务写 1 GiB 时，介质写 2–4 GiB。查 IOPS 时也看介质写量、GC 次数、磨损和预留空间（OP）。

1.2 文件存储：元数据路径与数据路径

文件存储至少有两条路径。

客户端 → 元数据服务（MDS / 文件系统管理） → 目录、锁、权限、布局
客户端 → 数据服务（DS / 存储节点）       → 实际读写

create、stat、readdir、rename、unlink 等元数据操作和读写数据走不同路径。小文件、深目录、并发 create、目录热点和锁竞争都可能先拖慢元数据。NFS 的 delegation/lease、SMB 的 oplock 和客户端的 attribute cache 都会影响测到的延迟。故障后还要检查客户端重连、会话恢复和锁回收带来的压力。

文件存储的 SLO 分别观察元数据操作延迟、数据读写延迟、元数据 IOPS、数据带宽和错误码分布。

1.3 对象存储：网关、索引与后端

对象请求通常经过以下环节。

S3 客户端 → 网关 / 负载均衡 → 认证与桶索引 → 元数据服务
          → 对象数据落到池 / 纠删码条带 → 后端节点

查尾延迟时，检查网关排队、桶索引热点、大对象、multipart 分片不均、LIST 扫描、慢节点和 EC 重建。S3 的 5xx、SlowDown、连接复用和重试策略会影响客户端观察到的长尾。按 GET、LIST 等操作和状态码分别统计 SLO。

1.4 分布式存储：以 Ceph 为例

Ceph 的 RADOS 层按以下路径放置对象。

对象 → pool → PG（placement group）→ CRUSH 映射 → OSD 集合
OSD → BlueStore → 块设备 → 介质

分别查看 PG 和 OSD 状态。

  • active 表示 PG 可以服务，clean 表示对象已达到配置的副本数。active+clean 是预期状态。检查数据完整性还要看 scrub 和其他健康项。
  • up/down 表示 OSD 进程是否可用，in/out 表示是否参与数据放置。两组状态都要保留。
  • degraded 表示部分对象未达到期望冗余。undersized 表示 PG 的副本集合小于期望。stale 表示 PG 映射变更后，Monitor 还未收到状态更新。
  • recovering 和 backfilling 分别表示恢复和回填。scrubbing 和 deep-scrub 表示校验。

OSD 下线维护后仍可能是 in。若被标为 out 且 PG 映射改变，可能触发 backfill，与前台写争用网络、CPU 和介质。P99 和队列上升、提交 IOPS 接近基线时，可以提出争用假设。再查块大小、读写比例、并发和更短窗口的突发。Ceph PG 状态 · Ceph OSD/PG 监控

Ceph Tentacle 的 mClock 为客户端、后台 recovery 和后台 best-effort 分配保底、上限和权重。backfill、scrub、快照裁剪和 PG 删除都归入 best-effort。调度变更前核对版本和 profile，变更后确认参数已生效并检查冗余。Ceph mClock

1.5 尾延迟放大：为什么平均值会骗人

同一个请求调用 k 个下游。假设每个下游独立地有 1% 的概率超过各自的 P99，可算出至少遇到一个慢下游的概率。

P(至少一个慢) = 1 − (1 − 0.01)^k
k 概率
10 9.6%
100 63.4%
1,000 99.996%

各下游的 P99 都达标时，仍要单独测端到端 P99。即使每个下游只有 0.1% 的概率超过各自的 P99.9，k=1000 时，仍有 63.2% 的请求会遇到至少一个慢调用。多副本、EC 条带、多路径以及分开的元数据和数据路径，都可能放大尾延迟。

压测时还要检查发送节奏和后台任务。

  • 协调遗漏（coordinated omission）。目标变慢时，压测工具也可能降低发送速率，系统性低估尾延迟。记录计划发送时间和实际发送时间的差，才能把被推迟的请求计入延迟分布。
  • 后台任务的延迟尖峰。GC、重建、快照或 scrub 正好落在取样窗口时，会抬高 P99。换窗口时也核对任务起止时间。

1.6 SLO：定义、聚合与燃烧率

定义 SLO 时写清在哪测、什么算好请求、哪些请求计入分母。以下以订单写请求为例。

好请求 = 成功 且 端到端延迟 ≤ 20 ms 的写请求
SLO = 好请求数 / 纳入统计的写请求数 ≥ 99.9% / 30 天

先算整个 SLO 周期允许的坏请求量。

预算 = (1 − SLO) × 总请求数
请求量近似均匀时，99.9% / 30 天 ≈ 43 分 12 秒的完全不可用等价时间
同一假设下，99.95% / 30 天 ≈ 21 分 36 秒

燃烧率（burn rate）衡量错误预算消耗得有多快。

burn_rate = 观测窗口内的错误率 / (1 − SLO)

燃烧率为 1 且持续整个 SLO 周期时，正好用完预算。请求量近似均匀时，14.4 倍燃烧率持续 1 小时会消耗 30 天预算的 2%。流量不均时，用观测窗的坏请求数除以整个周期的预算请求数。多窗口规则可要求 1 小时和 5 分钟窗口的燃烧率都超过 14.4。Google SRE

三个客户端的 P99 分别是 10/20/30 ms。全局 P99 取决于各自的请求量和尾部形状，仅凭这三个值无法得出。保留相同桶边界的直方图，按桶汇总后再算全局分位。

histogram_quantile(
  0.99,
  sum by (le) (rate(request_duration_seconds_bucket[5m]))
)

只有预计算的客户端分位数时，只报告各客户端的结果。低流量窗口要同时报样本量。窗口只有 100 个请求时，P99 可能由单次请求决定，应设置最小样本量，避免单条请求触发事故级告警。

2.2 指标模型与基数

指标名和标签集共同确定一条时间序列。

storage_pool_used_bytes{site="sh", cluster="ceph-a", pool="hot", unit="byte"}

标签用来分组。request_id、session_id、文件名和卷快照 ID 会随请求或对象不断增长，放进标签会产生大量序列。用稳定的 entity_id 标记实体，把显示名、别名和序列号放在实体表里。

用各个标签的取值数估算序列数量。

序列数 ≈ 实体数 × 每实体指标数 × 维度组合数

10,000 个 OSD，每个 100 个指标，共 100 万条序列。每 15 秒采样一次，每天有 57.6 亿个样本。按 2 字节/样本压缩，每天约 11.5 GB（单副本）。另算索引和查询的额外开销。

2.4 时间语义：事件时间、观测时间、知识时间

每条证据至少记三种时间。

  • event_time 是事情发生的时间，例如原始日志里的设备时间。
  • observed_at 是采集端看到数据的时间。早期资料也写作 observed_time。
  • available_at 是该条事件或证据首次可查的时间，对应本节所说的知识时间。由接入服务记录。

回放 02:16 的调查时，服务端从当时冻结的发布快照中筛选当前有权访问、且满足 available_at ≤ knowledge_cutoff 的记录。例如，一条日志在 02:12 被采集，但到 02:18 才能查，就不能出现在 02:16 的报告里。Ceph 实验的合成 CSV 用 observed_utc 表示可查时间，实际接入分别记录 observed_at 和 available_at。查拓扑时，从同一快照中选出事发时有效、到调查截止仍可查的版本。进阶篇 §7.2

处理数据迟到、时钟漂移、补数和重复上报。

  • 用接入端登记的 source_id 和该来源的 event_id 去重。同一来源重传时，保留原记录的首次可查时间。两个来源用了相同的事件 ID 时，各保留一条。
  • 按来源、信号和分区记录数据处理进度（水位，watermark）。判断某个窗口的数据是否齐全时，还要对照预期上报的对象和实际缺报的对象。
  • 计数器可能重置。用能识别重置的速率函数，核对重置附近的结果。
  • 单独标记缺失，在证据质量和结论中反映。

2.5 缺失机制与选择偏差

按缺失和观测值的关系区分三类情况。

  • 完全随机缺失（MCAR）。例如丢包与指标值无关。
  • 随机缺失（MAR）。缺失与已观测变量有关，例如观测到高负载时，采集器更容易丢数据。
  • 非随机缺失（MNAR）。缺失与未观测的值有关，例如设备快故障时采集 agent 先停报。

存储里常见 MAR 和 MNAR。一半 OSD 停报时，只剩健康 OSD 上报，仪表板的平均延迟可能下降。同时查采集覆盖率。

coverage = 实际上报的期望实体数 / 期望实体总数

每项聚合结果都带 coverage，并对覆盖率过低告警。覆盖率不足时，只报告已观测子集的均值或分位。

3.2 双时态：有效时间与知识时间

为每版拓扑关系保存以下字段。

edge: (src, dst, relation)
valid_from, valid_to      # 这条关系在现实中何时有效
observed_at               # 观测系统何时看到它
known_from, known_to      # 该修订何时对调查者可见
source, confidence        # 谁说的、有多确定

查询调查时所用的拓扑时，分别传入有效时点和知识截止时间。两个区间都包含起点，排除终点。网关先在冻结快照中检查边的来源和两端实体是否都获准访问，再把通过检查的边交给查询，示例将它们记为 authorized_snapshot_edges。

SELECT * FROM authorized_snapshot_edges
WHERE src_id = :workload
  AND valid_from <= :t AND (valid_to IS NULL OR :t < valid_to)
  AND known_from <= :knowledge_cutoff
  AND (known_to IS NULL OR :knowledge_cutoff < known_to);

若 02:20 才得知一条关系在 02:10 结束，就把旧版知识区间的终点设为 02:20，保留旧版原来的有效区间。然后新增一版，记下关系在 02:10 结束、新版从 02:20 起可查。这样回放 02:16 的调查时，仍能读到旧版。进阶篇 §7.1

4. 异常检测与告警工程

4.1 先选信号，再选算法

4.2 稳健基线：中位数与 MAD

先用基线样本 x1..xn 算出中位数和绝对偏差的中位数（MAD）。

median = 中位数(x)
MAD    = 中位数(|xi − median|)
z      = 0.6745 × (x − median) / max(MAD, ε)

公式中的 0.6745 让 MAD 分数在正态分布下与标准差可比。序列量化到 1 ms 时，MAD 可能为 0。此时给分母加下限 ε，或改用 IQR，避免 1 ms 抖动产生过高的 z。

实验里 M01–M05 的 P99 为 5, 6, 5, 7, 6，中位数为 6。绝对偏差是 1, 0, 1, 1, 0，MAD = 1。M06 的 P99 为 33 ms。

z = 0.6745 × (33 − 6) / 1 = 18.21

同样计算 M07 的 46 ms。

z = 0.6745 × (46 − 6) / 1 = 26.98

基线为 0.1 ms、MAD 为 0.01 ms 时，涨到 0.2 ms 也会得到很高的 z，业务却可能无感。再设变化幅度门槛，例如绝对增量 ≥ 5 ms 或相对倍数 ≥ 2，并要求连续 2 个采样点超限。实验里的 M06 首次超限，M07 再次超限才触发。

4.3 变化点与累积和

用累积和（CUSUM）检测均值小幅且持续的变化。

S_t = max(0, S_{t−1} + (x_t − μ0 − k))
若 S_t > h，报警

k 是容忍偏移，通常取 0.5σ。h 是决策阈值，通常取 4–5σ。CUSUM 对 SSD 磨损、端口误码和容量泄漏等缓慢变化比单点 z 更敏感。PELT 和 Bayesian change point 可离线分段，估计事故从何时开始。

4.4 多重检验：50,000 条序列的假阳性

假设 50,000 条序列各自服从正态分布。使用双侧 3.5σ 阈值时，每条序列单次误报的概率约为 0.000465。

50,000 × 0.000465 ≈ 23.3 条/次

每 15 秒采样一次，每天约有 13.4 万次单点超限。边际误报概率相同时，序列相关性会改变超限是否扎堆，期望次数仍可相加。连续窗口和聚合会改变实际通知量。若相邻采样相关，用正常时段回放估计。

可组合以下方法控制通知量。

  • 连续 N 个点超限才报（降低瞬时噪声）。
  • 要求效应量超过业务可感知阈值。
  • 按实体组做分层检验，再用 FDR/Bonferroni 控制组内误报。
  • 对同源序列做聚合，先在组级别检测，再下钻。
  • 维护“已知良性模式”白名单，但要有过期时间和审计。

4.5 告警聚合与因果抑制

把同一次事故的告警放在一起，按拓扑、时间和因果关系核对。

  • 拓扑。检查是否属于同一故障域、共享依赖或路径。
  • 时间。检查窗口是否重叠，传播延迟是否合理。
  • 因果。检查父子告警、上下游以及根因和衍生症状。

把两个独立根因合并会漏掉其中一个故障。保留原始告警 ID、规则版本和合并理由。DME 支持屏蔽、闪断/振荡、汇聚、相关性、自动确认、重定义和远程通知。相关性规则的父子关系由用户配置。外部资料拆解 §11

4.6 按 SLO 给告警分级

先用业务 SLO 的燃烧率确定告警级别。

severity = P1  若 1h burn_rate ≥ 14.4 且 5m burn_rate ≥ 14.4
         = P2  若 6h burn_rate ≥ 6
         = P3  若 3d burn_rate ≥ 1

再看冗余。业务 SLO 达标、冗余却已 degraded 时，优先修复冗余。业务 SLO 失守且冗余不足时，按事故响应。

5. 预测：容量、性能与介质

5.1 容量预测的账本

先确认哪些固定占用要从容量中扣除，哪些已计入用量。快照、克隆、元数据和回收站等占用只计一次。按下式扣除预留，再用可分配容量算告警线。

raw = 物理容量
冗余后容量 = raw × 冗余效率
冗余效率 = 1 / 副本数，或 EC 的 k / (k + m)
扣固定占用后容量 = 冗余后容量 − 单列的固定占用
可分配容量 = 扣固定占用后容量 × (1 − 预留比例)
告警线 = 可分配容量 × 告警比例

10 个节点，每个节点 12 块 20 TB 的盘，总容量为 2,400 TB。EC 8+2 的效率为 80%，冗余后容量为 1,920 TB。无另列的固定占用。扣一次 5% 预留，得到 1,824 TB 可分配容量。再按可分配容量的 95% 告警。假设当前已用 1,500 TB，每天净增 6 TB。

到 95% 水位的天数 = (1,824 × 0.95 − 1,500) / 6 ≈ 38.8 天

若每天净增 3 或 9 TB，则分别约在 77.6 天和 25.9 天后触线。报告列出各增长情景的结果。扩容、清理或调整生命周期规则后，用更新后的数据重新拟合。

随机切分会让未来信息泄漏到训练集，指标虚高。

5.3 性能预测与动态阈值

性能会随负载、周期和故障变化。预测时按不同用途选择窗口。

  • 用过去 1 个月预测未来 2 周（DME 白皮书披露的做法）。
  • 用过去 30 天预测未来 1 天，做“预测对比”健康扣分。
  • 用同工作负载、同时段的分位数作为动态阈值。
  • 用变化点检测识别突变。

用预测提前查到缓存命中率持续下降、端口误码增加、GC 变长或容量增长加快。

5.4 硬盘故障预测：标签、截尾与竞争风险

先定义盘在什么情况下记作故障。

样本 = (disk_id, day t, 当时可见的特征)
正例 = 该盘在 (t, t+H] 内发生“故障事件”
负例 = 该盘在 (t, t+H] 内没有故障，且观测未截尾
排除 = 主动退役、迁移、数据销毁、观测结束

把主动换盘标成故障，模型容易学到换盘策略。把停止观测的盘当成负例，则会低估风险。按设备和时间划分训练集和测试集，避免同一块盘的相邻日期混入两组，也确保同一盘的同一次故障只出现在一组。

特征只用当时可见的 SMART/NVMe 指标和变化率，包括重分配扇区、待定扇区、不可纠正错误、命令超时、CRC 错误、磨损、通电小时、温度、型号、固件和批次。树模型（GBDT）通常比 Logistic 回归表现好，仍需解释结果并做概率校准。

故障样本占比很低，评测还需看以下指标。

PR-AUC
召回率 @ 告警预算
每千盘日误报数
提前量分布（lead time）
概率校准（Brier / 校准曲线）

10,000 块盘的年故障率为 2%，每年约 200 次故障，平均每天约 0.55 次。以下假设召回率为 80%、精确率为 20%。

TP/天 = 0.55 × 0.8 = 0.44
总告警/天 = 0.44 / 0.2 = 2.2
误报/天 = 1.76

精确率只有 5% 时，每天约有 8.8 条告警，值班人员可能开始忽略告警。先确定每天能处理多少条，再反推阈值。

5.5 产品预测能力的读法

DME 25.1.0 白皮书和 DME IQ 页面分别披露了以下预测窗口、对象和算法。

  • 容量。最多用过去 180 天预测未来 1 年，按天输出。安装后至少 14 天，其中至少 11 天有有效数据。融合 SVM（多核）、ARIMA、对数回归和线性回归。
  • 性能。用过去 1 个月预测未来 2 周。健康评分的“预测对比”用过去 30 天预测未来 1 天。融合 Lasso、岭回归和随机森林。
  • 硬盘健康度。每天凌晨预测未来 14 天的健康度。低于 60 分判为风险盘。支持 SSD、NVMe SSD、SATA/SAS HDD 和 NL-SAS。
  • 硬盘故障。用希捷和日立 SAS HDD 的 10 天 SMART 数据预测未来 30 天是否故障。
  • DME IQ 页面。硬盘故障提前 14 天，性能趋势提前 2 个月，容量趋势提前 365 天。

采购验收前，要求提供定义、分母、故障类型、误报率和测试集。健康度 60 分是产品评分，换算成故障概率前需要校准。14 天和 30 天对应不同介质、模型和目标，分别验收。外部资料拆解 §11

5.6 漂移与反馈回路

固件、批次、工作负载、业务峰谷和运维策略改变后，检查以下指标。

  • 特征分布漂移（PSI/KL/KS）。
  • 预测分布漂移。
  • 校准漂移（预测 20% 的盘实际故障率是多少）。
  • 告警处置结果（真故障/误报/主动更换）。

模型报警后，运维可能主动换盘。这时已无法观察这块盘后来是否会故障。另记“因告警换盘”的干预标签。

6. 根因、证据与反证

6.1 相关、干预与反事实

存储现场很少有随机对照试验。调查可从相关、干预和反事实三个角度收集证据。

  1. 相关。A 和 B 同时异常，可能由同一个原因触发。
  2. 干预。改动 A 后，B 按预期变化。现场干预有风险，通常在受控窗口执行。
  3. 反事实。估计没有 A 时 B 会怎样，需要模型或对照数据。

报告要写清假设成立时还应该看到什么，以及什么结果会推翻它。

6.2 候选生成

沿事发时间、拓扑和故障域找候选。

候选 = 时间上先于症状的变更
     ∪ 事发拓扑上可达的实体
     ∪ 同故障域内共现异常的实体
     ∪ 已知故障树/历史工单匹配的模式
     ∪ 影响范围与对照不吻合的共享依赖

维护在 02:10:30 生效，backfill 在 02:11 开始。到 02:14 结束的窗口，测到尾延迟升高。02:18 收到晚到日志后，复盘才可补记 02:12:30 的应用积压。若可靠的证据显示 02:09 已变慢，重新检查触发事件和时钟。

6.4 故障树、因果图与 LLM

用三种方法分别处理结构化故障、因果关系和文本线索。

  • 故障树。专家把现象、子现象和根因连成树。适合边界明确的已知设备故障，规则可审计，覆盖取决于已建的故障模式。
  • 因果图。节点表示变量或事件，边表示假设的因果机制。用于表达共同原因、混杂因素和传播路径，需要领域知识维护。
  • LLM。从日志和工单提取线索、提出假设并组织报告，因果判断要由证据验证。

DME 的“智能分析”提供 I/O 全路径时延、资源瓶颈、故障分析、亚健康、配置分析和故障树。它基于规则和产品知识给出根因、传播路径和修复建议。可查明结论如何得出，覆盖范围取决于已支持的场景。外部资料拆解 §11

7.1 调查步骤和停止条件

7.5 上下文与防幻觉

给模型传入有明确字段的证据对象。

evidence_id, query_id, source_id, entity_id, window,
observed_at, available_at, quality, payload_ref, summary

  • 每个事实引用 evidence_id。

执行前重查拓扑、授权和冗余。任何一项发生变化，就重新评估计划。执行后分别检查业务 SLO 和数据耐久性。

8.3 存储特有的验证

P99 降低后还要查冗余和数据保护状态。

维度 指标 失败例子
业务 好请求比例、错误率、P99、吞吐 降级 QoS 让延迟好看，但业务被限速
冗余 degraded PG、副本同步、重建速率、校验错误 前台恢复，但副本还没同步
数据 快照年龄、复制 lag、备份成功、一致性 主可用，备不可用
容量 水位、预留、增长斜率 清理了日志，但快照仍在涨
配置 版本、参数、许可、拓扑 改了调度，但重启后回退

Ceph 的 P99 恢复后，继续查 degraded_pgs、恢复速率、scrub 错误和 OSD 是否再次 down。DME/Dorado 场景查控制器 CPU、缓存命中率、端口误码、复制或双活状态和硬盘健康。各产品的指标不同，业务和冗余都要验收。

8.4 从处置回到学习

每起事故结束后，将以下记录写入事故库。

症状、时间线、候选假设、证据、反证
实际根因、人工裁定、处置、验证结果
哪些证据缺失、哪些查询最有区分度
模型/规则版本、工具版本、数据快照 ID

用这些记录补充下一轮回放集，修订规则和验收条件。

8.5 评测集设计

评测集至少覆盖以下场景。

  • 真实事故回放。固定快照，隐藏答案，只用知识截止时间前的数据。
  • 合成故障。在实验环境模拟磁盘慢、网络丢包、OSD down 和元数据热点。
  • 负对照。用无事故窗口检查误报。
  • 缺数据变体。隐藏关键证据，检查是否降低结论强度。
  • 晚到数据变体。用事故结束后才到的日志，检查是否引用了未来数据。
  • 新版本和新型号。检查能否适应新版本和设备。
  • 跨租户和权限。检查是否拒绝越权查询或变更。

按事故、集群、时间和版本切分。隔离答案和复盘原文，使用独立裁定表评分。

8.6 指标与消融

维度 指标
检测 事故级召回、误报/集群日、首次告警延迟
定位 根因 Top-1/Top-3、候选召回、TTL
证据 引用正确率、关键事实支持率、缺数据暂缓率
处置 建议可执行率、越权拒绝率、SLO 恢复时间、冗余恢复时间
成本 工具调用数、P95 调查时长、每事故 token/查询成本、人工核实时间

从规则开始，依次加入统计、带工具的 Agent、拓扑与 RAG、因果图与故障树。每次都用同一份快照，比较新增组件带来的变化。

8.7 公开基准与边界

AIOpsLab、RCAEval 和 ORCA-bench 提供任务框架、盲测、候选召回和重排评测，主要覆盖云应用和微服务。存储要另建物理故障域、后台恢复、介质退化、双验收案例。Backblaze 和 FAST ’20 可用于硬盘预测，存储 RCA 仍需独立评测。

8.8 多集群与数据主权

多集群可以按站点、区域和全局组织。

站点边缘：就近采集、缓冲、脱敏、粗聚合
区域中心：跨站资产目录、证据索引、查询路由
全局：策略、模型、评测、审计

尽量在数据所在站点执行查询，按需回查明细。断链时保留缓冲和采集水位，恢复后补数并标记迟到。接入采集前确定租户隔离、数据驻留和跨境规则。

8.9 落地路线

阶段 交付 验收
0–1 月 实体表、SLO、采集覆盖率、事件时间语义 能查到事发状态和缺失数据
1–3 月 规则 + 稳健基线、告警聚合、事故时间线 每集群每天的误报数在预算内，MTTD 下降
