0. 三条流

业务 I/O
  应用 → 客户端/协议网关 → 存储池/PG → OSD/控制器 → 介质

遥测与知识
  指标/日志/事件/变更/拓扑 → 采集与实体对齐
  → 时序库/事件库/历史拓扑/文档索引 → 异常/预测/证据

调查与处置
  投诉/告警 → 工具查询 + 文档检索 → 假设/反证/影响范围
  → 受监督处置 → 业务+冗余双验收 → 回放/学习

三条流的时间语义不同：业务 I/O 是毫秒级，遥测是秒/分钟级，调查是分钟/小时级。专家系统的核心工作是把三条流对齐到同一个实体和时间窗。

1. 存储语义与服务目标

先画请求路径：

块：应用 → 客户端队列 → FC/iSCSI/NVMe-oF → 前端端口 → 控制器/缓存
    → 后端 → 池/extent → SSD/HDD

文件：客户端 → 元数据服务（目录/锁/权限）→ 元数据池
      客户端 → 数据服务 → 数据池

对象：S3 客户端 → 网关/认证 → 桶索引/元数据 → 对象数据 → EC/池

Ceph：对象 → hash → PG → CRUSH → OSD 集合 → BlueStore → 介质

机制：块存储的写路径关键在“何时向主机确认”（写回/写穿）；文件存储要分开元数据路径和数据路径；对象存储要分 GET/PUT/LIST；Ceph 要区分 active/clean/degraded 与 up/down/in/out。不同路径的瓶颈不同，不能用一个“存储延迟”概括。

SLO：写清测量点、好事件、分母。例子：

好请求 = 成功 且 端到端延迟 ≤20ms 的写请求
SLO = 好请求数 / 纳入统计的写请求数 ≥99.9%/30 天

不同客户端的 P99 不能平均；有相同桶边界的直方图，按 le 求和后再算全局分位。低流量窗口要带样本量。

例子：订单写 P99 从 6ms 升到 46ms，但 IOPS 从 1000 只降到 990，错误率略升。IOPS 不变说明不是流量洪峰，而是同样负载下服务时间变长；要查后端队列、backfill、缓存、网络，而不是先扩容。

参考：Ceph OSD/PG 监控 · Ceph 健康检查 · Prometheus 直方图

2. 采集、时序与海量成本

流水线：

设备/主机/应用
   │ 拉取/推送：REST、SNMP、SSH、OTel、syslog
   ▼
采集与缓冲（去重、水位、背压）
   │
   ├─ 时序库（指标/直方图）
   ├─ 事件库（告警/变更/工单）
   ├─ 对象存储（日志/证据快照）
   └─ 文档索引（Runbook/复盘）

机制：指标要定义实体、单位、标签；标签是维度，不是流水号。计数器先处理重置再求速率；缺失不等于 0；事件时间/观测时间/知识时间要分开。采集覆盖率是“一等指标”：一半 OSD 停报时，平均延迟可能下降，但覆盖率会暴露样本偏差。

成本算例：

50,000 序列 × 86,400/15 = 288,000,000 样本/天
2 字节/样本 ≈ 576 MB/天（单副本）
3 副本 ≈ 1.7 GB/天；一年 ≈ 0.63 TB

分层：原始 7–30 天，聚合 6–12 个月，天级 2–5 年；秒级数据只用于现场。DME 的产品化策略是分钟级 7 天、30 分钟 6 个月、天级 2 年，5 秒历史按需从设备读、最长一周。

例子：调查先读集群趋势，再缩到池/OSD/变更窗口；每一步带覆盖率和查询预算。若 coverage <80%，禁止输出“全局平均”，只报“已观测子集”。

参考：OpenTelemetry 日志模型 · Ceph Prometheus 模块 · Prometheus 原生直方图

3. 资产、身份与时态拓扑

图模型：

Workload → Volume/LUN/FS/Bucket
Volume   → Pool → PG → OSD → Disk
Host     → HBA/Port → Switch Port → Array Port → Controller
Array    → Site/Rack/Power/FailureDomain
Change   → Target
Incident → Symptom/Entity
Runbook  → Product/Version/FaultCode/Symptom

机制：实体用稳定 ID、别名和生命周期，OSD 数字编号可能复用，因此记录 UUID。边的每个修订保留有效区间、知识区间和来源观测时间。查询“02:16 可见、02:10:30 有效”的拓扑时，事发时点匹配 [valid_from, valid_to)，调查截止匹配 [known_from, known_to)。晚到的纠正作为新修订保存，旧修订可供历史回放。

例子：维护 osd.11 前后两版拓扑：

T01 02:00–02:10:30：orders → vol01 → hot → PG1 → osd.11/12/13
T02 02:10:30 起：  orders → vol01 → hot → PG1 → osd.12/17/18

02:16 的报告用 T02 解释 backfill 目标；用 T01 解释维护前路径。两版都保留，不能只存当前拓扑。

参考：Ceph OSD/PG 监控 · AWS DevOps Agent 服务卡

4. 异常检测与告警聚合

流水线：

指标/日志/事件
   ├─ 规则（硬边界/合规）
   ├─ 统计基线（同组/同时段/滚动中位数+MAD）
   ├─ 变化点（CUSUM/PELT）
   └─ 多指标模型（隔离森林/矩阵画像）
        │
        ▼
异常候选 → 持续性/效应量/最小样本 → 告警
        │
        ▼
按拓扑/时间/因果聚合 → 业务 SLO 分级

机制：固定阈值适合硬边界。处理季节性和工作负载变化时，可用分组基线。MAD 要处理分母为零。在正态边际分布和双侧 3.5σ 阈值的算例中，5 万序列每轮采样期望约 23 次单点超限。实际通知量用连续窗口、效应量、最小样本和聚合规则回放评估。聚合要保留原始告警 ID 和合并理由。

例子：M01–M05 P99=5,6,5,7,6 → 中位数 6、MAD 1；M06=33 → z=18.21，M07=46 → z=26.98。若规则要求连续 2 点，M07 才触发；M07 好请求 93.27%，M08 对照 99.97%。这说明“设备告警”与“业务故障”可以同时存在，也可以有时间差。

参考：NetApp DII Monitor · Dell PowerStore 可观测性

5. 容量与硬盘风险预测

容量账本：

raw → usable（副本/RAID/EC）→ effective（快照/克隆/元数据/回收站/水位）
到阈值天数 = (effective × 阈值 − 已用) / 净增

硬盘样本：

样本 = (disk_id, day, 当时可见特征)
正例 = 未来 H 天内真实故障
排除/删失 = 主动更换、迁移、观测结束
切分 = 按时间 + 按设备，禁止同盘泄漏
评测 = PR-AUC、召回@告警预算、提前量、校准

机制：容量预测的难点是口径（raw/usable/effective），不是模型；硬盘预测的难点是标签/截尾/竞争风险，不是分类器。厂商的“14 天/30 天/健康度 60 分”是不同口径，不能互换，也不能直接当概率。

例子：2,400 TB raw、EC 8+2（80%）、5% 水位、已用 1,500 TB、净增 6 TB/天 → 到 95% 水位约 38.8 天；净增 3/9 TB/天 → 77.6/25.9 天。硬盘 10,000 块、AFR 2%、召回 80%、精确率 20% → 总告警 2.19/天，其中误报 1.75/天。

参考：FAST ’20 硬盘预测 · Backblaze Drive Stats

6. 根因、证据与反证

流程图：

症状/影响范围
   │
   ├─ 时间上先于症状的变更
   ├─ 事发拓扑可达的实体
   ├─ 同故障域共现异常
   ├─ 已知故障树/历史工单
   └─ 对照（未受影响业务）
        │
        ▼
候选假设 → 每项写：支持/反证/鉴别查询/停止条件
        │
        ▼
根因 + 传播 + 系统性原因（三层）

机制：相关不等于因果；最强证据是“时间领先 + 路径可达 + 剂量响应 + 特异性 + 对照 + 干预响应”。故障树适合已知设备故障，因果图适合共同原因/传播，LLM 适合从非结构化线索生成假设；三者结合，不要让 LLM 单独判因果。

例子：维护 osd.11 → backfill 与前台写争用。H1 backfill：支持 E01/E02/T02/M06/M07；反证缺口是 OSD 级队列/恢复速率；鉴别是限速 backfill 后 P99 是否降。H2 备份：E03 在另一站点、T03 无共享路径、M08 对照正常 → 解释力低。H3 网络：重传持平 → 只降低已观测 TCP 路径故障，不能排除交换机端口丢包。

参考：Ceph OSD/PG 监控 · RCAEval

7. LLM 调查、RAG 与工具契约

流程图：

症状/窗口/权限
   → 查采集健康/覆盖率
   → 查业务影响（SLO）
   → 查事发拓扑
   → 查变更/事件
   → 生成候选假设
   → 对每个假设选最有区分度的查询
   → 证据足够/预算耗尽/需人工 → 报告/未决

工具契约：每个工具要有输入 schema、输出 schema、时间语义、权限、错误类型、查询 ID。例子：

query_metric(entity_id, metric, start, end, step)
  → unit, samples, missing_intervals, coverage, query_id, source

RAG：先按 ACL/租户/产品/型号/版本/故障码/审批/生效时间过滤，再做关键词+向量召回、重排；冲突文档返回版本/出处/适用范围，不强行合并。证据对象带 evidence_id/query_id/source/entity_id/window/observed_at/quality/payload_ref；报告区分事实/推断/未决。

例子：同一份 02:16 快照，“直接问模型”可能编造 46ms 的“平均值”；“工具约束+证据 ID”会返回 M06/M07 的窗口、单位、覆盖率和查询 ID，验证器还能拒绝引用 E04（02:18 才可见）。

参考：Fusion MCP 指南 · DII MCP · AWS 服务卡

8. 处置、验证与评测

流程图：

调查结论
   → 变更请求（目标/前置/预期/幂等/回滚/观察窗/审批）
   → 再次读取状态（拓扑/授权/冗余）
   → 执行（A2/A3/A4 分级）
   → 业务 SLO 验收 + 冗余/耐久性验收
   → 写回事故库/评测集

机制：调查与处置分开授权；读工具默认开，写工具默认关；每次变更要有幂等键、回滚、爆炸半径和观察窗。存储处置必须双验收：业务指标恢复不等于副本/复制/备份恢复。

例子：Ceph 回放中模拟调度调整后，02:25 的窗口写 P99 为 14 ms，好请求比例约 99.95%，仍有 11 个退化 PG。业务窗口已达标，继续检查冗余、恢复进度和新故障域压力。 实验验收

评测：同一快照比较规则、规则+统计、Agent+工具、Agent+工具+拓扑/RAG；指标包括检测、Top-k、证据正确率、缺数据暂缓率、越权拒绝率、成本。回放集要有正常、真实、缺数据、晚到、负对照；按事故/时间/集群切分，隐藏答案。

参考：Ceph mClock · AIOpsLab · RCAEval · ORCA-bench

9. 多集群与落地

分层：

站点边缘：就近采集、缓冲、脱敏、粗聚合、断链续传
区域中心：跨站资产目录、拓扑快照、证据索引、查询路由
全局：策略、模型、评测、审计（不存明细）

机制：查询尽量下推，明细按需回查；断链时保留水位，恢复后补数并标记“迟到”；租户隔离/数据驻留要在采集层设计。多集群不是“把所有明细集中”，而是“目录集中、证据按需”。

落地里程碑：

阶段 交付 验收
0–1 月 实体表、SLO、覆盖率、事件时间 能回答“当时是什么、缺了什么”
1–3 月 规则+稳健基线、告警聚合、时间线 误报/集群日可接受，MTTD 下降
3–6 月 时态拓扑、变更关联、证据对象、RAG 根因 Top-3 + 证据可复核
6–12 月 工具层/MCP、Agent 调查、回放评测 同快照可复现，缺数据会暂缓
12 月+ 受监督处置、双验收、有限自治 越权为零，回滚可演练

参考：Ceph Prometheus 模块 · Fusion MCP 指南
